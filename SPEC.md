## 1. Objective and instructions to the coding harness

A usable, publicly accessible Apron demo backend on native Cloudflare Workers, one SQLite-backed Durable Object (DO), and hibernating WebSockets: guest use and passkey authentication, bounded posting and history, and graceful resource exhaustion. It runs on Workers Paid ($5/month) within its included usage, and must still run on the Workers Free plan without paid services when its free budgets are selected (`src/plans/free.ts`).

This specification defines deployment policies within the base chat protocol; preserve the protocol's mandatory behavior and document material differences. MUST marks required behavior and SHOULD preferences. All limits live in validated configuration with the defaults below; do not silently raise them to make tests pass. Client changes (passkeys, rolling-history recovery) belong in the frontend repository. Do not deploy, switch billing plans, or create paid resources as part of a change.

### Required capabilities

- Protocol v10 core: the `server` announcement with liveness `ping` and a sign-in `welcome`, `auth` as a barrier, the default room, flat message snapshots delivered to rooms' members (the sender's broadcast before its result), framing, errors, and one server-wide log ID sequence.
- `history`, `edit`, `rooms`, `reactions` and `command` (section 4); `activity` (section 4.2); `embed:upload` with the Workers Paid budgets (section 4.3); live text, `embed:terminal` and `embed:append`, with the Workers Paid budgets (section 4.5); push (`webpush` only) and `status` where VAPID keys are configured (section 4.4).
- Guest authentication, read-only unless `GUEST_POSTING=true`; verified WebAuthn registration and login; bot, device, admin and invite tokens (section 5).
- Persistent request deduplication for mutating operations (section 8).
- Rolling history with permanent room IDs: 7 days with daily cleanup on Workers Paid, 24 hours with hourly cleanup on Workers Free; base-protocol availability boundaries and client recovery (section 9).
- Enforced application budgets, including cleanup, auth, and quota bookkeeping (section 7).
- System identities use the `~` prefix (notices come from `~private`, sent to one connection only); no user is given a `user_id` starting with `~`.

### Non-goals

No public workspace creation, top-level public room creation except by admins and mods, private threads, federation, multiplexing proxy, a presence service beyond `status` (no last-seen times but `seen`, section 4.4, User status; no status text), uploads other than images and audio, live text beyond section 4.5 (no text kept while it streams, so none survives a restart; no resumed writes; no `GET` of a text after it ends; no writer grace period), the `relay` push kind, push wake scope `badge`, and `joined` for anyone but admins and mods, read receipts (another user's read cursor) outside private rooms, email and external sign-in (the `email` and `external` schemes, protocol §4.11: the demo has no way to send mail and no sign-in page), bearer-token rotation, external URL previews, outbound bots, RTC, arbitrary search, FTS, or third-party analytics. Do not advertise unsupported capabilities. Passkeys do not establish one-human-one-account or solve Sybil resistance.

## 2. User scenarios

1. A visitor opens the public demo, connects, authenticates as a guest, and reads recent history without signup; posting, reacting, and starting threads take a passkey sign-in.
2. Several anonymous tabs behind one IP share the five-posts-per-minute allowance; opening another socket does not reset it.
3. A visitor creates a passkey or signs in with one. Successful authentication grants the registered allowance of twenty posts per minute, subject to IP and global limits.
4. A user reconnects after losing a mutation reply. A retry with the same request ID and authenticated identity returns a result reflecting the current state without another mutation or broadcast.
5. A connected client watches a room while another client loads history. Neither misses entries at the history/live boundary.
6. A user returns after more than the retention window (7 days; Free: a day). The client notices the retention boundary, clears stale recovery state, and rebuilds the available room view.
7. An old message edited within the retained window remains recoverable from its complete recent snapshot even after its creation record is purged.
8. A bot floods requests or creates identities. Per-principal controls and global budgets reject work without unbounded database, memory, or object creation.
9. A resource budget runs out. Posting, history, registration, or admission becomes unavailable as appropriate; accepted messages remain recoverable while resources permit.
10. The object hibernates, wakes, restarts, or is redeployed. Identity, room sequencing, retention boundaries, quotas, and deduplication remain correct; clients can reconnect when necessary.

## 3. Deployment and architecture

Use TypeScript, Wrangler, the native `DurableObject` base class from `cloudflare:workers`, and embedded SQLite. Follow the repository's tooling; pin resolved dependencies and a tested compatibility date. Prefer a small dependency surface and a maintained Workers-compatible WebAuthn verifier instead of handwritten cryptographic verification.

| Component | Responsibility |
| --- | --- |
| Entry Worker | Validate `/` and `/ws` upgrade requests, configured guest origin policy, route/method/body bounds, derive trusted IP metadata, apply cheap preliminary admission controls, forward to the fixed DO |
| `ApronDemoServer` DO | Own sockets, authenticate, authorize, sequence protocol operations, enforce budgets, persist state, serve history, broadcast, run cleanup |
| Embedded SQLite | Authoritative room records, the server-wide record log, current message and reaction state, credentials, deduplication, budgets, rate-limit state, maintenance progress |
| Existing Apron frontend | Guest access, passkey UI, retry/backoff, retention-aware recovery and concise demo status |

Exactly one production object is reachable, e.g. `env.DEMO.getByName("public-demo-v1")`. Never derive its name from an untrusted URL, room, user, or query parameter. There is one permanent room, `general`, displayed as General. Room IDs and the last log ID do not reset on cleanup or at midnight.

Use `new_sqlite_classes` for the initial Wrangler migration. Do not add D1, Workers KV, Queues, or a separate quota DO. Test/staging namespaces count toward account usage if deployed; do not assume an independent free allowance.

Return cheap 404/405 responses for unrelated routes without invoking the DO. On the host that is `RP_ID`, answer `GET` and `HEAD` of `/.well-known/webauthn` from configuration, without the DO: `{"origins": [...]}`, the `RP_ORIGINS`, as `application/json` with `Cache-Control: public, max-age=300` ([WebAuthn related origins](https://www.w3.org/TR/webauthn-3/#sctn-related-origins)); elsewhere, or without `RP_ID`, it is any other path. Serve the UI as static assets where the repository supports it. No polling endpoint may issue unbounded DO calls. Administrative metrics, if exposed, require authenticated operator access and contain aggregates only.

Cloudflare recommends the hibernation API for WebSocket servers: [WebSocket guidance](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

### Socket lifecycle

- Accept with `ctx.acceptWebSocket(server)`, not `server.accept()`.
- Implement `webSocketMessage`, `webSocketClose`, and `webSocketError`.
- Immediately send the protocol `server` announcement, before authentication.
- Store a versioned, bounded attachment containing connection ID, trusted IP key, auth identity/tier, pending challenge metadata, and any connection-local limiter leases. Re-serialize after changes.
- Keep attachments comfortably below the platform's 16 KiB maximum; do not put message history or credentials into them.
- Reconstruct connection indexes through `ctx.getWebSockets()` and attachments after hibernation. Check socket state before sending. Reconstructed indexes are caches, never durable authority.
- Do not re-send initial announcements or repeat auth just because the constructor runs after hibernation. Actual reconnects authenticate again.
- Liveness is the protocol's `ping` (`server.ping`, 45 seconds, [PROTOCOL.md §1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#1-transport--framing)), since the runtime cannot send WebSocket pings. The exact frame `{"method":"ping"}` is answered `{"method":"pong"}` by `setWebSocketAutoResponse` without waking the object, before authentication too, and spends no frame budget; a `ping` spelled otherwise is answered by the handler as an ordinary frame.
- A connection that has pinged and then sends nothing for `ping_timeout_seconds` (150), or that never pinged and sends nothing for `unpinged_timeout_seconds` (900) since it opened, is stale: it is closed with 1001 before `members` are listed and before admission, and does not count against its IP's connection limits. One that never pinged is first sent a `~private` notice, with no `room_id`: "Did not receive `{"method":"ping"}` in 15 minutes, closing stale connection." Workers Logs record each sweep that closes any (`stale_connections_closed`, with counts and up to 8 origins). Each close is also counted, unsampled, in the `METRICS` Analytics Engine dataset (`stale_close`, with `pinged` or `unpinged` and the origin; [configuration](docs/configuration.md), Metrics).
- No permanent `setInterval` or `setTimeout`, and no alarm, for liveness. Waiting status changes use the object's alarm, not a timer (section 4.4, User status); the one in-memory timer is a push wake's wait (section 4.4, Wake).
- Share one DO alarm scheduler between auth deadlines, cleanup, and maintenance retries. Always schedule the earliest outstanding task; cleanup scheduling must not overwrite an earlier auth deadline.
- A closing socket may remain visible to the runtime; do not let it receive broadcasts or grant extra admission while its close is pending.

API reference: [Durable Object state](https://developers.cloudflare.com/durable-objects/api/state/).

## 4. Feature and protocol contract

An illustrative initial announcement is:

```json
{"method":"server","params":{"apron":10,"agent":"apron-cloudflare-demo/10","capabilities":["history","edit","rooms","reactions","command","activity","embed:upload","embed:terminal","embed:append","status","ext","ext:settings","ext:limits","ext:media","ext:permissions","ext:emoji"],"auth":["webauthn","token","guest"],"signup":["webauthn","token"],"welcome":"**Apron public demo.** Guests can read along. **Create a passkey** to post, react, and start threads; it signs you in on your next visit too. An admin's invite token also creates an account; add a passkey once you're in, so you can sign in again without it. Bots sign in with a token their owner gets from `/invite-bot`. Messages are kept for 7 days.","title":"Apron Demo","description":"The public demo of [Apron](https://github.com/shazow/apron), an open chat protocol.","avatar":"https://web.apron.chat/icon-512.png","ping":45,"push":{"webpush":{"key":"<VAPID public key>"},"wake":["mentions","replies","private"]},"status":["dnd","invisible"],"ext":{"settings":{"read_cursors":true,"read_receipts":"private","private_rooms":20},"media":{"origins":["https://media.apron.chat"],"upload":{"image/png":{"max_bytes":5242880},"image/jpeg":{"max_bytes":5242880},"image/gif":{"max_bytes":5242880},"image/webp":{"max_bytes":5242880},"audio/webm":{"max_bytes":5242880},"audio/ogg":{"max_bytes":5242880},"audio/mp4":{"max_bytes":5242880}},"avatar":{"image/png":{"max_bytes":262144},"image/jpeg":{"max_bytes":262144},"image/gif":{"max_bytes":262144},"image/webp":{"max_bytes":262144}},"emoji":{"image/png":{"max_bytes":262144},"image/jpeg":{"max_bytes":262144},"image/gif":{"max_bytes":262144},"image/webp":{"max_bytes":262144}}},"emoji":{"catalog_url":"https://media.apron.chat/e/c/<sha256>.json"}}}}
```

The frame carries the protocol version as `apron` (10), the implementation string as `agent`, and `capabilities` ([PROTOCOL.md §3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#31-server-frame)). `auth` may carry `agent`, the client's implementation string for debugging; the server accepts and ignores it.

- `welcome` ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication)) is `general`'s current `description`, read for each connection. While `general` has none, or the read cannot be afforded, it is a generated summary of how guests, passkeys and bot tokens fit together and the retention, worded for what the connection can sign in with.
- `auth` lists the schemes the connection is offered: `webauthn` (canonical §4.10, no extension flag) only on origins configured for passkeys, `token` and `guest` always. `email` and `external` are never offered; an `auth` with either, or with `webauthn` where it is not offered, is `unsupported`, and one with a scheme the protocol does not define (such as `ext:foo`) is `invalid_params`, all before an authentication attempt is charged. `signup` lists `webauthn` where offered and `token`, which creates an account only with an admin's sign-up invite (`/invite-code`, section 5, Admins). `guest` is listed only in `auth`.
- With presence on, `status` lists `["dnd", "invisible"]` (section 4.4, Status).
- `capabilities` lists `ext` (Framing, ordering, and errors, below) and the [EXTENSIONS.md](https://github.com/shazow/apron/blob/main/EXTENSIONS.md) extensions `ext:settings`, `ext:limits` (section 6), `ext:permissions`, `ext:media` where uploads are configured, and `ext:emoji` where uploads are configured and the catalog has an emoji (each below).
- Every later `server` frame is a full replacement. The server sends one to every connection when the custom emoji catalog or the server's `title`, `description` or `avatar` changes. Temporary throttling does not mean a capability is unimplemented.

`title`, `description` and `avatar` ([PROTOCOL.md §3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#31-server-frame)) are the same for every connection. Each is what an admin set with `/server` (section 5, Admins; `_meta` rows `server:title`, `server:description`, `server:avatar`), else its variable (`SERVER_TITLE`, `SERVER_DESCRIPTION`, `SERVER_AVATAR`; [configuration](docs/configuration.md#server-title-description-and-avatar)), else none, except that the description falls back to `general`'s `description`, trimmed, when that is at most 500 bytes with no control character but line feeds (a longer one is left out, not cut). An empty variable counts as unset; a malformed one fails the configuration check. `RP_NAME` names the server to WebAuthn only, never as `title`. The stored values are read once per wake and kept in memory; while that read cannot be afforded, the variables apply. A `room_set` that changes `general`'s description while it is the server's sends every connection a new `server` frame. The server's avatar upload is section 4.3.

History availability is part of the base protocol's `history` capability, with no extension negotiation. Use `latest_log_id` and nullable `history_log_id` in room records (`room_list`, `room_update`) and history results, following protocol [§4.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#42-rooms) and [§4.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#43-history). Both are per room.

After final authentication, reply with `result.you`, a complete user object (Messages, edits, rooms, and reactions, below; the internal quota tier is private). Live delivery for the joined rooms starts with the auth result; the client lists them with `room_list` (`filter: "joined"`). `auth` is a barrier ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication)): each connection's frames are processed one at a time in arrival order through an in-memory queue, since the runtime delivers further `webSocketMessage` events while a handler awaits. Requests pipelined behind `auth` run as the `auth` left the connection: as the new identity after a success, and as before after one that authenticated nothing (a failure, or a WebAuthn `begin`). A `user_id` requested in `auth` is not honored, nor a `name` except in a passkey registration's `begin` (section 5); identities come from the server's guest counter or the verified credential or token. Do not send room records to unauthenticated sockets.

### Extension `ext:settings`

[`ext:settings`](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#extsettings) carries server-wide settings that clients adapt their interface to, beyond what the capabilities say. The `server` frame lists it in `capabilities` and carries its data under its name in the frame's `ext` ([PROTOCOL.md §4.12](https://github.com/shazow/apron/blob/main/PROTOCOL.md#412-ext)): `server.ext.settings`. It needs only its own capability, not `ext`, and defines no other name. This server always sends these keys:

| Key | Default when absent | Meaning |
| --- | --- | --- |
| `read_cursors` | `true` | An `activity` `read_message_id` is kept. `true` here with `activity`, and `false` without it: a registered user's are kept for the rooms they joined and sent after their listings (section 4.2); a guest's are dropped. |
| `read_receipts` | `false` | Where a member's `read_message_id` is shown to a room's other members (read receipts): `"private"`, in private rooms of at most 10 members only, with `activity`, and `false` without it (section 4.2). |
| `private_rooms` | no limit | The most private rooms without a `parent_room_id` one user may be a member of (`privateMembershipsPerUser`, section 4). |

What each user may do, such as whether a guest may post or a user may add others to rooms, is in their own `you` (extension `ext:permissions`, below). Like any `server` frame field, a later frame replaces it in full.

### Extension `ext:media`

[`ext:media`](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#extmedia) says where uploads are served from and which files the server keeps, so a client can load them and shrink a file to fit before it uploads. Where uploads are configured (section 4.3), the `server` frame lists it in `capabilities` and carries `server.ext.media`:

- `origins`: `[MEDIA_ORIGIN]`, the origin the bucket serves uploads from, only when it is not `PUBLIC_ORIGIN`, the server's own.
- `upload`: what a `write_url` of an attachment keeps, one key per exact MIME type (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `audio/webm`, `audio/ogg`, `audio/mp4`, the upload sniffer's own list in `src/image.ts` and `src/audio.ts`), each `{max_bytes}`, the plan's `maxFileBytes` (5 MB on Workers Paid). Write responses are section 4.3, Writes.
- `avatar`: the same for `/avatar`, the four image types with the plan's `maxAvatarBytes` (256 KB on Workers Paid).
- `emoji`: this server's own key, the same for `/emoji add` (extension `ext:emoji`, below), the four image types with the plan's `maxEmojiBytes` (256 KB on Workers Paid).

No `max_side` is sent: images are kept as written, of any dimensions, never scaled. While an admin has turned uploads off (`/toggle uploads`), the frame still lists `ext:media` with `origins`, since uploads already made are still served, but leaves out `upload`, `avatar` and `emoji`, as it leaves out `embed:upload`. Without uploads configured it is neither listed nor sent.

### Extension `ext:permissions`

[`ext:permissions`](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#extpermissions) tells a user what they may do, so a client offers only what works. The `server` frame lists it in `capabilities`, and every `you` carries `ext.permissions` (the `auth` and `me` results, and `user` `you`): an object whose absent keys take their defaults, so the server sends only the keys that differ, and `{}` when none does. Other users' objects (`new`, room `users`, `from`) never carry it. Keys:

- `write` (default `true`): may send `message`, `reactions`, `room_join`, `room_leave` and `room_set`, the `write` row of `ext:limits`. `false` for a guest while guests only read (`GUEST_POSTING` off, section 5, Guest), so a read-only guest's `you` carries `{"write": false}`.
- `add_members` (default `false`): may add other users to any room with `room_join` and a `user_id` (section 4, Memberships): `true` for an admin always, and for any other registered user but a bot while `addmember` is on (an admin's `/toggle addmember`). Members of a private room may add others to it, and an owner their own bot, without it.
- `move_any` (default `false`): may move other users' messages between rooms, into a thread or back out (section 4, Messages): `true` for a registered user with the role `admin`, `mod` or `threader` (`MODERATOR_ROLES`, which the move's commit checks), but an owner's bot, whose identity tier is `bot`, even with such a role.

It is the server's: `me` ignores an `ext.permissions` key, as it ignores `roles`, and a stored one is never read. A role change (`/admin`, `/role`) sends `user` `you` with it, and `/toggle addmember` sends each connected registered user but admins and bots `user` `{you: {user_id, ext: {permissions}}}` with the new value (`{}` clears the keys lost). The server still checks each request.

### Extension `ext:emoji`

[`ext:emoji`](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#extemoji) adds custom emoji: images that admins, mods and friends add, which users write as `:name:` in reactions and text. Where uploads are configured and the catalog has at least one emoji, the `server` frame lists `ext:emoji` in `capabilities` and carries `server.ext.emoji` `{"catalog_url": "<MEDIA_ORIGIN>/e/c/<sha256>.json"}`: the catalog, a JSON object mapping each key to `{url, width, height}` (`width` and `height` where the image's header gives them). The catalog is public, as uploads are, so the frame carries it before sign-in too.

- Managing, the suggested convention ([EXTENSIONS.md, Managing](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#managing)): `/emoji add :name:` with exactly one `upload` embed answers with the embed's `write_url`; when the write finishes, the image (`e/<id>`, PNG, JPEG, GIF or WebP, at most `maxEmojiBytes`; audio is `415`) becomes the key's, replacing an image the key had. `/emoji remove :name:` removes the key, and answers with a `~private` notice before the result. Both are for registered users with the role `admin`, `mod` or `friend`, other than bots; others get `denied`. A name is 1 to 32 of `[A-Za-z0-9_+-]`, case-sensitive; anything else, and a remove of a key the catalog lacks, is `invalid_params`.
- Storage: the catalog is one `_meta` row (`emoji_catalog`) holding the JSON exactly as published, absent while empty, read once per wake when first needed and kept in memory. Emoji uploads are `uploads` rows with purpose `emoji`, the key in `message_id`, owned by `~emoji` (the server), so `/purge` and `/rename` leave them; they never expire. An image an edit replaces or removes becomes `superseded` and keeps its row and bytes until deleted (Publishing).
- Publishing: each edit runs in the mutation queue. The new catalog is written to R2 at `e/c/<hex SHA-256 of the JSON>.json` (`application/json`, `Cache-Control: public, max-age=31536000, immutable`) first, then the edit commits in one transaction with the upload it finishes, then every connection gets a new `server` frame. So `catalog_url` changes whenever the catalog does and never names a missing object. The previous catalog and the images only it refers to are kept until the next edit, which deletes them unless it makes that catalog current again. Emoji images and catalogs have no lifecycle rule. An edit that cannot publish (R2 unavailable) changes nothing: an add's write is refused, and a remove is `retry_after`.
- Limits: emoji uploads count against the user's and the server's daily uploads and the stored-bytes cap (section 4.3, Limits). The catalog holds at most `maxEmoji` (500) keys; a new key past it is `denied`, while an existing key may be replaced.
- Reactions: an entry that looks like a key (`:name:`, a name of `[A-Za-z0-9_+-]`) must be in the catalog or already in the user's current set on that message, else the request is `invalid_params` ([EXTENSIONS.md, Reactions](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#reactions)). So a removed key does not stop its users changing their other reactions, but nobody takes it up again. Emoji sequences, and keys already in the set, never read the catalog. A removed key's earlier reactions stay.

### Framing, ordering, and errors

- Frames are the protocol's envelope ([PROTOCOL.md §1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#1-transport--framing)): JSON-RPC 2.0 shapes without `jsonrpc`, which, like any unknown key, is ignored and never sent. One text message contains exactly one object, not a batch array. Reject binary application messages.
- IDs on the wire are strings. Errors not tied to a request (parse errors, invalid envelopes whose `id` cannot be determined) omit `id`.
- Unknown request methods receive `unsupported`; unknown notifications are ignored. Valid notifications never receive result or error replies.
- A request method (the client request columns of [PROTOCOL.md §1.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#11-envelope-and-replies): `auth`, `me`, `message`, `command`, `history`, `room_list`, `room_join`, `room_leave`, `room_set`, `reactions`, `status`, `push_register`, `push_unregister`) sent without an `id` is ignored, as §1.1 allows: it changes nothing, gets no reply, and is not a policy violation, though it is charged as a frame.
- `ping` and `activity` are notification methods. An `id` on either is ignored and the frame is handled as the notification, never answered with a result or an error, even when its params or `id` are invalid or the server-wide frame limit drops it; such faults still count as policy violations. A `ping` with an `id` still gets its `pong`. A client's `status` is a request; the server's is a notification.
- Ignore unknown envelope fields. Unknown top-level message and room fields are dropped; extension data travels in `ext`. With capability `ext` ([PROTOCOL.md §4.12](https://github.com/shazow/apron/blob/main/PROTOCOL.md#412-ext)) the server keeps the `ext` clients write on users, messages, and rooms, and writes (`me`, a message save, a `room_set` edit) merge it one level deep: each key the write carries replaces the stored value whole, a key whose value is `""`, `[]` or `{}` is removed, keys left out stay, `null` is an ordinary value, and `"ext": {}` changes nothing. Size limits (a user's 512 bytes, the 8 KiB snapshot, a room's 2 KiB of client fields) apply to the merged result. A `"__proto__"` key is ordinary data. Server fields are read-only: a client-supplied `from`, `log_id`, or a room's delivery fields are ignored. Request `id`s are strings only; any other `id` is `invalid_request`.
- Process frames in arrival order per socket, including auth and later pipelined writes. External awaits and WebAuthn verification must not allow overtaking. Bound pending work instead of accumulating unlimited promises.
- Coordinate mutation commit and broadcast scheduling globally within this DO. No live room log ID may be sent after a newer ID on the same connection.
- Notifications a request causes on the requesting connection come before its result ([PROTOCOL.md §1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#1-transport--framing)): the sender's `message` and `reactions` broadcasts, the `room_update` of `room_join`, `room_leave` and `room_set` (with its `memberships`), and a command's `~private` reply. A sign-in is the exception ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication)): every notification it causes on its connection comes after the `auth` result. A sign-in that logs joins (an account's creation) sends them to the rooms' other members at once and holds them, with anything else for the signing-in connection, in memory (at most 256 frames, else the connection is closed to recover) until the result or error is sent. The status and mute snapshot (section 4.4) also follows the result.
- Commit durable state before a success becomes externally observable. Use documented storage/output-gate behavior; do not disable it. A failed send to one socket must not roll back an accepted mutation or skip all remaining recipients.
- On an ambiguous post-commit failure, preserve the recorded result and force affected recovery/reconnection rather than continuing a socket with an unexplained gap. Persistent exactly-once mutation effects within the deduplication window do not imply exactly-once network delivery.

For oversized frames, reject before parsing. If an ID cannot be safely obtained, close with 1009 rather than parsing an arbitrarily large payload just to return an error. Close binary input with 1003 and persistent policy violations with 1008. Use HTTP 429/503 before upgrade where applicable, with an appropriate Retry-After. A `GET` of `/` or `/ws` with `?apron_connection_status=1` and no `Upgrade` answers what the upgrade would have, since browsers hide a failed handshake's response: JSON `{error}` with the status (403, 429 or 503) and `Retry-After`, or `{available: true}`, without opening a socket. Its answers carry `Apron-Connection-Status: 1`, exposed through CORS with `Retry-After`, so a client ignores a reply without it ([limits](docs/limits.md#connecting-http-before-the-upgrade)). Do not turn capacity limits into fabricated malformed-request errors. `denied` is not counted as a policy violation; `invalid_params` and `too_large` are, except where noted.

### Messages, edits, rooms, and reactions

- Every record (room record, message snapshot, reaction set, membership) receives the next `log_id = max(now_ms, last_log_id + 1)` from one server-wide sequence, checked below `2^53`; use integer columns and decimal strings on the wire. A new message's `message_id` equals its creation `log_id`, so it is unique across rooms. Room IDs of threads are their creation `log_id`.
- Maintain `last_log_id` even after the entire log has expired. Clock rollback must not reuse IDs.
- Store each accepted record as a complete authoritative snapshot. Message notifications and history `messages` are the same flat object: `message_id`, `log_id`, `room_id`, `from`, `body`, optional `reply_to` (bare `{message_id}`), `deleted`, and `ext`. `body.format` defaults to `plain`. Deliver to every authenticated connection whose user has joined a room the record belongs to, including the sender's; a record is sent once per connection even when it belongs to two rooms. A thread's records go to the thread's members only; its parent's members receive only its room record, as `room_update` `updated`, when it is created or saved. Every room is visible to every client, so anyone may page any room's history, and posting does not require joining: a poster who has not joined gets only the result.
- Only the original author may replace/delete/restore their retained message, and move it, except that a registered user with the role `admin`, `mod` or `threader` may move anyone's: a save of another user's message by such a user is accepted only when it changes the message's room and nothing else (its `body`, `reply_to`, `deleted` and `ext` come out as they were, which a client resubmitting the stored client fields with a new `room_id` does), else `denied`. The moved snapshot stays the author's (`from`). The role is read from the identity row in the commit; `you` says whether the user may, with `move_any` (Extension `ext:permissions`). Preserve immutable author/ID fields. A save replaces every client field (`room_id`, `body`, `reply_to`, `deleted`) except `ext`, which merges (above); the rest is not a patch/merge. Tombstones omit `body` and `ext`, whatever the save sent, so a restored message starts with no `ext`. A request without `room_id` (a new message or a save) is in the default room, `general`.
- `reply_to` names an existing, retained message other than the message itself, in any room; otherwise `invalid_params`. A save that resubmits its current `reply_to` unchanged is accepted even after the target expires, so old replies stay editable.
- A save with a different `room_id` moves the message: the destination must exist, and the move snapshot belongs to both rooms' logs and history and carries `prev_room_id`, the source room, whose log holds its earlier snapshots. When the message has retained reactions, the same atomic commit logs one reaction record in the destination carrying every non-empty set. A move costs one post plus one more for each 8 sets it re-logs (`MOVE_REACTION_SETS_PER_POST`), charged to the mover's, their IP's and the server's posting limits in the same commit; past any of them it is `retry_after` and changes nothing.
- Guest authors own messages under their assigned guest identity; passkey authentication does not automatically transfer ownership of earlier guest messages.
- Rooms (cap `rooms`):
  - Anyone may create a thread; only a registered user with the role `admin` or `mod` (read from the identity row in the commit) may create a top-level room. `room_set` without `room_id` names an existing top-level `parent_room_id` for a thread, or leaves it out for a top-level room; a top-level room from anyone else, or a nested thread, is `denied`, an unknown parent `invalid_params`.
  - Created top-level rooms are permanent, as `general` is: they do not expire with their log nor go when emptied. At most 16 are created (`room_limit`), and they count against the thread ceiling (`thread_limit`).
  - Creating a room joins its creator: the creator's connections get one `room_update` with `joined` (the creator as its only member), the creator's logged membership in `memberships` for a registered creator, and `users`; a thread's parent's other members get `updated`; all before the `{room_id}` result.
  - Any participant may save a thread's client fields (`title`, `description`, `ext`), an admin or mod a created top-level room's, and an admin `general`'s (a blank title there falls back to `General`). A save replaces all client fields except `ext`, which merges, and `parent_room_id` and `private`, which are fixed at creation (a submitted value is ignored). It goes as `room_update` `updated` to the members of the room and of its parent, and to the saver.
  - The server supplies the title `Thread` when none is given (`Room` for a top-level room). `description` is a string, CommonMark by convention; an empty or blank one is none. Every room creation and save is a logged record in the room's own log.
- Private rooms ([PROTOCOL.md §4.2.4](https://github.com/shazow/apron/blob/main/PROTOCOL.md#424-creating-and-editing)): a registered user's `room_set` with `private: true` and no `room_id` creates a top-level private room and joins its creator (a guest's is `denied`, and so is one with `parent_room_id`). `private` must be a boolean (else `invalid_params`). Its `room_id` is `private_<log id>` (PRIVATE_ROOM_PREFIX), opaque to clients, which go by `private: true` on every record of a private room and no other; the prefix keeps private rooms in one key range that the public scans (listing, cleanup, top-level and creator counts) never read. A private room has no title or description unless given one. Only its members see it: to anyone else, every request that names it or one of its messages is answered exactly as for one that does not exist (`invalid_params`), typing in it is dropped, and no listing holds it. Nobody joins a private room by themselves: its members (registered, not bots) add registered users with `room_join` and a `user_id`, whatever `addmember` says. Its creator may remove members as a thread's creator may; admins and bot owners keep their rights but must see the room to name it. A move into or out of a private room, or a `reply_to` naming one of its messages from elsewhere, is `denied`. Pushes from it reach only its members (section 4.4). It is removed, freeing its slot, when its last member leaves or its whole log expires, as a thread is.
- Membership ([PROTOCOL.md §4.2.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#422-membership)): a new guest or registered identity has joined `general`. `room_join` and `room_leave` take a known `room_id` (else `invalid_params`) and return `{}` after the notifications they cause. Joining a joined room logs nothing and re-sends `room_update` `joined` to that connection; leaving a room not joined changes nothing. What is logged is in Memberships, below.
- Both also take a `user_id` (a string, else `invalid_params`; one's own is an ordinary join or leave) to add or remove someone else. An admin may for anyone, and a registered user (not a bot) for their own bot, `bot_<user_id>`. While `addmember` is on (the default; `/toggle addmember`), any registered user but a bot may also add anyone (`add_members` in `ext.permissions`). A thread's creator, when a registered user (not a bot), may remove anyone from it, whatever the toggle; the creator is `creator_id` in the room row's `fields_json`, never in the room record, moved by `/rename` and cleared by `/purge` (`general` and guests' rooms have none). Anyone else is `denied`. `room_join` adds registered users only: a guest or unknown `user_id` is `invalid_params`. The join is stored and logged like the user's own, charged to the adder's posting limits: the room's other members get it in `room_update` `memberships`, and the added user's connections get one `room_update` with `joined` and that `memberships`. `room_leave` with a `user_id` is `/kick` (section 5, Admins) without its notice, guests included; removing someone not in the room changes nothing, and a `user_id` no identity or connection has is `invalid_params`.
- At most 100 thread rooms, each with at most 2 KiB of serialized client fields, and at most `threadsPerUser` (25) live threads created by one registered user (one scan of the capped rooms table by `creator_id`; a thread whose log has expired stops counting). Guests' threads count only against the ceiling; creation past it is `denied`. All room creation and saves consume posting and resource budgets. No implicit room creation.
- A thread is removed, releasing its slot, when its entire log (creation record included) expires (its members get `room_update` `left` at cleanup), or when a leave (`room_leave`, a removal with `user_id`, or `/kick`) leaves nobody in it: no connection, a guest's included, has it among its rooms and no registered member is stored. Nobody is then told but the leaver, who gets `left`. Its records stay until they expire, but a lookup of a message whose room is gone finds nothing (`invalid_params`, as for an expired message), so it cannot be edited, moved, reacted to, replied to or pushed. A removal the budget refuses leaves the thread to expire with its log; the leave stands either way.
- Private rooms count apart from the threads: at most `privateRoomLimit` (100; at most 200) exist at once, one registered user may have started at most `privateRoomsPerUser` (5) live ones (by `creator_id`), and may be in at most `privateMembershipsPerUser` (20; at most 50) at once; past any of them, creating one or being added to one is `denied`. The per-user ceiling bounds every per-user read with the thread ceiling, and the server-wide one bounds scans of the private range. `server.ext.settings.private_rooms` advertises `privateMembershipsPerUser`. With `privateRoomLimit` 0 there are no private rooms, and a creation with `private: true` is `unsupported`.
- Reactions (cap `reactions`): a request sets the caller's complete emoji set on one retained message; `[]` clears it and duplicates collapse ([PROTOCOL.md §4.7](https://github.com/shazow/apron/blob/main/PROTOCOL.md#47-reactions)). An entry is a custom emoji key, checked as in Extension `ext:emoji`, or else an emoji sequence, never checked against the catalog. An emoji sequence is stored fully qualified where the runtime's Unicode data (`\p{RGI_Emoji}`) knows it: each part between zero-width joiners takes U+FE0F after its first code point where that makes it an RGI emoji (❤ is stored as ❤️, `src/emoji.ts`); one it does not know is kept as written. Entries that differ only in U+FE0F are the same entry. Entries are non-empty strings of at most 64 UTF-8 bytes (else `too_large`) without control characters, at most 8 distinct per user per message, and at most 32 reacting users per message (calibrated ceilings 16 and 64); past either count it is `denied`. A set that equals the current one is accepted without a new record. Non-empty sets on a tombstone are `denied`; clearing is allowed. Each change is a logged record in the message's current room. Reactions are mutations: they share the posting quotas and request deduplication below.
- A new message with empty text and no embeds is neither logged, charged, nor delivered; its result is `{}` (an unknown room is still `invalid_params`). A save that would leave a message empty is `invalid_params` by local policy; delete it instead. Accept the `plain` and `markdown` (CommonMark) formats. `body.mentions`, when present, is an array of `user_id` strings (duplicates collapse) stored as sent; one that cannot be a `user_id` (empty, or with whitespace or a control character, [PROTOCOL.md §2.4](https://github.com/shazow/apron/blob/main/PROTOCOL.md#24-opaque-ids)) is `invalid_params`. The server never reads mentions out of `text`. Limit embeds to four within all byte budgets (more is `denied`, a count limit; a mentioned `user_id` past 256 bytes is `too_large`); store accepted URLs/content without backend fetching or rendering. Unknown embed kinds remain opaque. A client-built `og` keeps only its `title`, `description`, and `site_name` as bounded single-line text; media are kept only with an `https:` URL, without credentials or a port, on a host `OG_MEDIA_HOSTS` allows (by default a few big platforms' image CDNs, [configuration](docs/configuration.md#link-preview-media)), and other media and properties are dropped (§4.8.1 lets the server keep, replace, or drop it). Client sanitization/sandboxing remains mandatory under the base protocol.
- `me` merges into the profile ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)): a given field replaces its value, an omitted one is unchanged, and an empty one removes it. `roles` and `ext.permissions` are ignored. A registered user's display name change is a bounded, rate-limited identity operation; `name: ""` removes it and is announced as `name: ""`; a guest's `name` is `denied`. `ext` must be an object (else `invalid_params`) and merges into the user's kept one, at most 512 bytes after the merge (`MAX_USER_EXT_BYTES`; past it `too_large`, checked before anything changes). Registered users, bots included, keep it in their identity row (`ext_json`), so a `name` or `ext` write is one row update, deduplicated and charged as a post; a guest's `ext` with any key is `denied`. Avatars come only from `/avatar` uploads (section 4.3): `avatar: ""` removes a registered user's avatar, and other values are type-checked and ignored. No avatar downloads from other servers or automatic link previews.
- User objects follow [PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity). Current objects (`you` in the `auth` and `me` results, `users` in `room_list` and `room_update` `joined`) are complete: `user_id`, `name`, `avatar` where the user has one, `roles` for a registered user (`[]` included), `ext` where the user has one, and `status` with capability `status`; a user's own `you` also carries `ext.permissions`. Recorded objects (`from`, a membership's `user`) carry none of `avatar`, `roles` or `status`. A user's `ext` and `roles` are read with the identity row wherever that is read anyway.
- `user` notifications carry identity changes only: `user_id` and at least the fields that changed, a cleared one as its empty value (`name: ""`, `avatar: ""`, `roles: []`), and of `ext` only the keys that changed (a cleared key as `""`). A profile change (`me` `name`, an avatar change, `/admin` and `/role`, `/invite-bot` renaming a bot) sends `you` to the user's other connections and `new` to the connections of users who share a room with them; a new `user_id` (`/rename`, a guest's new account) carries every field. Status changes are `{user_id, status}` alone (section 4.4, User status). `old` marks only the same account under a new `user_id` (§3.3): a guest whose connection creates an account (a passkey registration or a sign-up invite) sends `new` with `old` to those who shared a room with either. A guest's connection signing in to an existing account sends no `old` link: the guest departs as a disconnecting guest does, and the account shows only through its status. Joins and leaves are never `user` notifications. History pages carry no `users`.
- `command` (cap `command`, [PROTOCOL.md §4.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#41-command)): `/help` answers `{}` and a `~private` notice listing the commands the sender may run, alphabetically, the admins' marked "(admin-only)", delivered to that connection only, never logged, with no `message_id` or `log_id`. `/invite-bot` (section 5, Bots), `/invite-device` (section 5, Devices), `/passkeys` (section 5, WebAuthn) and `/avatar` (section 4.3, with uploads) are for registered users other than bots; `/embed-terminal` and `/embed-append` (section 4.5, with live text) for anyone who may post; `/emoji` (Extension `ext:emoji`) for those with the role `admin`, `mod` or `friend`; and `/admin`, `/role`, `/kick`, `/rename`, `/invite-token`, `/invite-code`, `/invite-purge`, `/purge`, `/server`, `/toggle` and `/status` for admins (section 5, Admins). Anyone else gets `denied`. Other commands are `invalid_params` without counting as policy violations, as are an admin command's usage and `user_id` errors; what an admin command may not do, such as `/kick` or `/purge` of oneself, is `denied`. `/help` needs no SQL beyond a cached room check and, once per wake, the uploads toggle.
- Message snapshots carry `prev_log_id` when an earlier record for the same key is still stored, and a move's snapshot also `prev_room_id`. Reaction sets and memberships carry neither ([PROTOCOL.md §4.3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#431-a-rooms-log)); room records carry no `prev_log_id` (it is optional). The links are added after the snapshot size check. Deleted messages are not redacted.
- `room_list` (cap `rooms`, [PROTOCOL.md §4.2.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#421-listing)) returns room records with delivery fields in `joined` (the user's rooms, never truncated) and `not_joined` (visible rooms not joined: top-level ones, or with `parent_room_id` that room's threads), each most recently active first. `filter` (`joined`, `not_joined`, or `all`, the default; anything else is `invalid_params`) leaves out the other array, and an array it asks for is present even when empty. It takes `parent_room_id` and `room_id` (one room, in the array its membership selects; unknown is `invalid_params`). With `members: true`, each listed room carries `members`, bare `{user_id}` objects in `user_id` order, and `member_count` when those leave some out (Memberships), and the result `users`, each member's current object once, in `user_id` order, present even when empty; without it, neither. `latest_log_id` is validated and ignored (Memberships). It writes nothing. A listing that would pass the 256 KiB response cap leaves out `members`, `member_count`, and `users`. Listing unjoined top-level rooms while joined to every one is answered from memory and not throttled.
- `room_update` `joined` carries the room's record with its `members` (and `member_count`) and the frame's `users`, as a `members: true` listing does.

### Memberships

The protocol logs every membership change, and lets a server keep some out of the log, such as ephemeral guests' ([PROTOCOL.md §4.2.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#422-membership)). The demo logs what is durable already and keeps the rest out:

- A registered user's membership is stored (the `memberships` table) and each change is a logged `membership` record in the room's log: `{log_id, room_id, members: [{user: {user_id, name}, joined}]}`, one entry, with the user as a recorded object. Logged changes are `room_join`, `room_leave`, the creator's join when a registered user creates a thread, and each starting room of a new registration (the guest's rooms it replaces, or `general`), which reaches the registering connection after its `auth` result (Framing, ordering, and errors). A record advances the room's `latest_log_id`, is delivered in `room_update` `memberships` ([PROTOCOL.md §4.2.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#423-updates); there is no `membership` notification) to the room's members before and after the change, and is returned in `history`'s `memberships` array. The joining user's connections get it in the same `room_update` as their `joined`, and the leaving user's in the same one as their `left`; the room's other members get `memberships` alone, one frame each. The joins and leaves count as posts; an unchanged join or leave writes nothing.
- A guest's memberships live in its connection attachment, like the guest identity, and are not logged or stored. Where guests may post, a guest's join or leave that changes something still counts as a post against the guest's (`anonymous:<ip>`), the IP's and the server's posting limits. Clients learn guest members from `room_list` and `room_update`.
- Because guest joins and leaves are not in the log, `room_list` ignores `latest_log_id` and never sends `left`: its result is a full listing, which the protocol allows.
- `members` lists every connected member, guests included, and the registered members stored with the room, at most `room_list_members` (200; Free: 100) per room, by `user_id` besides those connected. This deviates from [PROTOCOL.md §4.2.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#421-listing), which lists the most recently active members: ordering by activity would cost a written row per post and an index. Connected members are always listed. A user whose status hides being connected (`invisible`, or `""`) is not listed for being connected (section 4.4, User status). A room with more members than listed carries `member_count`: its stored registered members (a count kept on the room row, updated in the same row update as the room's head) plus its connected guests. Listings are reused for up to a minute (section 4.4, User status). Each listed member costs a bounded number of indexed reads ([cost report](docs/cost-report.md#memberships-and-identities)).
- Retention discards the log prefix older than the retention window (section 9), membership records included. The demo does not append the full-member record the protocol asks for before discarding a prefix that holds memberships, since guest memberships are out of the log anyway; clients start member lists from `room_list` and `room_update`. This is a deviation.
- A thread room removed at cleanup leaves the `rooms` table at once, and its members get `room_update` `left`. Its stored memberships are purged in later bounded cleanup batches from a list of removed rooms in `_meta` (at most 100; no further room is removed while it is full); until then membership reads join `rooms`, so they never see them.

### 4.2 Server-wide minute, activity, and per-type throttles

The whole server processes at most `globalFramesPerMinute` (600; Free: 300) frames in a rolling minute, counted in memory after the per-connection gates and parsing but before any SQL. Over it, a request gets `retry_after` with the seconds until the oldest counted frame leaves the window, and a notification or malformed frame is dropped; the socket stays open and nothing is charged. It is sized for a spike from 50 connected users, 10 of them active (Paid: 20), at about 20 frames a minute per active user, and is at least one IP's frame minute. The window is lost on hibernation. It shapes spikes; the daily frame and SQL budgets still bound the day.

`activity` is on by default with the Workers Paid budgets and off with the Free ones; `ACTIVITY` overrides either. When off it is not advertised, and `activity` is ignored. When on:

- Typing (`typing`, seconds, capped at 30) in a known room (`general` without `room_id`) is relayed to the room's other members' connections as `{room_id, from, typing}` and never stored.
- A registered user's `read_message_id` (a decimal message ID; anything else is `invalid_params`, like a bad `typing`) in a room they see is relayed as `{room_id, from, read_message_id}` to their own other connections, and in a private room of at most `MAX_READ_RECEIPT_MEMBERS` (10) registered members to its other members' connections too, unless the reader chose `invisible` (read receipts, `read_receipts` `"private"`; in other rooms there are none; the room's `member_count` is read, one row, only when another member is connected to it), within 10 relays a minute apart from typing's (past them it is kept, not relayed). One not past the one the connection holds unwritten is dropped, not relayed. For a room they joined it is also kept on the connection's attachment and written to `read_cursors` at most once a minute per connection (`READ_CURSOR_FLUSH_MS`: by its next cursor, the next alarm, or when it closes), and at once when the connection holds more than `MAX_ATTACHED_ROOMS` or signs in as someone else, only while the user is a member and only forward; one held when the instance is lost leaves the last one written. After a `room_list` whose result has `joined`, the server sends the user, as `activity` from them, their cursor for each listed joined room that has one (the kept one, or a further unwritten one), then, for each listed private room of at most 10 members, its other members' cursors as `activity` from each with `from` holding only their `user_id` (the kept one, or a further unwritten one held for a room its connection is still in), leaving out members who chose `invisible`: an invisible member's cursor is kept for their own devices, and shows to the others once they are visible again. A cursor is deleted with its membership (so with a leave, an expired room and `/purge`) and moves with `/rename`. A guest's is dropped.
- Other fields are ignored; neither typing nor a read cursor changes `idle` (section 4.4). An unknown room drops the update; room existence comes from an in-memory cache with one bounded lookup per unknown ID.

Some message types have their own per-user rate, counted across the user's connections in a rolling 60-second window whose events live in connection attachments (so they survive hibernation and need no SQL):

| Type | Default per user per minute | Over the limit |
| --- | ---: | --- |
| `activity` (relayed typing) | 10 | Dropped. The sender's connection gets one `~private` notice per window ([PROTOCOL.md Appendix A.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#a1-system-identities-and-scoped-notices)) saying typing is limited |
| `room_list` | 6 | `retry_after` with the seconds until the oldest counted listing leaves the window. The first `filter: "joined"` listing after each authentication is not counted: it is how a client learns its rooms |
| `push_register` (with push) | 10 (`registersPerUserMinute`) | `retry_after`, as for `room_list`; refused registrations count too. Counted on the object per user, so reconnecting does not reset it |
| `status` `mute` and `me` `status` changes (with push) | 6 (`mutesPerUserMinute`), the two together | `retry_after`, and nothing in the request changes (section 4.4). Counted on the object per user |
| `status` changes to idle (with push) | 12 per connection (IDLE_CHANGES_PER_CONNECTION_MINUTE) | `retry_after`, and nothing in the request changes (section 4.4, Attendance); `idle: false` is never refused |
| User `status` announcements (with presence) | 1 per `statusCoalesceSeconds` (60) for changes the connections cause; a `me` change at once | Not dropped: the latest change goes out when the minute is up (section 4.4, User status) |
| `seen` writes (with presence) | 1 per `SEEN_WRITE_GRANULARITY_MS` (10 minutes) per registered user | Not refused: the stored `seen` is carried again, unwritten (section 4.4, User status) |

The `~private` notice goes to the throttled connection only, is never logged, and needs no SQL. Posting quotas continue to cover every logged mutation (`message`, `room_set`, `reactions`, `me`) and room joins and leaves.

Every frame is charged to the IP and daily frame budgets before any other work (section 6). Each connection reserves frames in blocks of `frameLease` (10) and spends them from its attachment (section 7, durable block reservation). A block counts against the IP's frame minute and the daily frame budget when reserved, lives only in that connection's attachment so it is never granted twice, and is burned when the connection closes or the UTC day ends. Operations that do SQL work still reserve their own cost. The frame is parsed, bounded CPU work with no storage, before it is charged.

### 4.1 Internal names

Internal names such as the `anonymous` quota tier and its `anonymousPosts*` configuration keys refer to guests; wire-visible names use `guest` (such as `guest_<n>` user IDs and the `guest` auth scheme).


### 4.3 Uploads and avatars

With the Workers Paid budgets (`uploads` in `src/plans/paid.ts`) and a deployment that sets `MEDIA_ORIGIN`, `PUBLIC_ORIGIN`, the `UPLOAD_SIGNING_KEY` secret and the `MEDIA` R2 binding, the server advertises `embed:upload`, and `ext:media` with the types and sizes below (section 4, Extension `ext:media`), and follows [PROTOCOL.md §4.8](https://github.com/shazow/apron/blob/main/PROTOCOL.md#48-embeds-and-avatars):

- Embed identity (§4.8.2): every embed gets an `embed_id`. A save keeps an embed by sending it back with its `embed_id`; one left out is removed; an unknown one is `invalid_params`. An upload keeps its `url` and `og` from the server's record and takes only a new `title` (single line, 256 code points).
- Writes (§4.8.3): a new `{"kind": "upload"}` embed from a registered user (guests cannot upload) is broadcast pending, and the sender's result lists `embeds: [{embed_id, kind, write_url}]` in request order. `write_url` is `PUBLIC_ORIGIN/w/<token>`: an HMAC-signed grant naming the R2 key, the largest body, and a 10-minute expiry, so a retry of the same request gets the same URL.
  - The client `PUT`s the file there with `Content-Length` (any origin; CORS preflight allowed). The entry Worker checks the signature before reading the body, and the Durable Object claims the upload so one request writes it. The claim counts against the server's daily uploads; past them the write is `429` with `Retry-After` until the reset, and the upload stays pending within its window.
  - A body over the grant's size is `413`. Only the types `ext:media` lists are kept, typed from their bytes, never from the sender (audio by its container only); anything else is `415`, and so is a declared `Content-Type` (without parameters) that is none of them, before the body is read.
  - The object is stored at `f/<128-bit random id>`, then the message gets a server snapshot with the embed completed: `url` on `MEDIA_ORIGIN` and `og.image` with `url`, `type`, and `width`/`height` when the header gives them, or for audio `og.audio` with `url` and `type`. A failed write, or none within the window plus a minute's grace, publishes the message without the embed; a message left with neither text nor embeds becomes a tombstone. Removing the embed or deleting the message deletes the object.
- Avatars (§4.8.7): `/avatar` with exactly one upload embed returns its `write_url`; when the write finishes, the image (`a/<id>`; audio is `415`) becomes the sender's avatar and they get `user` `you`, and users sharing a room `new`. `avatar` is in current objects (`you`, `new`, room `members` and `users`), never in `from`. `me` with `avatar: ""` removes it; other values are declined. A new avatar replaces and deletes the old.
- The server's avatar (§3.1, §4.8.7): an admin's `/server avatar` with exactly one upload embed returns its `write_url`; when the write finishes, the image (`e/<id>`, an image of at most `maxAvatarBytes`; audio is `415`) becomes the server's `avatar`, and every connection gets a new `server` frame. It is kept like a custom emoji's image (`Cache-Control: public, max-age=31536000, immutable`, no lifecycle rule, never expiring) and owned by `~server`, so `/purge` and `/rename` of that admin leave it. A new one replaces and deletes the old; `/server avatar` alone clears it and deletes its image.
- Serving: the bucket's custom domain (`MEDIA_ORIGIN`) serves uploads, not the Worker. Where `MEDIA_ORIGIN` equals `PUBLIC_ORIGIN`, as for local development, the Worker serves `GET` and `HEAD` of upload keys (`f/<id>`, `a/<id>`, `e/<id>`, `e/c/<sha256>.json`) from the bucket itself, with their stored type and cache headers, `Access-Control-Allow-Origin: *`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'`.
- Custom emoji images (`e/<id>`) are section 4, Extension `ext:emoji`.
- Limits: 5 MB per attached file, image or audio, and 256 KB per avatar or custom emoji; images, audio and custom emoji share one budget: 500 uploads a UTC day server-wide, counted as writes are claimed, so uploads started and never written close nothing for others, and 20 per user, counted as they start (avatars and custom emoji included); live upload bytes, pending writes counted at their largest, at most 5 GB, custom emoji and the server's avatar included for as long as they stay; at most 500 custom emoji (`maxEmoji`). Past a daily count, `retry_after` until the reset; past the byte cap, `retry_after` of an hour.
- Retention: attached files live 7 days and avatars 30, matching the bucket's lifecycle rules (custom emoji and the server's avatar, `e/`, have none), and still count as stored for a day after, since R2 deletes them asynchronously. An avatar whose owner signs in during its last week is written again, restarting its 30 days. Messages are kept as long as their images (7 days on Workers Paid); cleanup removes a message up to a day after its image expires, so R2 can delete an image during its message's last day.
- Cost: the daily counts and byte cap keep uploads within R2's free tier; the budget guard counts R2 operations against their daily and monthly shares and blocks the media host with the server's ([configuration](docs/configuration.md#uploads)).

### 4.4 Push

Where the plan has a push policy (`push` in `src/plans/`, both plans) and the deployment sets `VAPID_PUBLIC_KEY`, `VAPID_SUBJECT` and the `VAPID_PRIVATE_KEY` secret ([configuration](docs/configuration.md#push)), the `server` frame carries `push: {"webpush": {"key": "<VAPID public key>"}, "wake": ["mentions", "replies", "private", "joined"]}`, the wake scopes this server implements for the connection (§4.9.4), and follows [PROTOCOL.md §4.9](https://github.com/shazow/apron/blob/main/PROTOCOL.md#49-push) for the `webpush` kind only. `joined` is listed only on a connection signed in as a registered user with the role `admin` or `mod` (`JOINED_WAKE_ROLES`), not an owner's bot; a sign-in or role change that changes this sends the connection a new `server` frame right after the `auth` result or `user` `you`. Without push configured there is no `push`, and `push_register` and `push_unregister` get the unsupported-method path.

- Registration: `push_register` with `{"kind": "webpush", "url": <endpoint>, "keys": {"p256dh": …, "auth": …}, "push_id": …}`, the browser's `PushSubscription.toJSON()` with `kind` and the optional `push_id` added (`expirationTime` is ignored). Registered users only, bots included; a guest's is `denied`. Any other `kind` (`relay` included) is `invalid_params`. At most `registersPerUserMinute` (10) a user (section 4.2). The result is `{}`. Checks:
  - `push_id` is 1 to 64 letters, digits, `_` or `-` (else `invalid_params`), stored and copied unchanged into every push to the registration.
  - `wake` is an array of strings (else `invalid_params`), at most 16 (else `denied`) of at most 64 characters each (else `too_large`). Scopes this server does not implement (`ext:` ones) are ignored, and so is `joined` from a user who is not a registered `admin` or `mod` (read from their identity row as they register), so such an array, or `[]`, keeps the registration but wakes it for nothing; without `wake` it wakes for `mentions` and `replies`. Moderators' registrations that keep `joined` are also in a partial index (`push_subscriptions_joined_idx`).
  - `url` is at most 512 bytes (else `too_large`) and must be `https`, without credentials or a port, naming a public host without a trailing dot: IP literals in any spelling, single-label hosts, and `localhost`, `.local`, `.internal`, `.home.arpa` and similar internal suffixes are `invalid_params`. Names are not resolved; the platform's outbound fetch does not reach private networks. The host must also be one `PUSH_HOSTS` allows (by default the browsers' push services, [configuration](docs/configuration.md#push)); another is `invalid_params` "push service not allowed here". The endpoint is stored as `new URL(url).href`, and `push_unregister` matches it the same way.
  - `p256dh` must be an uncompressed P-256 point on the curve and `auth` 16 bytes, both base64url.
- Registrations belong to a user, identified by `user_id` and `url`, so two users may register the same endpoint. Registering a held `url` again replaces its keys, `push_id` (absent removes it) and scopes; an unchanged one registered again within a day writes nothing. A user keeps at most `subscriptionsPerUser` (5); another replaces the least recently registered. One not registered again for `pushExpiryDays` (7) is skipped by wakes and deleted by cleanup. `push_unregister` `{url}` removes only the sender's own registration and answers `{}` for an unknown one (§4.9), a `url` over 512 bytes included, without SQL. `/rename` moves registrations and `/purge` deletes them; `/passkeys remove` and a replaced or removed device token delete all the user's registrations, and a new bot token deletes the bot's.
- Status: with push, the server advertises capability `status` ([PROTOCOL.md §4.5](https://github.com/shazow/apron/blob/main/PROTOCOL.md#45-status)), presence on or off: the user `status` set with `me` (Chosen status), and the `status` request, with `idle` for the sending connection and the user's `mute`. With presence on, the `server` frame also carries `status: ["dnd", "invisible"]`; with it off the list is left out, though `me` still takes and keeps both, so a choice holds across `/toggle presence`. The frame is sent once per connection, so one opened before a toggle keeps the list it got.
  - The server replies `{}` once it has applied the request; on an error nothing in it changes (§4.5): every check comes before any change, and the mute is applied before `idle`. Unknown fields are ignored. `room_id` scopes only `mute`.
  - `invalid_params` (a policy violation): an `idle` that is not `false` or a whole number of seconds (`true` included), a `mute` that is not `true`, `false` or a positive integer number of seconds (`0` included), a `room_id` without `mute` or that is not a string of 1 to 64 characters, or a mute of a room that does not exist. `retry_after`: past `mutesPerUserMinute`, or the idle limit (Attendance). `denied`: a room mute past the cap, any guest's `mute`, and any `status` before sign-in (§3.2).
  - Without push, `status` is `unsupported`, and `me` ignores `status`. The server never sends `idle`.
- Attendance: `idle` is per connection, kept in the connection attachment. A connection starts attended, with nothing kept from earlier connections (§4.5); a sign-in on it keeps its own `idle`. A whole number of seconds (`idle: 300`) marks it unattended since that long ago ([PROTOCOL.md §4.5.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#453-the-status-request)); the connection keeps `idleAt` (now less those seconds, at most 600), which held wakes go by (Wake). Only `idle: false` or a close ends it; messages, history, `activity` and other requests do not. The server never infers idleness (§4.5): a connection that never sends `idle` stays attended while it is open and not stale, for wakes and for the status others see. A connection may go idle at most 12 times a minute (IDLE_CHANGES_PER_CONNECTION_MINUTE, counted in memory); past that the request is `retry_after` and nothing in it changes. `idle: false` is never refused. A repeat of the current value is answered `{}` and not counted. Each change re-derives the user's status from attachments, with no SQL.
- Chosen status: `me` with `status` (a string, else `invalid_params`) sets the status the user chooses (§3.3, §4.5): `online` (the default), `""` (none), `dnd` or `invisible`; any other string is taken as `""`. Guests may choose too. Every `you` a connection gets carries the choice, presence on or off, and each change is sent to the user's other connections as `user` `{"you": {"user_id", "status"}}`. A registered user's is stored in their `user_status` row (with the unscoped mute; the row goes once both are back to the defaults); a guest's lives on its connection. It is read once at sign-in with the mutes and kept on all the user's connections. Changes count against `mutesPerUserMinute` with mutes, once stored; past it, `me` with a changed `status` is `retry_after` before anything else in the request changes. `me` checks everything that can make it invalid before the status applies, so an invalid `me` changes nothing and counts nothing. `dnd` silences the user's pushes like the unscoped mute (Wake). If the status and mutes cannot be read at sign-in, the sign-in fails (`internal_error`, "sign in again") before the connection becomes the user's and, for a passkey, before its session is issued. `/rename` moves the `user_status` row and `/purge` deletes it.
- Mute: `mute` is the user's, private (others never see it), and `true` (until changed), `false`, or a positive integer number of seconds to stay quiet (cut to a year; `0` is `invalid_params`, §4.5). Without `room_id` it silences the user's pushes everywhere; with `room_id`, in that room and its threads, mentions and replies included. The unscoped mute is stored for registered users in their `user_status` row (`mute_until_ms`, the largest safe integer for `true`), and each room's in the `room_mutes` table, keyed by user and room, at most 100 a user (MAX_ROOM_MUTES_PER_USER); both hold across connections, devices and restarts. A room mute needs the room to exist, except to clear it; past 100, a mute of another room first deletes the user's room mutes that ran out, and is `denied` if that frees none. A muted user gets no pushes and takes no wake slot. A guest's `mute` is `denied`, and with it the whole request, `idle` included.
  - Each change goes to every connection of the user, the sending one included, before its result, as a `status` notification with the resulting `mute`: the seconds left (rounded up), `true`, or `false` once it ends or is cleared, with the `room_id` of a room mute; an unchanged or refused mute sends nothing but the result or error. Only a change the store accepts counts against `mutesPerUserMinute`.
  - After every sign-in of a registered user, the connection is sent one `status` for each mute in effect, after the `auth` result and before others' statuses (User status); a scope not sent is unmuted. A sign-in is an `auth` that signs the connection in as a user it isn't already signed in as (§3.2), on every path (passkey registration and login, a session token, and the keyless tokens). An `auth` that only adds a passkey, a repeated guest `auth`, and a token `auth` on a connection already signed in (`denied`) are not sign-ins and are followed by neither the mutes nor others' statuses.
  - A mute that runs out is sent as `mute: false` to every connection of the user by the status alarm and sweep (User status): the unscoped one from the attachments with no SQL, room mutes by one range read that deletes those that ran out, so each is told once. One running out within a minute of an event is told on time, a later one at the first event after it; clients count the seconds down themselves. Expired room mutes of a user without a connection stay until the cap or their next sign-in drops them.
- User status (presence): on by default with both plans' budgets; `PRESENCE` (`true` or `false`) overrides it, and admins turn it off and on with `/toggle presence` ([configuration](docs/configuration.md#user-status-presence)). With presence on, others see each user's `status` (§4.5) in current user objects: `users` in `room_list` and `room_update` `joined`, `new` when `/rename` gives a user a new `user_id`, and `user` notifications. Every current user object in `room_list` and `room_update` carries `status`, `offline` and `""` included, presence on or off (off, it is `""`). A profile change's `new` leaves it out, and recorded objects never carry it. `you` carries the chosen status, never `offline`.

  | Chosen | Attended connection | Connected, none attended | No connection |
  | --- | --- | --- | --- |
  | `online` | `online` | `idle` | `offline` |
  | `dnd` | `dnd` | `dnd` | `offline` |
  | `invisible` | `offline` | `offline` | `offline` |
  | `""` | `""` | `""` | `""` |

  Connected users' status comes from their connection attachments, with no SQL; a member listing reads each listed registered member's chosen status with them. A push registration never shows anyone as `idle`.
  - `seen` ([PROTOCOL.md §4.5.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#452-delivery)): every object that shows a user `offline` carries `seen`, as a decimal string of epoch milliseconds, in each `user` notification that changes them to `offline` and each listing object, whoever lists them; it is left out where none is recorded (including after a schema reset). It is set only when the status others were told becomes `offline`: at once when a connected user chooses `invisible` (the time of the change), and when the last connection of a user others were told was `online`, `idle` or `dnd` closes (the time it closed, settled at the close and sent once the grace is over). An `invisible` user's connections coming and going change nothing. A registered user's is stored in their identity row (`seen_ms`, 0 for none), read at sign-in with that row and kept on all their connections; a guest's lives on its connection.
  - `seen` is written at most once in `SEEN_WRITE_GRANULARITY_MS` (10 minutes) per user: when the shown status becomes `offline` no more than 10 minutes after the stored `seen`, that one is carried again and nothing is written (decided from the connections' copy, with no read); otherwise the store writes the change's time only where the one it holds does not stand either (a conditional update), so a stale copy never writes twice. So `seen` may be up to 10 minutes earlier than the real change. This deviates from §4.5.2, which makes `seen` the time the shown status *last* became `offline`: a user who leaves at 5:00, is back and shown `online` at 5:03, and leaves at 5:04 is announced with `seen` 5:00. A departure after a longer absence always writes its own. A settling the store refuses (an exhausted budget) is logged and the connection's copy is carried instead. Costs are in the [cost report](docs/cost-report.md#user-status).
  - One departure settles one `seen`, owes one change, and tells everyone one value, even when several of the user's connections close together: only the first close handled as the last connection counts. Only a close handled after an eviction, and after the change it repeats was told, is announced again, with the stored `seen`.
  - When presence is turned back on, each user shown `offline` since carries the time it came on (`presence_on_ms` in `_meta`) unless a later `seen` is recorded. `/rename` keeps `seen` with the identity row; `/purge` deletes it.
  - Announcements: changes go as `user` `{"new": {"user_id", "status"}}` to every other user's connections that share a room with the user; the user's own connections are not told what others see. A connected user who joins a room has their status sent the same way to that room's members, after the membership.
  - After every sign-in (as defined under Mute), after the `auth` result and the mutes, the connection is sent the status of each other connected user who shares a room with it, as others were last told it. Users shown `offline` or `""` are left out, as connected member listings leave them out, so nothing tells that a user who hides it is connected. It reads attachments only, with no SQL.
  - Coalescing: changes the connections cause go out at most once per user per `statusCoalesceSeconds` (60); a change within the minute waits, and only the latest goes out (none if it is back to what was told). A change caused by a closed connection (offline, or idle when the attended connection closes while an idle one stays) waits `offlineGraceSeconds` (60) besides, so a reconnect within it shows nothing; a runtime-closed socket whose close has not arrived counts as closed, and a vanished peer from when it is found stale. A change made with `me` is announced at once. Listings show what others were last told.
  - What others were last told is kept on each of the user's connections (`pres` in the attachment), and for a user whose last connection closed, on each connection that still has to be told (`owed`, at most 32 a connection; more are sent at once), so a waiting change survives hibernation and eviction.
  - Alarm: the earliest due change or mute ending within a minute, only while a signed-in connection is open, is asked of the object's alarm (one alarm, shared with auth deadlines, uploads and cleanup), rounded up so changes due in the same window share one wake: a registered user's to `presenceAlarmSeconds` (15; Free: 60), a guest's to `guestPresenceAlarmSeconds` (60), since anyone can open a guest connection, a multiple of the first so guests add no boundaries. The object hibernates while it waits. An in-memory timer did this until 2026-10-31 and kept the object awake until it fired: 5,900 to 8,200 seconds a day (2026-10-29 to 31), 34% to 38% of its awake time. Moving the alarm earlier costs a metered alarm write (Store.scheduleAlarm); an alarm with nothing to do but status changes announces them and sets the next, skipping the usage refresh, sweeps and cleanup, which run on the alarms that have their own work. It tells whether cleanup is due from a cached time, and reads a pending upload's deadline from storage once after a wake, so neither waits for a later alarm. Rounding caps presence wakes at 5,760 a day (Free: 1,440; [cost report](docs/cost-report.md#user-status)). Each event also sweeps (at most every 30 seconds, when a change is overdue, and first after a wake) for mutes that ran out and stale peers, never closing the connection whose frame started it.
  - Turning presence off stops showing statuses to others and sending them after `auth`; the chosen status is still kept and in `you`, mutes still work, and `dnd` and mutes still silence pushes. Each connection is sent `user` `{"new": {"user_id", "status": ""}}` for each user it was told of or is owed a change for, with no SQL, and listings then carry `status: ""` for everyone. Turning it on starts from each user's status then, announcing no change, and sends each signed-in connection the statuses as after a sign-in.
  - Member listings are reused for up to `statusCoalesceSeconds`: the store keeps each room's member rows in memory and serves a listing again with no SQL and no reservation until any write to `identities`, `memberships` or `user_status`.
- Wake: only a registered user's new message wakes anyone (not an edit, move, deletion, retry, reaction, command, guest's message or transient notice, §4.9).
  - Candidates, at most 32, deduplicated with their reasons combined: the replied-to message's author (scope `replies`; one metered lookup, skipped when the message is unknown or expired), then the users `body.mentions` lists, in order (`mentions`), then, in a private room, each of its members (`private`, at most 32 from the room's member listing), and last, for any message, the moderators who kept `joined` (`joined`, most recently registered first, at most 32), so `joined` never crowds out the others. Never the sender or a guest, and only users with no connection that is both fresh (section 3, Socket lifecycle) and not idle.
  - Wait: candidates wait `delaySeconds` (30; `PUSH_DELAY_SECONDS` overrides it, `0` for none) in memory. One who sends `idle: false` or posts in the message's room meanwhile is dropped; at the end, those attended again are passed over, and the message is looked up again: one deleted, expired, or gone with its room is not pushed, and an edited one is pushed as edited, to a mentioned user only if it still mentions them and to the replied-to author only if it still replies to the same message. A dropped wake spends no wake slot, allowance or coalescing window. At most 60 seconds, held in memory: production measured it keeping the object awake about 200 seconds a day (2026-10-29 to 31), too little to move onto the alarm; at most 256 messages' wakes (MAX_PENDING_WAKES) wait at once, and one past that goes without waiting; a wake waiting when the instance is lost is not pushed.
  - Read cursors (with `activity` on) drop, as they arrive, a waiting or held wake for a message in their room at or before them (§4.9).
  - Held wakes: a candidate attended when the message comes is held instead, for every reason but `joined`, on their connections' attachments (`held`, at most 8 a connection, kept 10 minutes; no SQL). When their last attended connection goes idle, the held wakes that came after they were last attended (the latest `idleAt` of their connections) are pushed as one: the newest still current and unread, through the same wait and claim; if it wakes no one (muted, or coalesced), the next newest is tried, until one is pushed or an allowance is spent. An `idle: 0` releases none; posting in a room forgets its held wakes; a sign-in as another user forgets a connection's; each is released once.
  - Claim: each candidate in turn is passed over, taking no wake slot, when their unscoped mute is in effect or their status is `dnd` (§4.9: those go only to `badge` registrations, which this server lacks); when no live registration's scopes include a reason they qualify by; when they muted the message's room or, for a thread, its parent; when woken for the same room within `coalesceSeconds` (60); in a private room, when not a member as the claim is made; and for `joined`, unless they still hold `admin` or `mod` and are a member of the room or, for a thread, its parent. A registration whose endpoint `PUSH_HOSTS` no longer allows is passed over before it counts. The rest are woken, up to `wakesPerMessage` (10) users, each on every live registration, most recently registered first; a user who qualifies by several reasons is pushed once. Public rooms are visible to everyone, so a mention or reply in one counts, joined or not.
  - Allowances: each push counts when claimed, delivered or not, against the recipient's `pushesPerRecipientDay` (100), the sender's `pushesPerSenderDay` (200; Free: 50) and the server's `pushesPerDay` (5,000; Free: 1,000); past any, the rest are skipped. A user pushed only for `joined` counts instead against their own `joinedPushesPerRecipientDay` (20) and the server's, not the sender's, and is coalesced by `joinedCoalesceSeconds` (300). The coalescing window is kept per user and room in one `push_wakes` row for both windows (moved by `/rename`, deleted by cleanup once past the longer) and does not restart when the user comes back.
  - The pushes go out after the result, kept alive with `waitUntil`; a failure is logged and never affects the post.
- Delivery: the payload is the envelope `{"push_id": …, "unread": …, "message": {…}}` (§4.9), built per registration: `push_id` when the registration has one, `unread` (below) unless the push is only for `joined` or is an operator alert, and `message`, the message object without `log_id`: `message_id`, `room_id`, `from`, `reply_to` when set, and `body` with `text` cut to 200 code points (ending in `…`; left out when empty) and `mentions`. The whole envelope is at most 2048 bytes of JSON (§4.9), so `message` drops `mentions` first, then all of `from` but `user_id` and `name`, then `body` (`body` is also left out when it would be empty), and last everything but `message_id`, `room_id` and `from.user_id`, which always fits (the server asserts it); `format`, `embeds`, `ext` and the `prev_*` links are left out. It is encrypted per [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291) (`aes128gcm`, a fresh P-256 key and salt per push) and sent with a [VAPID](https://www.rfc-editor.org/rfc/rfc8292) `Authorization: vapid t=<ES256 JWT for the endpoint's origin, 12 hours>, k=<public key>`, `TTL` of `ttlSeconds` (a day) and `Urgency: high` for `mentions`, `replies` or `private`, `normal` for `joined` alone (never `low`), without following redirects, all with WebCrypto. Before each push the endpoint is checked again against `PUSH_HOSTS`. The configuration check signs and verifies with the VAPID pair, so mismatched keys fail it. A 404, 410 or 403 (the push service refuses this VAPID key, so the registration was made with another) deletes the registration pushed to, by its primary key and only while it still has the keys pushed to; other users' registrations of the same endpoint are left to their own pushes and to expiry, so the delete stays one row. Any other failure loses that push, which is not retried.
- Unread: `unread` (§4.9.3) is never more than what the user has not seen, and often less: the pushes claimed for them since they last came back (signed in, sent `idle: false`, moved a read cursor, or sent anything from a connection not idle, such as a stale one resuming), each for a message from someone else that came while nobody attended them. A message coalesced away counts nothing, held wakes released together count one, and a push for `joined` alone, or an operator alert (pushed to admins attended or not), counts nothing and carries no `unread`. It is kept in the `uploads_day` column of the user's `push_recipient` counter, which every claim that pushes them writes anyway; only the current UTC day's count stands. A sign-in zeroes it in the reservation that reads the user's status and mutes; the other returns zero it only when a push counted it up since (each push marks the user's connections, `unreadOwed`), so coming back with nothing pushed since runs no SQL. A failure to zero it is logged and left to the user's next return. The count does not drop when a counted message is deleted. This server sends no badge pushes (§4.9.4).
- Cost: a wake claim reads a bounded number of rows per candidate and writes nothing for a message that wakes no one; a status, mute or room mute change writes a few rows; deriving and announcing statuses, and telling an unscoped mute ran out, cost no SQL and no requests. The pushes are outbound requests, which no allowance counts; `/status` shows the day's pushes against `pushesPerDay`. Measured figures are in the [cost report](docs/cost-report.md#push) and its [user status](docs/cost-report.md#user-status) section.

### 4.5 Live text

With the Workers Paid budgets (`liveText` in `src/plans/paid.ts`) and a deployment that sets `PUBLIC_ORIGIN` and the `UPLOAD_SIGNING_KEY` secret, the server advertises `embed:terminal` and `embed:append` and follows [PROTOCOL.md §4.8.3, §4.8.5 and §4.8.6](https://github.com/shazow/apron/blob/main/PROTOCOL.md#483-writes) and the shared server contract for its commands. The Free budgets have the same policy, smaller, and off by default (`features.liveText`); `LIVE_TEXT` overrides either, an admin's `/toggle livetext` turns it off and on, and `LIVE_TEXT_<KEY>` variables set the policy within its calibrated ceilings ([configuration](docs/configuration.md#live-text)). Without `PUBLIC_ORIGIN` and the key, `terminal` and `append` embeds are unknown kinds, kept as sent.

- Starting (both ways share the limits and the accounting below):
  - A `message` with a new `{"kind": "terminal"}` (an optional `title`, single line, 256 code points) or `{"kind": "append"}` embed is posted at once with the embed `{embed_id, kind, title?}`, waiting for its writer; when its write starts, the message is republished with the embed's `url`, `PUBLIC_ORIGIN/live/<128 random bits>` (§4.8.5). The result lists `{embed_id, kind, write_url}` in request order, as for uploads (section 4.3), and a retry gets the same `write_url` while it is unused. A message starts at most one live text and has at most one `append` (more is `denied`). The server owns `url` and `output` (§4.8.2): a save restores them and takes only a terminal's new `title`; a kind cannot change.
  - `/embed-terminal [title]` (the rest of the line, a plain title) and `/embed-append [markdown]` (the rest of the command text, newlines kept and trailing whitespace trimmed, the message's opening `body.text` with `format: "markdown"`, followed by a paragraph break, `"\n\n"`, when not empty, so the streamed text starts a new paragraph; the `message` flow keeps `body.text` exactly as sent), for anyone who may post: everything below is checked and charged at once, the post included, and nothing is posted. The result is `{"embeds": [{embed_id, kind, write_url}]}`, after a `~private` notice in the command's room with the `write_url` in copy-paste recipes (`script -qfc 'stty cols 80 rows 40; YOUR_COMMAND' /dev/null | curl -sT - '<write_url>'`, its macOS form, or `your-llm-command | curl -sT - '<write_url>'`) and the limits that apply to the sender. When the `PUT` arrives, the message is posted from the sender, in the command's room, with the command's `reply_to`: `{text: "", embeds: [terminal]}` or `{text, format: "markdown", embeds: [append]}`, an ordinary new message that wakes as one does (§4.9), and mentions no one. A command's `reply_to` that names no visible retained message is `invalid_params`, as is a `terminal` or `append` embed in any other command.
- Limits (Workers Paid; Free in `src/plans/free.ts`): one open live text per user, an unused `write_url` included (`denied`); starts per user (a guest: per IP) 3 at once and one more each 3 min 20 s, per IP 6 and one each 1 min 40 s, 20 a day per user and 100 a day on the server (`live` rows in `principal_limits`, `retry_after` with no `ext.limits` category, since none counts every request of a row), each start also a post; at most 4 open on the server (`retry_after` until the soonest ends). A `write_url` is an HMAC-signed grant (`l/<id>`, the input cap, a 2-minute expiry) checked in the entry Worker. Streaming lasts at most `maxSeconds` (120) from the `PUT`, `moderatorMaxSeconds` (300) for a registered user with the role `admin` or `mod`, decided at the start; one `PUT` sends at most 2 MB, and an append's at most what it keeps, so that its edits never let it send more than an append without them. A terminal keeps its last 32 KB, cut with §4.8.6's `keep_last`; an append keeps its first `appendMaxBytes` (4,096) and never more than leaves `body.text` within `maxTextBytes`, cut back to a whole character. An append's text is decoded, then edited (§4.8.5): a backspace removes the code point before it and a form feed all the text before it, never reaching into `body.text`; what is kept, and counts against the limit, is the edited text. Each text has at most 10 readers at once (`429`, `Retry-After: 10`) and 30 `GET`s over its life (`403`). Guests use it only where guests may post.
- Writes: the entry Worker checks the token and charges the request to its address's and location's attempt limiters (`CONNECTION_ATTEMPTS`, `LOCATION_ATTEMPTS`, as a connection), then pipes the body natively to the object (an `IdentityTransformStream`, so no JavaScript runs per chunk in the Worker; aborted when the object answers early), which claims the write once (a used, unknown or expired one is `409`), posts a command's message, and reads the body into memory as it streams. Each chunk goes to the readers; a terminal compacts its buffer at twice what it keeps (`keep_last` is stable under repeated cuts), an append stops at its limit. An append decodes as it streams and sends its readers whole characters, edits included (clients apply them), so a reader that connects late gets the edited text so far, without erased drafts, then what follows; a terminal's backspace and form feed stay terminal control functions. The text ends when the body ends, the writer goes (no grace period), the input cap or an append's limit is reached, the time limit's one-shot timer fires (it exists only while the `PUT` does), or a save removes the embed or deletes the message (`edit`: the text ends with that save, and nothing more is published; `/purge` ends its owner's). Then, exactly once, the object publishes a server snapshot (`prev_log_id` set): a terminal's embed `{embed_id, kind, title?, output}` without `url`, or for an append the kept text appended to `body.text` (mentions unchanged), the embed removed, and `embeds` left out when none remain; with nothing kept, the embed is removed, and a message left with neither text nor embeds becomes a tombstone. Only then is the `PUT` answered, in plain text (`200` "Done: the text is posted.", or why it stopped). A terminal's `output` is cut further while its JSON passes 128 KiB (`MAX_TERMINAL_OUTPUT_JSON_BYTES`), so the record fits a history response however its control characters escape. The snapshot is charged as maintenance, as finishing admitted work.
- Reads: `GET` (or `HEAD`) of `url`, charged to the same attempt limiters, returns `text/plain; charset=utf-8` with `X-Content-Type-Options: nosniff`, `Cache-Control: no-store, no-transform` (`no-transform` stops the edge compressing it, which would hold back the stream until it ends; `wrangler dev` compresses it anyway when the client accepts gzip, so test live reads locally with `Accept-Encoding: identity`), `Content-Security-Policy: default-src 'none'` and `Access-Control-Allow-Origin: *`: the kept text, then what arrives, from memory, until the text ends, in batches sent at most every 50 ms (or at 16 KiB), so a writer's small chunks do not each cost a write per reader. A reader that falls 256 KiB behind is dropped. Once the text ends, or for an unknown id, `404`.
- State: the open texts are one `_meta` row (`live_texts`, a JSON array of at most `concurrent` entries: write key, url id, kind, owner, IP key, state `pending` or `live`, write expiry, time limit, kept size, embed and message ids, and a command's message until it is posted), an additive change with no schema version: read once a wake, kept in memory and written with each change, inside the transaction that makes it. The text itself is never stored while it streams. An instance that is evicted or redeployed mid-stream loses it, so the next instance ends every text it finds marked `live` but does not hold, before its first live text work (a `PUT`, a `GET`, a start), and the alarm does at the text's time limit plus 30 seconds: its embed is removed, with nothing kept. The alarm also ends a message's `write_url` that was never used, removing its embed, and drops a command's. The alarm's deadline is the soonest open text's, recomputed when one starts, streams or ends, so none is left behind; with no open text, live text costs the alarm no SQL.
- Cost: a text is a `PUT` and its `GET`s, each one Worker request and one Durable Object request, two to three posts' worth of SQL rows, and its kept text stored as one record for the retention window; while it streams the object is awake. The [cost report](docs/cost-report.md#live-text) measures them and the worst month at these limits against the plan's included usage.

## 5. Authentication and IP attribution

### Guest

`auth` with `scheme: "guest"` assigns a server-authoritative guest ID `guest_<n>` from a server-wide counter (`guest_1`, `guest_2`, …; [PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication) suggests this convention) and the generated display name `Guest <n>`, bounded by the name limits. Repeated guest auth on that same connection must not mint fresh identities to escape limits: it returns the connection's identity and takes no number. No durable account row is necessary for each guest socket.

Guest numbers are reserved in blocks of `guestNumberBlock` (10): the object serves a block from memory and, when it is used up, advances a durable high-water mark (a `_meta` row) by one block in one write. A start, eviction, or wake loses the in-memory block, so numbers are unique across restarts, hibernation and schema resets (the mark is carried across the wipe) but not contiguous. Reserving and taking a number are synchronous, so concurrent auths never share one. An exhausted budget fails the guest `auth` that needs a new block ([cost report](docs/cost-report.md#guest-numbers)).

Guest identity lasts for that socket, including hibernation, and is not recovered after a reconnect, so guest retry deduplication and ownership cannot span one. IP posting limits still span reconnects.

Guests only read unless the deployment sets `GUEST_POSTING=true`; a read-only guest's `you` carries `ext.permissions` `{"write": false}`. A read-only guest may authenticate, list rooms, read any room's history, and run `/help`; it stays in `general`. `message`, `reactions`, `room_set`, `room_join`, `room_leave`, and `/invite-bot` are `denied` with "Guests can only read here; sign in with a passkey to post or join rooms" (§3.5 and §4.2.2 allow this), and its typing is dropped. Any guest may set its `status` with `me`; a guest's `name` is always `denied` (§3.3).

Every connection gets a `~private` welcome notice right after the `server` frame, before the object reads any frame, to that connection only and with no `room_id`. Its markdown opens with "Welcome to Apron Chat. Server version: `<version>`", the deploy's tag or else the first 8 characters of its Worker version ID (`CF_VERSION_METADATA`). Where guests only read, a second paragraph says so, worded for what the connection can sign in with ("Guests can read. *Sign in with passkey* to participate." where passkeys are offered).

### Bots

A registered user (not a guest, not a bot) runs `/invite-bot` to get a bearer token for a bot account. The bot's `user_id` is fixed as `bot_` plus the owner's `user_id`, and its name is "Bot of <owner's name>" (the owner's `user_id` when the name was removed), cut to the name limits. The first invite creates the bot as an identity row with tier `bot` and no credential, which counts against the registration caps (per IP, per day, and the identity cap) and starts the bot in `general` with a logged `membership` record; a later invite renames the bot after the owner's current name, announcing the change with `user` `new` to those who share a room with the bot, and adds nothing else. Each invite mints a new token, `apron_bot_` plus 32 random bytes as base64url, and revokes the last one: bot connections open with the old token close with 1008. The token goes to the inviting connection only, in a `~private` notice in the room of the command (the token, then instructions to give an LLM for connecting with it), before the `{}` result.

Tokens are kept in the object's key-value storage like passkey sessions: `bot-token:<sha256 of the token>` → `{botId, ownerId}`, and `bot:<botId>` → the current token's key. They do not expire; a new invite rotates or revokes one, and a schema reset wipes them and the bot identities.

Idle bots are signed out: an account whose only role is `bot` that neither signs in nor posts or reacts for 7 days has its connections closed with 1008, leaves each of its rooms as `/kick` would remove it (charged to its posting limits under the limiter key `bot-sweep`), and has its tokens revoked; its account and posts stay. An alarm sweep at most daily (`bot_sweep_ms` in `_meta`) does this, up to 4 bots at a time, going by the identity's `updated_ms` (written at sign-in, on a post at most hourly, and by `/role` and renames; set to 0 once signed out). A new or upgraded object's first sweep only schedules the next a week out. An owner's next `/invite-bot` gives the bot a working token again; a user made a bot by `/role` has no way back in.

A bot authenticates with `auth` `scheme: "token"`, which every connection is offered, since bots send no `Origin`. The `apron_bot_` prefix routes a token to the bot path without a storage read; passkey session tokens still resume only on the origin that minted them. A bot acts as a registered user with its own posting quota and stored memberships, except that `me` cannot rename it ("A bot is named after its owner") and it cannot run `/invite-bot`.

An admin may also make a registered user a bot with `/role <user_id> bot` (section 5, Admins), say one made by `/invite-token` for a script that signs in with its token. Such a user acts as a bot everywhere except that it has no owner: it shows `roles` `["bot"]`, can't register a passkey, change its name with `me`, run the commands for owners (`/invite-bot`, `/passkeys`, `/avatar`), or be an admin, and `/rename` refuses it (`denied`). Its `user_id` is not `bot_…`, so no owner may add it to rooms, and `/purge` treats it as a user. Taking the role away makes it an ordinary user again.

### Devices

A registered user (not a guest, a bot, or `admin`, which signs in with `APRON_ADMIN_TOKEN` only) runs `/invite-device add [<id>]` to get a bearer token that signs in as them on another device. The id is 1 to 32 letters, digits, `_`, `.` or `-`, starting with a letter or digit (else `invalid_params`); without one, the token takes the first of `device_1`, `device_2`, … the user does not hold. A user holds at most 5 device tokens, each under its own id; a sixth id is `denied`, naming the five. Adding the same id again mints a new token and revokes the last one: the user's other connections that signed in with the old one close with 1008, and the user's push registrations are deleted, as after `/passkeys remove`, so the replaced device stops getting their messages. `/invite-device remove <id>` revokes that id's token the same way, answering with a `~private` notice before `{}`; an id the user does not hold is `invalid_params`, naming those they do. `/invite-device list` answers with a `~private` notice listing the user's device ids, oldest first, each with the UTC day it was added (none for tokens minted before this was recorded) and last signed in, or "never used". The asking connection stays open when it signed in with the replaced token, and from then on counts as signed in with the new one; one that removes its own token gets the result and then closes with 1008. The connections close before the push registrations are deleted. A `/rename` or `/purge` of the user that lands while the command is on its way makes it `denied`. Each token is `apron_device_` plus 32 random bytes as base64url, sent to the asking connection only in a `~private` notice in the room of the command, before the `{}` result. A connection signed in with a device token may run `/invite-device` too. Any other form of the command is `invalid_params` with its usage.

Each connection keeps the storage key of the credential it signed in with (its passkey session, or its bot, invite or device token), and revoking a credential closes the user's connections that kept its key.

Tokens are kept in key-value storage like bot tokens: `device-token:<sha256 of the token>` → `{userId, device, createdMs, usedMs}`, and `devices:<userId>` → a list of the user's device ids (each stored as `name`) with their tokens' keys. `auth` with `scheme: "token"` and a device token signs in as the user from any origin, with no session `token` in the result, and writes `usedMs` when it last did on an earlier UTC day. Device tokens do not expire. `/rename` moves them to the new `user_id`, and `/purge` revokes them.

### Admins

Where `APRON_ADMIN_TOKEN` is set ([configuration](docs/configuration.md)), as a Worker secret, `auth` with `scheme: "token"` and that token signs in as the registered user `admin` ("Admin") from any origin, without a passkey. The user is created on first use like a bot, as an identity row with no credential that counts against the registration caps and starts in `general`, and otherwise acts as any registered user. The result carries no session `token`. The `admin` user is always an admin and never holds a passkey, so deleting the secret turns it off completely.

Roles are a column of the user's identity row, `roles_json`, a JSON list of role names in the order given (at most 8; `[]` for none), read with the identity wherever it is read anyway and kept on the connection after sign-in. They move with the row on `/rename`, go with it on `/purge`, and are carried across a schema reset with the user's passkey (but `bot`). The `admin` user is created with `admin`, and an owner's bot (`bot_…`, identity tier `bot`) with `bot`; neither can lose it. Current user objects carry `roles`, `[]` included, so a client's kept object clears a lost role even if it missed the `user` notification; guests and recorded objects carry none. Any role name is a label for display, except: `admin` runs the admin commands; `admin`, `mod` and `threader` move other users' messages between rooms; `admin` and `mod` create and edit top-level rooms (section 4); `bot` makes the user a bot (section 5, Bots); and any role selects the trusted posting limits (section 6). Admins may run these commands, each answered by a `~private` notice to the sender before the `{}` result:

- `/admin <user_id>`: makes that registered user an admin, or says they already are. `/admin remove <user_id>` takes it away again (not from `admin`). A bot can't be an admin (`denied`). Each change is announced with `user` `you` to the user's connections and `new` to those who share a room with them, with the new `roles`.
- `/role <user_id>` (a leading `@` is allowed): says which roles a registered user or bot has. `/role <user_id> <role>` gives them the role, or takes it away when they have it, announced like `/admin`'s. A role is 1 to 24 lowercase letters, digits, `_` or `-`, starting with a letter (taken case-insensitively). `friend` grants the trusted posting limits and `/emoji`, and nothing else. `/role <user_id> admin` is `/admin`. `bot` is not given to an admin, nor to a user who holds a passkey (`/invite-token` makes a token-only user). `admin` can't be taken from the `admin` user, nor `bot` from an owner's bot, and guests have none: those, unknown users, malformed roles, and a ninth role are `invalid_params` or `denied`.
- `/kick <user_id>`: removes the user from the room of the command, as if they had left it (`room_leave`): a registered user's leave is stored and logged, and its membership goes to the room's other members in `room_update` `memberships`; a connected guest's leaves its connections. The user's connections get `room_update` `left` (with the membership, for a registered user), and they may join again. It is charged to the admin's posting limits. Kicking oneself is `denied`, and a user not in the room `invalid_params`. The notice goes to the kicker only; the room's other members learn of a registered user's removal from the membership, not a `~room` notice, and a guest's removal reaches only the guest.
- `/rename <old_user_id> <new_user_id>`: gives a registered user (not a bot, a guest, or `admin`) a new `user_id`, 1 to 64 letters, digits, `_` or `-`, starting with a letter or digit and ending with a letter, digit or `_`, not `guest_…` or `bot_…`, and not taken. The identity row, its passkeys, stored memberships, roles, created rooms (`creator_id`), uploads, limiter windows and dedup rows move to the new id. The old `user_id` is retired (`renamed:<old>` in `_meta`) and never reissued, until a schema reset. The user's connections become the new identity and get `user` `you`, and those who share a room with the user get `user` `new` with `old` ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)). Their push registrations, status, mutes, read cursors, wake times, invite and device tokens move too. What the user left under the old id is rewritten to the new one, keeping the recorded names: the `from` of their logged and current message snapshots, their reaction sets, logged and current, and their logged membership changes. This is the one case where a logged record changes after the fact. It is not announced; clients see the new id when they load history again. Finding the records scans the retained log once, like `/purge`. Other users' `body.mentions` keep the old id; the user's sessions are `denied` on resume and deleted then or when they expire; and the user's bot keeps its `bot_<old>` id and token, while a later `/invite-bot` makes a new `bot_<new>`.
- `/invite-code <uses>`: mints the sign-up invite ([PROTOCOL.md Appendix B](https://github.com/shazow/apron/blob/main/PROTOCOL.md#appendix-b--valid-scenarios-informative)), `apron_join_` and 43 base64url characters, sent in a `~private` notice before the result: a token that signs up to `uses` (1 to 50; more is `denied`, a count limit) new users within 7 days. There is one live invite: a new `/invite-code` revokes the last, and `/invite-code 0` only revokes it. It is kept in key-value storage under its SHA-256 (`join-token:…`) with its remaining count and expiry, and a `join-invite` pointer. Each `auth` with `scheme: "token"` and the invite (from any origin, on an unauthenticated or guest connection) creates a registered user with no passkey, named as `auth`'s `name` asks (trimmed, within the name limits; else "Member"), with a `user_id` picked from the name like a passkey registration's, charged as a registration against the per-IP, daily, and identity caps, starting in `general`. The result carries `you` and the new user's own `apron_invite_` token, which the client signs in with from then on. A used-up, expired, or revoked invite is `denied`, and a used-up or expired one is deleted when it is tried. Uses are serialized with the other token work, so they never exceed the count. A sign-up reserves its whole key-value cost before the account is created and spends no use when the connection has already closed; the put of the token and the counted-down invite follows the account's creation with no await between them. The session lock is taken before the mutation lock; no code takes them the other way round.
- `/invite-token <user_id>` (a leading `@` is allowed): creates a registered user with that `user_id` and no passkey, named after the `user_id` and starting in `general` (a logged membership), charged as a registration against the per-IP, daily, and identity caps. The `user_id` follows `/rename`'s rules and must be free: not held by any identity or retired by `/rename` (`invalid_params` "The user_id … is taken"). The sender gets the user's bearer token, `apron_invite_` and 43 base64url characters, in a `~private` notice before the result. `auth` with `scheme: "token"` and it signs in as that user from any origin, like a bot token; it does not expire and is stored only as its SHA-256. The user is an ordinary registered user: they may rename themselves, run `/invite-bot`, and set an avatar. `/rename` moves the token to the new `user_id`, and `/purge` revokes it.
- `/invite-purge <user_id>` (a leading `@` is allowed): takes away every way a registered user signs in and gives them a new one. Their invite and device tokens are deleted; their passkeys are removed and their WebAuthn user handle cleared, which ends their passkey sessions (below); a marker `auth-reset:<user_id>` ends those issued before sessions recorded the handle; and a new invite token is minted, as `/invite-token`'s, replacing any earlier one. Then all their connections close with 1008, even if a step failed, and their push registrations are deleted. The sender gets the new token in a `~private` notice before the result. Their account, posts, rooms, roles and bot stay, and they may register a new passkey once signed in. Another admin may be the target: the sender then holds the only way into that admin's account. A passkey login or passkey addition whose ceremony was verifying when the purge ran is `denied` at its finish. Not the sender, `admin` or a bot (`denied`); an unknown user is `invalid_params`.
- `/purge <user_id>` (a leading `@` is allowed): disconnects the user and their bot (`bot_<user_id>`), then deletes, silently and with no new records, their message snapshots and current messages with every reaction set on them, their reaction sets elsewhere, their memberships and membership records, their uploads and avatar (R2 objects included; custom emoji they added are the server's and stay), and their identity (with its roles and `ext`), passkeys, bot, invite and device tokens, push registrations, status and mutes, limiter and dedup rows. Each purged identity's `user_id` is retired (`purged:<user_id>` in `_meta`) and never issued again, so a passkey session still held for it fails and is deleted when presented or when it expires. A logged record listing them beside others (a move's reaction sets) is rewritten without them; rooms they created stay, without a `creator_id`. A thread the purge leaves nobody in is removed, as after a leave. Clients already showing their content keep it until they load history again. Not the sender or `admin`; an unknown user is `invalid_params`. The sender gets a `~private` notice with the counts before the result.
- `/toggle activity`, `/toggle uploads` (with uploads configured), `/toggle presence` (with push configured), `/toggle addmember` and `/toggle livetext` (with live text configured; texts streaming finish): turn the feature off or on for everyone and answer with a `~private` notice naming the new state. The override is kept in `_meta` across restarts; toggling back to the deployment's default (the plan or `ACTIVITY` for activity, on for uploads and addmember, the plan or `PRESENCE` for presence, the plan or `LIVE_TEXT` for live text) removes it, and a schema reset clears it. New connections are offered the cap (`activity`, `embed:upload`, `embed:terminal` and `embed:append`) only while the feature is on; connected clients keep the caps they were given. With activity off, `activity` gets the unsupported-method path. With uploads off, `/help` leaves out `/avatar`; new upload embeds, `/avatar` and `/emoji add` are `denied` ("Uploads are turned off here"), while `/emoji remove` still works; writes already started still finish; and new connections get `server.ext.media` without `upload`, `avatar` and `emoji`. With addmember off, a registered user's `room_join` with another user's `user_id` is `denied` unless they are an admin or it names their own bot; members already added stay; connected registered users but admins and bots get `user` `you` with their new `ext.permissions`, as again when it is turned back on. Presence off and on is section 4.4, User status. With live text off, `/help` leaves out `/embed-terminal` and `/embed-append`, which become unknown commands, and new `terminal` and `append` embeds are `denied` ("Live text is turned off here"). Any other argument is `invalid_params`.
- `/emoji add :name:` and `/emoji remove :name:` (also for mods and friends): section 4, Extension `ext:emoji`.
- `/server` ([PROTOCOL.md §4.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#41-command), its suggested convention): alone, a notice showing the server's `title`, `description` and `avatar` (section 4) and where each comes from. `/server title <text>` and `/server description <text>` set one: the text after the field, trimmed, line breaks kept, with the rules of `SERVER_TITLE` (one line within the display-name policy) and `SERVER_DESCRIPTION` (at most 500 bytes); anything else is `invalid_params`. Without the text, each clears its `_meta` row, so the fallback applies again. `/server avatar` with one upload embed sets the avatar (section 4.3), and alone clears it; text after `avatar`, more than one embed, or an embed on any other `/server` is `invalid_params`. A set or clear answers with a notice saying what it did and the three values, before the result; a change sends every connection a new `server` frame.
- `/status`: today's Cloudflare account usage (refreshed from account analytics at most once a minute, where `ACCOUNT_ID` and `ACCOUNT_ANALYTICS_TOKEN` are set) against the selected plan's daily allowance (for Workers Paid, its monthly included usage over 31 days, with the month's estimated bill, the overage added today, and the bill cap), and the object's own daily reservations (SQL reads and writes, frames, admissions, posts, registrations), registered users, open connections and database size against their budgets, as CommonMark lists.

### Canonical WebAuthn authentication

Implement protocol [§4.10](https://github.com/shazow/apron/blob/main/PROTOCOL.md#410-webauthn-authentication): `action` is `register` or `login`, `step` is `begin` or `finish`, and both steps require request IDs. Support discoverable passkeys; do not download a directory of all credentials to the client.

```json
{"method":"auth","id":"a1","params":{"scheme":"webauthn","action":"register","step":"begin"}}
```

A registration `begin` may carry `name`, the display name to register with (trimmed; over the name limits is `too_large`). It also picks the new `user_id`: the name as lowercase ASCII letters and digits, other runs as one `_`, at most 16 characters, plus `_` and 4 random digits (`Foo` → `foo_1234`), retried up to 8 times while taken. With no `name`, or one that leaves nothing usable or would read as a guest (`guest…`) or bot (`bot…`) id, the id is `u_` plus 16 random bytes as base64url and the name is the guest's. The id is only a candidate until `finish`, which still fails if another registration took it meanwhile.

The intermediate response is `{"id":"a1","result":{"challenge_id":"...","public_key":{...}}}`: JSON-encoded WebAuthn creation options (request options for `login`), binary fields as base64url. It does not authenticate the socket or start live delivery.

```json
{"method":"auth","id":"a2","params":{"scheme":"webauthn","action":"register","step":"finish","challenge_id":"...","credential":{}}}
```

`credential` is the serialized browser credential response. On successful verification return `result.you` plus a bearer `token` for session resume ([policy](docs/policy.md#authentication-policy)), store the authenticated tier in the attachment, and start live room delivery. Login uses the same exchange with `action: "login"`.

- Challenge TTL: 120 seconds, one outstanding challenge per connection. A challenge is bound to connection, action, RP ID, and allowed origin, and is consumed by a matching finish attempt. Begin replaces an earlier challenge. A challenge does not extend the initial authentication deadline; challenge expiry and unauthenticated timeout are independent.
- A guest may register or log in on its guest socket and keeps guest rights until success; a registration replaces the guest identity on that connection, and a login departs it (section 4, `user` notifications). A failed upgrade grants no higher allowance.
- A registration on a connection already signed in as a registered user adds the passkey to that account ([PROTOCOL.md §4.10](https://github.com/shazow/apron/blob/main/PROTOCOL.md#410-webauthn-authentication)): `begin` offers creation options for the account's `user_id` and name, under its WebAuthn user handle (an account without a passkey yet, such as an invited user, gets a new one, stored at `begin` so concurrent ceremonies share it), excluding its existing passkeys; a verified `finish` stores the credential and answers `{you}`, the connection staying signed in as it was (no new session token), and the account's other connections get a `~private` notice that a passkey was added. A bot and the `admin` user (section 5, Admins) are `denied`. There is no re-authentication step: any signed-in connection may add a passkey, so the account's other connections are told.
- `/passkeys` (registered users other than bots) lists the sender's passkeys, oldest first and numbered, with when each was added and last used, in a `~private` notice; `/passkeys remove <n>` removes one and tells the account's other connections, but never the last one (`denied`). Sessions a removed passkey started stay valid until they expire. A session records the account's WebAuthn user handle when issued and resumes only while the account still has it, so `/invite-purge`, which clears it, ends them; one issued before sessions recorded it resumes unless `auth-reset:<user_id>` is set, an extra KV read that ends when the last such session expires. An account holds at most 8 passkeys (`MAX_PASSKEYS_PER_USER`); past that, `begin` is `denied`. Each added passkey is charged as a registration against the per-IP and daily caps, not the identity count. A `login` on a signed-in connection is `denied`: switching identity requires a reconnect.
- Configure an explicit RP ID, the server's host or a domain it is under, and exact allowed origins. An allowed origin outside the RP ID is a related origin, which browsers accept only where `https://<RP ID>/.well-known/webauthn` lists it (section 3); browsers without related origins refuse it. Validate type, challenge, origin, RP ID hash, signature, user presence, and user verification using a maintained verifier. Registration requires discoverable credentials, user verification, and `attestation: "none"`. Bound all credential sizes before expensive verification.
- Do not accept a claimed user ID or credential ID as authentication. Resolve identity from the verified stored credential. Handle zero/non-monotonic counters for synchronized passkeys according to the verifier's supported semantics; do not invent a counter-only proof of authenticity.
- Account linking across identities and recovery are out of scope. Unique credential IDs cannot register another identity or be added twice. Store only bounded necessary public-key and verifier metadata.
- Recheck registration caps and atomically write credential/identity/budgets after verification, before returning success. Concurrent successful verifications cannot exceed caps.
- Authentication executes on every new connection; it is not bypassed by the mutation deduplication cache. All begin/finish/retry attempts count toward auth/frame/resource limits.
- Registration does not clear the IP's anonymous usage or aggregate quota. Multiple passkeys remain subject to the common IP/global budgets.

Implementation reference: [WebAuthn verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).

### IP key

Extract Cloudflare's client address in the public entry Worker. Strip any incoming copy of the private forwarding field before setting trusted metadata for the DO. Do not trust `X-Forwarded-For`, client JSON, or a public query parameter. Account for documented Worker-subrequest and Pseudo IPv4 behavior; a missing/unusable trusted IP fails admission rather than creating a fresh unlimited bucket.

Canonicalize IPv4 and IPv4-mapped IPv6 to the same IPv4 key; group native IPv6 by /56, the size ISPs most often delegate to one site, so one subscriber cannot multiply its per-IP limits across its /64s. The entry Worker also limits a native IPv6 /48's attempts together. Store the first 128 bits of SHA-256 of the canonical key, encoded as unpadded base64url. This requires no server secret and is a compact internal identifier, not anonymization. Keep the hash format stable across daily rollover and deployments to preserve active rolling windows. Public users behind NAT share IP limits; explain this tradeoff in the demo help text.

Reference: [Cloudflare request headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

## 6. Default limits

All applicable limits compose: passing one does not bypass another. Time means server time. Per-minute limits on posts, history, authentication, frames and admissions are token buckets (`src/limiter.ts`), not calendar-minute buckets: a quiet principal may spend a burst at once (a minute's allowance, or `historyBurstPer*` for history) and then the rate, a refused request is told its exact wait, and a lower allowance after a higher one still counts what was spent. History is also counted per user and per IP a UTC day, and server-wide on the day's budget row; a request that serves no page gives its server-wide count back. Daily limits use UTC dates and change lazily on access, with no midnight timer. A backward clock jump must not reset a budget or move retention backward.

A user's or IP's limiter row is cached in memory and written on its first charge after it is read, once it holds four charges unwritten, once a minute, and on a new UTC day; server-wide rows are written through, and each operation writes its budget row once, when it settles. So server-wide limits and daily budgets stay exact to within the operation in flight, while an eviction may forget up to three charges of a principal's row: a daily cap of N admits at most N + 6 between evictions, and never more than 4N ([cost report](docs/cost-report.md#limiter-rows-and-the-budget-row)).

A `retry_after` raised by a limit carries its category in `data.ext.limits` (extension [`ext:limits`](https://github.com/shazow/apron/blob/main/EXTENSIONS.md#extlimits)) where it has one ([limits](docs/limits.md#how-a-limit-reaches-you)):

- `read`: a history page (the user's, IP's and server's counts, and a page already in flight on the connection) or a `room_list`.
- `write`: anything charged as posting (`message`, `reactions`, `room_join`, `room_leave`, `room_set`), at every scope. A `me` charged as a post names no category, since the `write` row does not list `me`.
- `upload`: the user's and server's daily upload counts and the stored-bytes cap, charged for each new `upload` embed of a `message` and for `/avatar`'s and `/emoji add`'s image, not for one an edit keeps by its `embed_id`.

Every other `retry_after` carries no category; the daily SQL budget's has `data.reason: "daily_budget"` and the frame budget's `data.reason: "frame_budget"`. A request that changes nothing (a deduplicated retry, a join of a room already joined, a leave of one not joined) is not charged. Messages name the limit in plain words ("Daily posting limit reached") and never its amount, rate or delay; `data.retry_after` carries the timing.

### Application allocations

| Budget | Ceiling | Allocation |
| --- | ---: | --- |
| SQL writes/day | 800,000 (Free: 80,000) | Up to 700,000 foreground; 100,000 reserved maintenance/control (Free: 60,000 and 20,000) |
| SQL reads/day | 30,000,000 (Free: 3,000,000) | Up to 25,000,000 foreground; 5,000,000 reserved maintenance/control (Free: 2,500,000 and 500,000) |

| Resume growth low-water | 640 MiB (Free: 80 MiB) effective occupied storage | Avoid oscillating admission |

The daily post ceiling (10,000; Free: 5,000) is a maximum, not a promise. If the measured schema/traffic exhausts resources earlier, refuse work earlier. Do not claim capacity from a guess of one write per message. Include snapshot/log/index/dedup writes, limiter state, credential counters, alarms, failed work, expired-data deletion, migrations, and bookkeeping. Cleanup's workload includes yesterday's records while accepting today's. Avoid indexing every metadata column or enabling FTS.

Implementation must have one metered storage boundary for all SQL/KV/alarm work. For each operation class, establish a conservative cost bound, reserve it before work, and observe actual SQL cursor row counts to verify the model. Include the cost of the reservation itself. No public request may trigger a full-table scan, unbounded join, migration, or unmetered maintenance query. `LIMIT` alone does not prove bounded scan cost. A cap breach in cost calibration is a release blocker, not a reason to silently raise budgets.

Durable block reservation is allowed to avoid a SQL write on every incoming/rejected frame: commit an allowance before spending it; tie it to an owner and UTC day; never grant the same allowance twice. Persist consumption where necessary, or burn unused allowance on restart. Connection attachments can preserve connection-local lease state across normal hibernation. Budget reservations must remain charged even if subsequent work rolls back or crashes; a rolled-back row is not evidence of refunded platform usage. Once a metered operation finishes, the part of its reservation that its SQL cursors show it did not use (rolled-back rows count as used) is credited back in one budget-row update, which the operation pays for; a crash before then leaves the whole reservation charged, and KV work, which has no cursor, stays fully charged. Exhausted/uncertain accounting fails closed.

Posting window timestamps and counters must survive reconnection/hibernation and concurrent sockets. Keep bounded persistent limiter keys for admitted principals, expire them after their applicable windows, and bound any additional in-memory negative cache. Never create one durable record per attacker-supplied request ID, failed credential, or rejected IP. Proposed limiter-record cap: 10,000, with old expired entries reclaimable in metered batches; new principals are denied when the cap is reached.

The DO is the authoritative limiter. Cloudflare's edge Rate Limiting binding is optional preliminary filtering and cannot serve as an exact global budget. The entry Worker uses it per address, per IPv6 /48, and per location; the per-location limit bounds the DO requests that rejected attempts spend, since a rejection in the Worker costs only a Worker request: [documented locality/accuracy](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

### Storage pressure

Measure physical database bytes and bounded logical payload totals. Reject growth with enough margin for the largest admitted operation, indexes, and control updates; check again after commits. Deletions may free SQLite pages for reuse without shrinking `databaseSize`. A file staying large must not be mistaken for still-occupied data, and delete/reinsert churn must not make it grow without bound. Determine actual supported freelist/page instrumentation and page reuse in tests. Do not assume VACUUM is available or free, and do not put it on a request path.

At pressure thresholds, purge only already-expired data and stop growth if that is insufficient. Do not silently shorten the advertised retention window to accept another message. The hard target does not guarantee a day's ceiling of maximum-size messages plus all ancillary data; size admission takes precedence. Never delete the whole database to reclaim chat space because it contains credential and quota authority.

### What can and cannot be guaranteed

Select the budgets that match the account's plan, use no paid ancillary services, and reserve account headroom for this workload. Incoming rejected HTTP/WebSocket traffic still consumes platform resources; no application limiter can guarantee availability under unlimited hostile traffic. On Workers Free, Cloudflare's hard free-plan limits are the final zero-overage backstop. On Workers Paid there is no such backstop: rejected traffic past the included usage is billed. A budget guard on a minute cron trigger reads account usage for the day and the calendar month, prices what runs past the plan's inclusions (`src/pricing.ts`), and, once the overage added today passes `BILL_CAP_DAY` ($5) or the month's passes `BILL_CAP_MONTH` ($25), enables a zone WAF rule that blocks the server's hostname before the Worker runs ([budget guard](docs/configuration.md#budget-guard)). App quotas provide controlled degradation under admitted traffic, not a network-level request shield.

One active object at the documented memory allocation uses roughly 10,800 GB-seconds over a full day, below the duration allowance; still use hibernation and avoid extra production objects. Fan-out remains processing/memory work even when it has no outgoing request charge. Native resource errors must be caught where possible and fail closed without reconnect or alarm retry storms.

## 8. Persistence and transaction boundaries

Use versioned schema migrations, parameterized SQL, minimal indexes, and synchronous transactions for related writes. Do not run migration DDL on every hibernation wake. Keep constructors light and initialize once per schema version under the appropriate initialization gate. Reference: [SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

Suggested logical schema; physical layout may change to reduce measured costs:

| Table/state | Required contents |
| --- | --- |
| log_state | Server-wide last log ID, monotonic history floor F, last commit time, as of the last retention or `/purge` (the newest record is the head between them) |
| rooms | Room ID, fixed parent, creation/current record log IDs, per-room head, bounded client fields (`title`, `description`, `ext`), count of stored registered members; `general` plus at most 100 threads and created top-level rooms, of those at most 16 top-level, and at most `privateRoomLimit` (100) private rooms in their own key range |
| memberships | Each registered identity's joined rooms, one row per room and user: by room (the primary key) for `members`, and by user for the user's rooms; guests' live in connection attachments |
| records | Room/log primary key, internal commit time, record kind, complete record JSON; a move is stored in both rooms |
| message_state | Message ID primary key, current room, latest log ID (its snapshot is that record) and author |
| reaction_state | Message/user primary key, latest log ID, reacting identity, emoji set |
| identities/credentials | Stable user ID, unique credential ID (several per user ID, at most 8), public key, required verifier state, bounded name, roles, the user's `ext` (`ext_json`, at most 512 bytes), and when the status others see of the user last became `offline` (`seen_ms`, 0 for none) |
| push_subscriptions | User and push endpoint URL primary key, browser keys (`p256dh`, `auth`), the client's optional `push_id`, wake scopes, created and registered times; by registration time for expiry, and by registration time for moderators' that keep `joined` (a partial index); a user's are a primary-key range |
| user_status | User primary key, the `status` the user chose with `me` (`online` by default) and until when they are muted (`status` `mute` without `room_id`); a row only while either differs from the default |
| room_mutes | User and room primary key, until when the user muted the room and its threads (`status` `mute` with `room_id`); at most 100 a user |
| read_cursors | User and room primary key, the `read_message_id` the user read the room through (§4.6); one a membership at most, deleted with it |
| push_wakes | User and room primary key, when the user was last woken by push for the room (coalescing); by that time for cleanup |
| accepted_requests | User/request primary key, canonical method+params digest, the result's identifiers (replayed against current state), expiry |
| resource_budgets | UTC day, charged/reserved reads/writes/frames/admissions/posts/registrations |
| principal_limits | Bounded IP/user counters and each scope's token bucket (`level`, `level_ms`) |
| maintenance | Next due tasks, pending cleanup cutoff/cursor, schema version |
| _meta | Schema version, effective clock, bounded counters and latches, the guest-number high-water mark, and the custom emoji catalog (`emoji_catalog`, the JSON as published) with the R2 key of the one before (`emoji_catalog_previous`) |

Indexes cover per-room log ranges (the primary key), the server-wide log prefix (commit times follow it, so it also serves expiration), registered memberships by room (the primary key) and by user, dedup expiry, and limiter expiry. A record belongs to every room its message is in just before or after it; storing a move once per room keeps each room's history a single indexed range. Benchmark the actual query plan.

Each mutation, after resource reservation and validation, performs one atomic decision: check dedup, recheck all applicable quotas/ownership, allocate log IDs, update current state, append every record to each room log it belongs to, advance room heads, record result, update applicable posting counters. Send the recorded result and ordered broadcast only after success. Do not call remote services inside the mutation transaction.

Store internal commit time for retention, distinct from the wire log ID. Make commit times nondecreasing so expiration is a prefix of the log even if the system clock rolls back. Keep a nondecreasing effective time for budget/retention decisions; clock anomalies may delay expiry, never resurrect expired data or replenish a used budget.

### Schema versions

The schema version lives in `_meta` and the `maintenance` row. A new object creates the current schema, 11, and seeds the `general` room's creation record. Schema 11 is the table above plus the `uploads` table and each identity's avatar. Every table keyed by text or by more than one column is `WITHOUT ROWID`; `records` is indexed by `log_id` alone, as commit times follow log order (section 9); `message_state` points at each message's latest record rather than copying it; and `log_state` is written by retention and `/purge` before they delete records, not by every commit (the head is kept in memory, read once a wake). An additive change that older code ignores and whose absence reads as its initial value needs no new version, such as a `_meta` row like the guest-number mark or `presence_on_ms`.

Schemas 7 to 10 are upgraded in place to 11 on the first wake, synchronously in the constructor, keeping history, sessions, tokens and every passkey. Each step is one transaction:

- 7 → 8 creates the push, wake, status and room-mute tables and adds `identities.ext_json`.
- 8 → 9 adds each limiter row's token bucket (minute limits start over once; day counts are kept) and each budget row's history count, leaving the old timestamp-list columns unread.
- A schema 9 object lacking `identities.seen_ms` gains it (probed with `SELECT seen_ms FROM identities LIMIT 0`); a schema 10 wake does not probe.
- 9 → 11 deletes state below the history floor and rebuilds each table the current schema keys differently, copying rows by column; `read_cursors` starts empty. It can cost more than a day's maintenance allocation, so it is logged (`storage_schema_upgraded`) and not charged to the day's budget.
- 10 → 11 deletes state below the history floor and drops unread indexes and the uploads' `content_type`, charged.

The other steps charge the rows they measurably read and wrote to the day's maintenance reservation without a capacity check. Row counts are in the [cost report](docs/cost-report.md#schema-upgrades-and-reset).

An upgrade fails closed: if it throws, its transaction rolls back, the object stays at its schema, and the constructor throws on every wake until a fixed deploy upgrades it. It never falls back to the reset. An upgrade is also one-way: code of an older schema finds a newer one and resets the object; roll forward rather than back.

Any other schema version, older or newer, resets the object: the constructor wipes it with `deleteAll()` (every SQLite table and key-value entry) under `blockConcurrencyWhile`, then creates a fresh schema. Carried across the wipe:

- Up to `MAX_CARRIED_PASSKEYS` (100) credentials of `registered` identities, most recently used first, written back with their identity rows (same `user_id`, name, WebAuthn user handle and roles, but no avatar, `ext` or `seen`), `identity_count`, and a `general` membership row (without a log record). Passkeys past the cap, bot identities, and the `admin` user are dropped. The carry reads `identities` (with `roles_json`), `credentials` and `memberships` by column name, so only a schema 7 or later object carries passkeys; a schema change to those tables must keep that query working or accept that the reset drops them.
- The current UTC day's resource-reservation row, added back together with the one-time 512/512 bootstrap reservation and the carry's measured rows, charged as maintenance without a capacity check, so a reset neither replenishes today's usage nor fails on an exhausted budget.
- The guest-number high-water mark, so a reset never reissues a guest ID.

The overrun guard (breakers) is not carried (section 10). The log head is not preserved; new log IDs are commit-time milliseconds and normally still exceed old ones, and clients rebuild from the listed history bounds. A token that outlives its session or identity is `denied`, sending the client back to sign-in.

### Deduplication

Deduplicate accepted mutating requests by `(user_id, request_id)` for 24 hours after acceptance. Canonicalize method and params recursively with stable object-key ordering, preserving arrays/types; other envelope keys are not part of the operation. Store a cryptographic digest rather than a full duplicate message payload where practical. Same key/same operation is not executed or broadcast again, and returns a result reflecting the current state ([PROTOCOL.md §1.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#12-retries-and-deduplication)): the stored result names what the operation made (`message_id`, `room_id`), which stays true, and an upload's write grant is left out once its write was claimed, finished, or expired (one indexed read per upload embed); `me` answers with the current `you`. Same key/different operation returns invalid_params. Concurrent copies cause one effect and one broadcast. Dedup responses still spend their bounded lookup/frame costs.

Check an unexpired duplicate before applying new-post quotas or deciding an old message has expired; a previously accepted result remains valid through the dedup window. Expired records are logically absent even if physical cleanup is pending. Failed/limited operations are not recorded as accepted. Notifications have no dedup guarantee. After the documented TTL, replaying an old request ID may execute again; the client must not retry stale queued operations indefinitely.

## 9. Rolling history and base-protocol availability

Keep `general` unchanged. Every cleanup interval (`cleanupSeconds`), expire the prefix of the server-wide log committed more than `retentionSeconds` earlier: 7 days once a day on Workers Paid, 24 hours every hour on Workers Free. Healthy operation normally exposes the retention window plus up to one interval of records (7 to 8 days on Paid); scheduling delay or quota exhaustion can delay physical cleanup. This is a demo history policy, not a secure-erasure SLA or a guarantee about backups, provider recovery, or copies on clients.

### Retention semantics

- Expire records by their internal nondecreasing commit time, not message creation ID. Commit times are nondecreasing in log order, so expiry is always a prefix of the one server-wide log.
- Retain a current message while its latest record remains retained. Remove current state when its latest record expires. Tombstones and reaction sets follow the same rule; a move re-logs the moved message's reaction sets, refreshing them.
- A recent edit can keep a message visible past the retention window from creation. Its older creation/edit records may be removed; its latest complete snapshot is sufficient to reconstruct it.
- A registered user's membership is current state, kept in `memberships` after its record leaves the log (see "Memberships" in section 4).
- Room records are current state, like messages: a room keeps being listed with its latest record (and that record's original `log_id`) after the record itself leaves the log. A thread room whose entire log has expired is removed, and its members get `room_update` `left`.
- Physical row deletion is separate from logical visibility. History, edits, and lookups always enforce the published floor, including during partial cleanup.
- Passkeys and global/principal budgets are independent of chat retention. Dedup uses its own 24-hour expiry.

### Floor definition and wire shape

Internally maintain one server-wide positive log boundary F, initially 1. All
records with `log_id < F` have been logically discarded; records at/above F, if
committed, are available. F never decreases and is not a client checkpoint.
Advance F to one greater than the greatest record logically expired. If
nothing further expires, retain F. Future IDs must be at least F.

On the wire, each room reports its own values. `latest_log_id` is the room's
historical committed head H (the greatest `log_id` in its log), including when
history expires. `history_log_id` is the inclusive decimal-string coverage
boundary max(F, the room's creation `log_id`) while that is <= H, and `null`
when no history remains. A new room's history therefore starts at its creation
record. Clients derive the effective floor from a null value as H + 1; no
inverted range is sent on the wire. The boundary never decreases: F is
monotonic, and a room reports `null` only while F > H, so any later record in
the room is at least F.

Include both fields in every room record the server sends (`room_list`,
`room_update`) and every successful history result, without an extension
advertisement:

```json
{"method":"room_update","params":{"updated":[{"room_id":"general","log_id":"1789900000000","title":"General","latest_log_id":"1790000001000","history_log_id":"1789913600001"}]}}
```

```json
{"id":"h1","result":{"more":false,"latest_log_id":"1790000001000","history_log_id":"1789913600001"}}
```

This empty page can represent an out-of-range or expired query; only a room
whose retained log is empty uses `history_log_id: null`.

After advancing F, tell removed thread rooms' members first with `room_update` `left` (no storage access), then send every room whose `history_log_id` changed as `room_update` `updated` to the members of the room and of its parent, with the listing charged to the maintenance budget; a failed listing never suppresses committed removals. A cleanup job whose last batch reported more work (including thread rooms still awaiting removal) continues on its next run without the idle probe ending it. Attach both wire boundaries atomically with each history page's query snapshot; do not return entries evaluated under an older floor with a newer response floor. Capture response state synchronously without external awaits. Keep F monotonic on clients even if paginated responses arrive out of order.

### History queries

Follow protocol [§4.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#43-history): inclusive after/before, forward oldest selection when after is present, backward newest otherwise, always return each array ascending.

With `room_id`, that room's log is paged; unknown rooms, and private rooms the requester is not in, are `invalid_params`. Without `room_id`, the logs of every room the connection has joined are paged as one log; `latest_log_id` is the greatest of those rooms' heads, and `history_log_id` is where the server's log starts (the default room's creation, or the retention floor past it), so it never moves with a join or a leave; with nothing retrievable the log is empty, `history_log_id` is null, and `latest_log_id` ends just before that start. Such a page scans at most four pages of the server-wide log for the joined rooms' records, and when that comes up short reads each joined room's slice instead, so its reads stay bounded by the joined rooms.

A moved message's snapshot, in both rooms' logs, is returned once. A window with `after` equal to `before` returns exactly that record when it is retained in the requested room's log; a moved message's earlier snapshot is fetched from the room its `prev_room_id` names. Query only the intersection with the room's `[history_log_id, latest_log_id]`. `limit` counts records of every kind, and `first_log_id`/`last_log_id` span all kinds; results are partitioned into `rooms` (with the room's delivery fields), `messages`, `reactions`, and `memberships`, each omitted when empty. An empty or entirely expired range returns `more: false` and neither bound, with F; do not invent pagination IDs. History carries no `users`. No compaction is required for this version.

Select from the room's own log before the source-slice limit. With a byte cap, shrink the effective positive limit before selecting the final contiguous slice in the requested direction. Return its true first_log_id/last_log_id and more, accounting for records omitted due to either count or byte cap. Each allowed snapshot must fit into at least one response with envelope overhead. Forward continuation is last_log_id+1, backward continuation first_log_id-1; never use string ordering or message IDs for pagination.

A move's snapshot appears in both rooms' histories and carries the destination `room_id`; the message's earlier history stays in the source room. Threads are separate rooms with independent histories and floors.

### Client recovery

The implementing harness must add this behavior to the demo client:

1. Track the greatest advertised F per room. Remove cached snapshots whose greatest applied log ID is below F; remove expired pending rendering references. Preserve newer snapshots even when their message creation IDs are old.
2. A checkpoint C is usable for forward recovery only when `C + 1 >= F`. If `C + 1 < F`, some uncovered records were discarded: clear that room's recovered state/checkpoint and rebuild from F. This handles the exact boundary without needless resets at `C = F - 1`.
3. Capture head H when establishing live delivery. Recover forward through fixed H, buffer live entries above H, apply newer snapshots only (at an equal `log_id` a tombstone wins, [PROTOCOL.md §2.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#23-records-and-replay)), then drain the buffer. Without a checkpoint, the client may instead load the newest page with `before: H` and older pages on demand ([PROTOCOL.md §4.3.5](https://github.com/shazow/apron/blob/main/PROTOCOL.md#435-replay-and-recovery)). If F>H, the retained initial view is empty and subsequent live entries can proceed.
4. Before applying each page, inspect its F. If retention has overtaken the next unprocessed recovery position, discard the partial history replay and rebuild against the new floor while preserving the fixed head H and retained live entries buffered above it. Do not mark a silently truncated gap as recovered. Cancel or ignore obsolete in-flight requests by a local recovery generation.
5. An increased floor within already processed coverage need not restart recovery, but must evict newly expired snapshots. Bound live/recovery buffers (1 MiB or 1,000 entries); on overflow, clear partial recovery and reconnect/recover with backoff.
6. Each room's checkpoint is independent; threads are separate rooms. Eviction and asynchronous older pages must never resurrect snapshots below the current floor or overwrite a newer snapshot.
7. Room record updates (`room_update`, listings) do not advance checkpoints or replace an active fixed recovery head by themselves. The floor only invalidates unavailable history.

Include a visible demo notice of how long history is retained.

### Cleanup algorithm and failure recovery

Use a single scheduler backed by the DO alarm API. Due cleanup fixes a cutoff (`effective_now - retention`) and identifies an expired log prefix with indexed, bounded work. Persist logical floor advancement and a cleanup job before discarding its rows. Publish floor changes in commit order. If discovering the prefix requires several batches, advance the floor incrementally; each visible floor must match actual logical coverage.

Delete expired records, each with the message and reaction state that points at it (a message's state row with its latest record, and each reaction set with the record that logged it, by its whole primary key from the users the record names; every state row counts against the batch with its record, and a record whose state would not fit waits for the next batch), fully expired thread rooms and then their stored memberships, expired accepted-request entries, and expired limiter state in bounded, metered batches. Retained latest snapshots and necessary current state must not be accidentally removed with an older version of the same message. Never reset room head, floor, credentials, or live quota counters. A next task is scheduled until the job completes; ordinary cleanup starts every cleanup interval, continuation wakes only as needed and within the budget.

Retries are idempotent and work from persisted progress. A crash before or after any batch must preserve externally advertised coverage. If maintenance budget is exhausted, defer physical work until resources reset, suspend growth as needed, and do not spin alarms. Alarm/API failures must not permanently orphan cleanup: re-establish missing due work on subsequent valid activity as well as documented alarm retries. No live socket is needed to perform cleanup.

Use the same scheduler for unauthenticated socket deadlines, batching deadlines where possible; every alarm setup/invocation is accounted. Alarms are at-least-once and retries are finite: [Alarm API](https://developers.cloudflare.com/durable-objects/api/alarms/).

## 10. Degradation and public-demo behavior

| Exhausted resource | Required behavior |
| --- | --- |
| Principal posting limit | Reject new mutations with retry_after; allow affordable reads |
| Global daily posting/foreground write budget | Read-only until replenished; matching dedup retries may return stored results |
| Read/history budget | Reject history; do not fake an empty successful history page |
| Registration count/durable identity cap | Stop registration; existing logins and guest use continue if affordable |
| Storage high-water | Stop growth, clean expired data using reserve, resume only when safe |
| Socket/admission cap | Reject upgrade; existing sockets continue if affordable |
| Daily foreground SQL or frames at 70% (degraded tier) | Refuse live text, uploads and older history with `retry_after` (`data.reason` `degraded`) until the reset; chat continues |
| Global frame budget | Refuse new frames and admissions with `retry_after` until reset; keep open sockets |
| Accounting overrun (an operation's rows exceeded its reservation) | Observe it: the operation finishes, the excess is charged, it is logged under the operation's name, and the day's first is told to the admins. Three of one foreground operation within an hour refuse that operation for an hour (`retry_after`, `data.reason` `operation_paused`) |
| One overrun past a hundredth of a day's SQL ceilings | Open that operation's breaker at once, for an hour; the operation itself finishes |
| Storage failure leaving accounting uncertain (a budget read or write failed) | Fail closed only while it fails ("Server storage is unavailable; try again shortly"); reopen once the staged budget write lands, with no operator. Where it can be written, a marker (`uncertain`) survives an eviction: the first operation after the next wake charges a hundredth of the day's SQL ceilings for what the lost instance left unwritten, then reopens |
| Estimated overage past the bill cap (Paid: `BILL_CAP_DAY` $5 today, `BILL_CAP_MONTH` $25 this month) | Account stop: 503 and sockets closed once; the budget guard turns on the edge stop until the day's or month's end |
| Shadow burn of $1 an hour or more, mostly refused (a flood), or breakers open on three operations | Attack pause: refuse everything with 503 and `Retry-After`, close every socket, edge stop held 30 minutes (doubling with each pause that UTC day, at most 4 hours); lifts by itself, or at once with `ATTACK_PAUSE=false` |
| Cloudflare hard limit | Fail closed; no automatic paid fallback |

Every 503 for a failure or overload carries `Retry-After`: its own delay where it has one, else 60 seconds (an operator's admission switch and a configuration error carry none), so an outage is not met with every client retrying at once. An internal error says its cause where it has one (storage unavailable, or "Server unavailable; try again shortly" when the object itself throws), so a connection status probe alone tells why the server refuses.

The admins hear at once when the edge stop turns on or off (by the budget guard or the flood trip), the server changes tier (open, degraded, exhausted, account stop, paused) either way, heavy traffic that is mostly admitted burns past $1 an hour of shadow cost (at most once an hour), an operation's breaker opens or closes, and at the day's first overrun: the server posts a message in `general` as the `admin` user (created if need be) that mentions every user with the `admin` role (up to `wakesPerMessage`) and pushes it to them without the usual wait, attended or not, past the coalescing window and the push allowances (`notifyTrigger` in `src/notify.ts`); a mute or `dnd` still silences its push. Its storage work is charged but never refused (`Store.alert`). The change is made first and the notice after; a notice that fails is only logged (`trigger_notice_failed`). Lifts are told as well as stops. The edge stop blocks public requests only, not the guard's call to the object or its pushes.

Compute retry delay from the limiting window where known; when multiple limits apply, use the longest applicable delay. Capacity/storage retries may use a documented backoff estimate, not a false guarantee of future availability. Persist an optional operator-configured admission-off flag; it must not require migrating or deleting the object.

For a permanent policy cap with no automatic replenishment, such as the identity or thread-room ceiling, use `denied` with an explanatory reason such as `registration_closed` or `thread_limit`; do not induce endless retries with an invented reset time. The operator can raise a policy ceiling only after reassessing the resource budget.

Keep UI messages concrete: "Guest posting limit reached", "Daily posting limit reached for the server", "Daily history limit reached for the server", or "Demo capacity reached", naming the limit without its amount, rate or delay. No billing/SQL details in normal user flows. Do not silently drop a successful write, alter user content, or hide an error as success.

Support a standalone `ALLOWED_ORIGINS = "*"` to admit every guest origin, including opaque origins. Exact allowlist deployments reject unexpected browser origins before upgrade. Require explicit exact RP origins for WebAuthn even under wildcard guest admission; advertise WebAuthn only to connections from those origins. Non-browser clients with no Origin may use the public protocol subject to the same quotas; origin checking is not bot authentication. Reuse the existing CommonMark sanitization and iframe restrictions. No backend URL fetching from embeds. Secrets never enter logs, public status responses, or source control.

Limit observability to bounded structured events and counters: operation category, accepted/rejected reason, daily resource reservations/actuals, active sockets, database bytes, oldest retained commit, floor/head, cleanup backlog, and alarm failures. Sample repetitive rejection logs and never persist request bodies, passkey challenges, or raw IPs to analytics.

- Forward/backward inclusive bounds, numeric ordering, byte-limited contiguous pages spanning every record kind, exact more/first/last behavior, empty ranges, and unknown/empty rooms.

Empty filtered pages retain the room-wide non-null boundary when history remains. Both fields are captured with every page. No accidental reset to zero or giant integer/string comparison bug.

### Auth and abuse controls

- Guest sixth mutation within 60 seconds fails across tabs/reconnects; five can be accepted when timestamps permit. Test the token bucket's drain at the minute rate explicitly (section 6).
- Registered twenty-first mutation fails; several credentials at one IP cannot exceed aggregate IP limits. Failed/unverified WebAuthn cannot raise a tier.
- IPv4, mapped IPv6, equivalent textual forms, /64 and /56 rotation, spoofed forwarding fields, and missing trusted metadata behave as specified.
- WebAuthn wrong challenge, replay, expired challenge, wrong connection/action/origin/RP, bad signature, missing UV, duplicate credential, and unsupported oversized metadata are rejected.
- Registration races enforce global/IP/count limits; existing passkey login works when registration is full. Real browser or virtual-authenticator end-to-end registration/login complements verifier unit fixtures.
- Frame, connection, auth, history, registration, global posting, and byte/depth limits are independent and survive hibernation/restart as applicable.
- Unicode byte boundaries, escaped JSON, many tiny fields, binary input, invalid JSON, notifications, and oversized WebSocket messages cause bounded processing and correct close/error behavior.
- `ping` and `activity` with an `id` are never answered, even with invalid params, a too-deep body, or at the server-wide frame limit (section 4, Framing, ordering, and errors).
- The `status` request, attendance and the idle limit: every rule of section 4.4, Status and Attendance, including that nothing in a refused request changes, that a connection that never sends `idle` stays attended, and that idle changes need no SQL (`test/presence.test.ts`, `test/presence.integration.test.ts`).
- Mutes and the chosen status: every rule of section 4.4, Mute and Chosen status, including the snapshot after each sign-in and none after a non-sign-in `auth`, the shared `mutesPerUserMinute`, the room-mute cap, `dnd` silencing pushes, and `/rename` and `/purge` (`test/push.integration.test.ts`).
- User status: the visibility table, `seen` and its 10-minute granularity, coalescing and the offline grace, waiting changes surviving eviction, the post-sign-in snapshot, `/toggle presence`, an invisible user never shown connected, zero SQL for announcing, and member listings within their reservation at their worst (section 4.4, User status; `test/presence.test.ts`, `test/presence.integration.test.ts`). The sweep never closes the socket whose frame started it; the timer is armed at most a minute ahead and only with a signed-in connection.
- Push: registration checks, per-user registrations and `push_id`, wake candidates and scopes, the wait, held wakes, the claim and its allowances, the payload fallback within 2048 bytes, removal of gone registrations one row at a time (50 users sharing an endpoint, within the reservation), `PUSH_HOSTS` rechecked before each push, and `/rename` and `/purge` (section 4.4; `test/push.integration.test.ts`). Encryption reproduces RFC 8291's test vector (`test/webpush.test.ts`).
- Exhaustion cannot be bypassed by deleting cookies, changing request IDs, reconnecting, upgrading guest auth, or client-supplied claims. Unique denied identities do not grow tables indefinitely.

### Capacity, accounting, and lifecycle

- Measure rows read/written per operation with the actual indexes, including quota writes, auth, alarms, failure paths, and deletion. Produce a cost table and test every claimed upper bound.
- Exercise at least three simulated UTC days: accepted traffic plus previous-day cleanup, midnight double bursts, worst-case snapshots, frequent edits, reconnect/history load, and invalid traffic. A retention window spans more than one daily posting allowance (two for 24–25 hours, eight for 7 days); never assume it contains at most one day's post ceiling of records.

- Demonstrate pressure control at the hard storage target (1 GiB; Free: 128 MiB) and SQLite page reuse under repeated delete/reinsert cycles. No unmetered VACUUM/DDL/full scan or accidental account-wide delete.
- Hibernation wake restores socket auth/challenges and budget authority without reannouncing sessions, losing IP counters, resetting IDs, storing history in attachments, or losing a status change still to be announced.
- Saturate 100 connections and maximum allowed fan-out; bounded queues and recovery buffers prevent memory growth. Validate slow/disconnected consumers without relying on an undocumented bufferedAmount API.
- Alarm scheduling handles simultaneous auth deadlines and cleanup, at-least-once retries, and retry exhaustion; no interval prevents idle hibernation.
- Constructor/redeploy never erases budgets or performs recurring schema writes. Platform failures produce controlled closure/backoff rather than retry storms.

Use tiny configured quotas for deterministic exhaustion tests and a separate calibrated load scenario for realistic defaults. Do not spend production free-tier quotas on exhaustive CI load tests. A local dry run is not proof of production billing; report measured assumptions and remaining platform-specific checks honestly.
