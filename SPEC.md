# Apron public demo server on Cloudflare Workers

Date: 2026-09-20
Status: Implementation specification
Target: https://github.com/shazow/apron
Protocol: https://github.com/shazow/apron/blob/main/PROTOCOL.md
Protocol reference reviewed: protocol version 7, the repository's `PROTOCOL.md`.

## 1. Objective and instructions to the coding harness

Build a usable, publicly accessible Apron demo backend using native Cloudflare Workers, one SQLite-backed Durable Object (DO), and hibernating WebSockets. Support guest use and passkey authentication, bounded posting and history, and graceful resource exhaustion. The demo runs on Workers Paid ($5/month) within its included usage, and must still run on the actual Workers Free plan without enabling paid services when its free budgets are selected (`src/plans/free.ts`).

Read the repository's `AGENTS.md`, existing code, package-manager configuration, and `PROTOCOL.md` before implementing. Reuse existing client/protocol utilities where appropriate. Compare the current protocol with the reference above; preserve its mandatory behavior and document material differences. This specification defines deployment policies within the base chat protocol.

Implement the backend, the minimal Apron client changes required for passkeys and rolling-history recovery, tests, configuration, and operating documentation. Keep unrelated frontend work out of scope. If the frontend is in another repository, provide a concrete patch/adapter and integration instructions rather than silently omitting the client requirements. Prepare a deployable result; do not deploy, switch billing plans, or create paid resources merely to complete this implementation task.

Use MUST for required behavior and SHOULD for preferences. Centralize all limits in validated configuration with the defaults below. Do not silently increase limits to make tests pass.

### Required capabilities

- Protocol v7 core: server announcement with liveness `ping` and a sign-in `welcome`, authentication that finishes before any later frame on its connection, the default room, creation and delivery of flat message snapshots to the rooms' members (the sender's broadcast before its result), framing, errors, one server-wide log ID sequence.
- `history`: complete record snapshots of every kind (room records, message snapshots, reaction sets, registered users' memberships), correct pagination and live/recovery ordering per room.
- `edit`: owner-authorized replacement, deletion, restoration, and moves between rooms of retained messages.
- `rooms`: rooms by request (`room_list`, `room_update`); thread rooms (rooms with `parent_room_id`) created and edited by participants with `room_set`, each with an optional Markdown `description`; `room_join`/`room_leave` for `general` and threads, with deliveries only to joined rooms (a thread's messages to its members only), and with another user's `user_id` for admins and bot owners (section 4). No room is private: a creation with `private: true` is `unsupported`. Registered users' joins and leaves are logged `membership` records; guests' are not (section 4). The permanent `general` room is the only top-level room.
- `reactions`: per-user emoji sets on messages.
- `activity`: implemented; on by default with the Workers Paid budgets and off with the Free ones (`ACTIVITY` overrides; advertised when on): typing only, relayed to the room's members and never stored, at most 10 relays per user per minute (section 4.2). Read cursors are neither kept nor relayed. Attendance for push is `status` (section 4.4), not part of `activity`.
- `room_list`: joined rooms and rooms to join, by the protocol's `filter`, with `members` and `users` on request.
- System identities use protocol v7's `~` prefix: notices come from `~private`, sent to one connection only; no user is given a `user_id` starting with `~`. Current user objects carry `roles` (`admin`, `bot`) for display (section 5, Admins).
- `command`: `/help`, answered with a `~private` notice, `/invite-bot` for registered users (section 5, Bots), `/passkeys` for them too (section 5, WebAuthn), `/avatar` with uploads (section 4.3), and `/admin`, `/role`, `/kick`, `/rename`, `/invite-token`, `/invite`, `/purge`, `/toggle` and `/status` for admins (section 5, Admins).
- `embed:upload` with the Workers Paid budgets: registered users attach images to messages and set avatars, stored in R2 and served from its public bucket domain (section 4.3).
- Push (`server.push`, kind `webpush` only) where VAPID keys are configured: registered users register browser push subscriptions, and a new message that mentions them or replies to them wakes them, by the scopes each registration chose, when none of their connections is attended and they have not muted (section 4.4).
- `status` where push is configured (advertised with it): the user `status` chosen with `me` (`online`, `""` for none, `dnd`, `invisible`), the `status` request's `idle`, which decides pushes, and `mute`, everywhere or in one room and its threads, which stops them (section 4.4). With presence on, others see each user's status, and the `server` frame lists the optional values in `server.status` (`["dnd", "invisible"]`). Presence is on by default with both plans' budgets (`PRESENCE` overrides, admins `/toggle presence`): connected users' status comes from their connections, and a user without one shows `offline`, or `""` when they chose none. A timed mute is cut to a year, which PROTOCOL.md §4.11 allows.
- Guest authentication (`guest`), read-only unless `GUEST_POSTING=true`; verified WebAuthn registration/login; bot tokens (`token`).
- Persistent request deduplication for mutating operations.
- Rolling history, using the same room ID indefinitely: 7 days with daily cleanup on Workers Paid, 24 hours with hourly cleanup on Workers Free.
- Base-protocol history availability boundaries and client recovery support.
- Enforced application budgets, including cleanup, auth, and quota bookkeeping.

### Non-goals

No public workspace creation, top-level room creation, private rooms, federation, multiplexing proxy, a presence service beyond `status` (no last-seen times, no status text), read cursors, non-image uploads, streams (`embed:stream`), the `relay` push kind, push wake scopes other than `mentions` and `replies` (no `private`, `joined` or `badge`), email (including the `email` sign-in scheme, protocol §4.10: the demo has no way to send mail), bearer-token rotation, external URL previews, outbound bots, RTC, arbitrary search, FTS, or third-party analytics. Do not advertise unsupported capabilities. Passkeys do not establish one-human-one-account or solve Sybil resistance.

## 2. User scenarios

1. A visitor opens the public demo, connects, authenticates as a guest, and reads recent history without signup; posting, reacting, and starting threads take a passkey sign-in.
2. Several anonymous tabs behind one IP share the five-posts-per-minute allowance; opening another socket does not reset it.
3. A visitor creates a passkey or signs in with one. Successful authentication grants the registered allowance of twenty posts per minute, subject to IP and global limits.
4. A user reconnects after losing a mutation reply. A retry with the same request ID and authenticated identity returns a result reflecting the current state without another mutation or broadcast.
5. A connected client watches a room while another client loads history. Neither misses entries at the history/live boundary.
6. A user returns after more than a day. The client notices the retention boundary, clears stale recovery state, and rebuilds the available room view.
7. An old message edited within the retained window remains recoverable from its complete recent snapshot even after its creation record is purged.
8. A bot floods requests or creates identities. Per-principal controls and global budgets reject work without unbounded database, memory, or object creation.
9. A resource budget runs out. Posting, history, registration, or admission becomes unavailable as appropriate; accepted messages remain recoverable while resources permit.
10. The object hibernates, wakes, restarts, or is redeployed. Identity, room sequencing, retention boundaries, quotas, and deduplication remain correct; clients can reconnect when necessary.

## 3. Deployment and architecture

Use TypeScript, Wrangler, the native `DurableObject` base class from `cloudflare:workers`, and embedded SQLite. Follow the repository's tooling; pin resolved dependencies and a tested compatibility date. Prefer a small dependency surface and a maintained Workers-compatible WebAuthn verifier instead of handwritten cryptographic verification.

| Component | Responsibility |
| --- | --- |
| Entry Worker | Validate `/` and `/ws` upgrade requests, configured guest origin policy, route/method/body bounds, derive trusted IP metadata, apply cheap preliminary admission controls, forward to the fixed DO |
| `ApronDemoServer` DO | Own sockets, authenticate, authorize, sequence protocol operations, enforce budgets, persist state, serve history, broadcast, run cleanup |
| Embedded SQLite | Authoritative room records, the server-wide record log, current message and reaction state, credentials, deduplication, budgets, rate-limit state, maintenance progress |
| Existing Apron frontend | Guest access, passkey UI, retry/backoff, retention-aware recovery and concise demo status |

Exactly one production object is reachable, e.g. `env.DEMO.getByName("public-demo-v1")`. Never derive its name from an untrusted URL, room, user, or query parameter. There is one permanent room, `general`, displayed as General. Room IDs and the last log ID do not reset on cleanup or at midnight.

Use `new_sqlite_classes` for the initial Wrangler migration. Do not add D1, Workers KV, Queues, or a separate quota DO. Test/staging namespaces count toward account usage if deployed; do not assume an independent free allowance.

Return cheap 404/405 responses for unrelated routes without invoking the DO. Serve the UI as static assets where the repository supports it. No polling endpoint may issue unbounded DO calls. Administrative metrics, if exposed, require authenticated operator access and contain aggregates only.

Cloudflare recommends the hibernation API for WebSocket servers: [WebSocket guidance](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

### Socket lifecycle

- Accept with `ctx.acceptWebSocket(server)`, not `server.accept()`.
- Implement `webSocketMessage`, `webSocketClose`, and `webSocketError`.
- Immediately send the protocol `server` announcement, before authentication.
- Store a versioned, bounded attachment containing connection ID, trusted IP key, auth identity/tier, pending challenge metadata, and any connection-local limiter leases. Re-serialize after changes.
- Keep attachments comfortably below the platform's 16 KiB maximum; do not put message history or credentials into them.
- Reconstruct connection indexes through `ctx.getWebSockets()` and attachments after hibernation. Check socket state before sending. Reconstructed indexes are caches, never durable authority.
- Do not re-send initial announcements or repeat auth just because the constructor runs after hibernation. Actual reconnects authenticate again.
- The runtime cannot send WebSocket pings, so a peer that vanishes without a close frame (sleep, a network change) would stay connected until the edge gives up on it. The server frame advertises protocol liveness instead (`server.ping`, 45 seconds, [PROTOCOL.md §1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#1-transport--framing)): clients send the frame `{"method":"ping"}`, byte for byte, at that interval, and `setWebSocketAutoResponse` answers `{"method":"pong"}` without waking the object, before authentication too, so it spends no frame budget. A `ping` notification with other spacing reaches the handler and is answered there, as an ordinary frame. A connection that has pinged and then sent neither a ping nor any frame for `ping_timeout_seconds` (150) is stale: it is closed with 1001 before `members` are listed and before admission, and does not count against its IP's connection limits. A connection that never pinged is never judged stale. No permanent `setInterval` or `setTimeout`, and no alarm for this. The only timer is the user status one (section 4.4, User status): one-shot, armed only while a status change waits to be announced and a connection would be told, at most a minute ahead.
- Share one DO alarm scheduler between auth deadlines, cleanup, and maintenance retries. Always schedule the earliest outstanding task; cleanup scheduling must not overwrite an earlier auth deadline.
- A closing socket may remain visible to the runtime; do not let it receive broadcasts or grant extra admission while its close is pending.

API reference: [Durable Object state](https://developers.cloudflare.com/durable-objects/api/state/).

## 4. Feature and protocol contract

An illustrative initial announcement is:

```json
{"method":"server","params":{"apron":7,"agent":"apron-cloudflare-demo/7","capabilities":["history","edit","rooms","reactions","command","activity","embed:upload"],"auth":["webauthn","token","guest"],"signup":["webauthn","token"],"welcome":"**Apron public demo.** Guests can read along. **Create a passkey** to post, react, and start threads; it signs you in on your next visit too. An admin's invite token also creates an account; add a passkey once you're in, so you can sign in again without it. Bots sign in with a token their owner gets from `/invite-bot`. Messages are kept for 7 days.","ping":45,"ext":{"demo":{"retention_seconds":604800,"cleanup_seconds":86400,"max_frame_bytes":16384,"max_message_text_bytes":4096,"max_snapshot_bytes":8192,"guest_posts_per_minute":5,"registered_posts_per_minute":20,"guest_posting":false,"server_frames_per_minute":600,"room_list_per_minute":6,"room_list_members":200,"read_cursors":false}}}}
```

The frame carries the protocol version as `apron` (7), the implementation string as `agent`, and `capabilities` ([PROTOCOL.md §3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#31-server-frame)), and only those names: no `protocol`, `name`, or `caps`. `auth` may carry `agent`, the client's implementation string for debugging; the server accepts and ignores it, like any unknown field (such as a pre-release `client`).

`welcome` is the Markdown the client shows on its sign-in screen ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication)): how guests, passkeys, and bot tokens fit together, and the retention, worded for what the connection can sign in with like `auth` (connections not offered passkeys are pointed at the demo's own site, bot tokens, and admins' invite tokens). `email` is never advertised. `signup` lists the schemes that create an account ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication)): `webauthn` (a passkey registration) where passkeys are offered, and `token`, which creates an account only with an admin's sign-up invite (`/invite`, section 5, Admins); every other token signs in to an existing user. `guest` is listed only in `auth`: a guest is a throwaway identity for one connection, not an account. With presence on, `status` lists the optional user statuses `me` accepts, `["dnd", "invisible"]` ([PROTOCOL.md §3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#31-server-frame), §4.11; section 4.4, Status). `ext.demo` is additive server-announcement policy metadata in the standard `ext` object. Authentication uses the canonical `webauthn` scheme in protocol [§4.9](https://github.com/shazow/apron/blob/main/PROTOCOL.md#49-webauthn-authentication), without an extension flag. Every later `server` announcement is a full replacement, including auth, capabilities, and policy metadata. Temporary throttling does not mean a capability is unimplemented.

History availability is part of the base protocol's `history` capability, with no extension negotiation. Use `latest_log_id` and nullable `history_log_id` in room records (`room_list`, `room_update`) and history results, following protocol [section 3.4](https://github.com/shazow/apron/blob/main/PROTOCOL.md#34-rooms) and [§4.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#41-history). Both are per room.

After final authentication, reply with `result.you` (`user_id` and `name`, and `avatar` and `roles` where the user has them; the internal quota tier is private). The client lists its joined rooms with `room_list` (`filter: "joined"`), and live delivery for them starts with the auth result. `auth` is a barrier ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication)): each connection's frames are processed one at a time in arrival order, through an in-memory per-connection queue, because the Durable Object runtime delivers further `webSocketMessage` events while a handler awaits (WebAuthn verification, key-value session reads). Requests pipelined behind `auth`, such as `room_list` and `history`, therefore run with the connection's authentication as the `auth` left it: as the new identity after a success, and as before after an `auth` that authenticated nothing (a failure, or a WebAuthn `begin` step), so on a connection not yet signed in they are `denied`, and on a guest's connection they run as the guest. A `user_id` requested in `auth` is not honored, nor a `name` except in a passkey registration's `begin` (below): guests get `guest_<n>` from a server-wide counter, never reissued, and the name `Guest <n>`, and registered identities come from the verified credential or session. Do not send room records to unauthenticated sockets.

### Framing, ordering, and errors

- Accept the minimal and JSON-RPC 2.0 envelopes. One text message contains exactly one object, not a batch array. Reject binary application messages.
- IDs on the wire are strings. Errors not tied to a request (parse errors, invalid envelopes whose `id` cannot be determined) omit `id`.
- Unknown request methods receive `unsupported`; unknown notifications are ignored. Valid notifications never receive result or error replies, but successful mutation notifications still cause broadcasts.
- `ping` and `activity` are only notifications in the protocol, so an `id` on one is ignored (§1): it is handled as the notification and never answered with a result or an error, even when its params are invalid (not an object, or past the JSON depth or node limits), its `id` is not a bounded string, or the server-wide frame limit drops it. The method decides this, so it is known before any params check. Each such fault still counts as a policy violation. A `ping` with an `id` still gets its `pong`, a notification.
- A client's `status` is a request (§4.11, since shazow/apron 6bda48b); the server's `status` stays a notification. A `status` without an `id` is a notification the protocol does not define for clients, so it is ignored like any unknown notification (§1): no reply, and nothing changes. Ignoring it, rather than applying it, keeps one rule (a change is made only where its result can say whether it was) and keeps a client written for the earlier notification from believing an unanswered change applied; an error is impossible without an `id`.
- Ignore unknown envelope fields. Unknown top-level message and room fields are dropped (protocol [section 1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#1-transport--framing)); extension data travels in `ext`, which is stored and returned unchanged. Server fields are read-only ([PROTOCOL.md §2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#2-identifiers)): a client-supplied `from`, `log_id`, or a room's delivery fields are ignored, never applied. Request `id`s are strings only; any other `id` is `invalid_request`.
- Process frames in arrival order per socket, including auth and later pipelined writes. External awaits and WebAuthn verification must not allow overtaking. Bound pending work instead of accumulating unlimited promises.
- Coordinate mutation commit and broadcast scheduling globally within this DO. No live room log ID may be sent after a newer ID on the same connection.
- Notifications a request causes on the requesting connection come before its result ([PROTOCOL.md §1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#1-transport--framing)): the sender's `message` and `reactions` broadcasts, the `room_update` of `room_join`, `room_leave` and `room_set` (with its `memberships`), a registration's logged joins before its `auth` result, and a command's `~private` reply.
- Commit durable state before a success becomes externally observable. Use documented storage/output-gate behavior; do not disable it. A failed send to one socket must not roll back an accepted mutation or skip all remaining recipients.
- On an ambiguous post-commit failure, preserve the recorded result and force affected recovery/reconnection rather than continuing a socket with an unexplained gap. Persistent exactly-once mutation effects within the deduplication window do not imply exactly-once network delivery.

| Error | Code | Use |
| --- | ---: | --- |
| parse_error | -32700 | Invalid JSON |
| invalid_request | -32600 | Invalid envelope |
| unsupported | -32601 | Unimplemented request |
| invalid_params | -32602 | Invalid fields, conflicting duplicate, nonexistent/expired message, unknown room or parent room, reaction caps |
| internal_error | -32603 | Unexpected failure, with sanitized text |
| denied | -32001 | Authentication or ownership failure |
| retry_after | -32002 | Temporary resource/rate limit; integer `data.retry_after` in seconds (rounded up, at least 1) |
| too_large | -32003 | Valid identifiable request exceeds a payload policy |

For oversized frames, reject before parsing. If an ID cannot be safely obtained, close with 1009 rather than parsing an arbitrarily large payload just to return an error. Close binary input with 1003 and persistent policy violations with 1008. Use HTTP 429/503 before upgrade where applicable, with an appropriate Retry-After. Do not turn capacity limits into fabricated malformed-request errors.

### Messages, edits, rooms, and reactions

- Every record (room record, message snapshot, reaction set, membership) receives the next `log_id = max(now_ms, last_log_id + 1)` from one server-wide sequence, checked below `2^53`; use integer columns and decimal strings on the wire. A new message's `message_id` equals its creation `log_id`, so it is unique across rooms. Room IDs of threads are their creation `log_id`.
- Maintain `last_log_id` even after the entire log has expired. Clock rollback must not reuse IDs.
- Store each accepted record as a complete authoritative snapshot. Message notifications and history `messages` are the same flat object: `message_id`, `log_id`, `room_id`, `from`, `body`, optional `reply_to` (bare `{message_id}`), `deleted`, and `ext`. `body.format` defaults to `plain`. Deliver to every authenticated connection whose user has joined a room the record belongs to, including the sender's; a record is sent once per connection even when it belongs to two rooms. A thread's records go to the thread's members only; its parent's members receive only its room record, as `room_update` `updated`, when it is created or saved. Every room is visible to every client, so anyone may page any room's history, and posting does not require joining: a poster who has not joined gets only the result.
- Only the original author may replace/delete/restore/move their retained message. Preserve immutable author/ID fields. A save replaces every client field (`room_id`, `body`, `reply_to`, `deleted`, `ext`); it is not a patch/merge. Tombstones omit `body`. A request without `room_id` (a new message or a save) is in the default room, `general`.
- `reply_to` names an existing, retained message other than the message itself, in any room; otherwise `invalid_params`. A save that resubmits its current `reply_to` unchanged is accepted even after the target expires, so old replies stay editable.
- A save with a different `room_id` moves the message: the destination must exist, and the move snapshot belongs to both rooms' logs and history and carries `prev_room_id`, the source room, whose log holds its earlier snapshots. When the message has retained reactions, the same atomic commit then logs one reaction record in the destination carrying every non-empty set.
- Guest authors own messages under their assigned guest identity; passkey authentication does not automatically transfer ownership of earlier guest messages.
- Rooms (cap `rooms`): the public demo permits creating threads only. `room_set` without `room_id` must name an existing top-level `parent_room_id` (`general`); a top-level room request or a nested thread is `denied`, an unknown parent is `invalid_params`. Creating a thread joins its creator: the creator's connections get one `room_update` with `joined` (the creator as its only member), for a registered creator the creator's logged membership in `memberships` (its `log_id` already the room's `latest_log_id`), and `users`; the parent's other members get `updated`; all before the `{room_id}` result. Any participant may save a thread room's client fields (`title`, `description`, `ext`); `general` cannot be edited. A save replaces all client fields except `parent_room_id` and `private`, which this server fixes (a submitted value is ignored, and an omitted `private` is kept, as [PROTOCOL.md §4.3.4](https://github.com/shazow/apron/blob/main/PROTOCOL.md#434-creating-and-editing) requires; here that is always not private); the server supplies the title `Thread` when none is given so clients ignoring `parent_room_id` still render it. `description` is a string, Markdown by convention ([PROTOCOL.md §3.4](https://github.com/shazow/apron/blob/main/PROTOCOL.md#34-rooms)); an empty or blank one is none. A save goes as `room_update` `updated` to the members of the thread and of its parent, and to the saver. A v6 `intro_message` is an unknown field and dropped. Every room creation and save is a logged record in the room's own log.
- Private rooms ([PROTOCOL.md §4.3.4](https://github.com/shazow/apron/blob/main/PROTOCOL.md#434-creating-and-editing)) are not kept: every room is visible to every client and its history readable without joining, which the listing, history, move, reply, cleanup, and guest-membership paths rely on. `private` must be a boolean (else `invalid_params`); a creation with `private: true` is `unsupported`, as the protocol requires of a server without private rooms, and no room record carries `private`.
- Membership ([PROTOCOL.md §4.3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#432-membership)): a new guest or registered identity has joined `general`. `room_join` and `room_leave` take a known `room_id` (else `invalid_params`), work for `general` and threads alike, and return `{}` after the notifications they cause. Joining a joined room logs nothing and re-sends `room_update` `joined` to that connection; leaving a room not joined changes nothing. See "Memberships" below for what is logged.
- Both also take a `user_id` (a string, else `invalid_params`; one's own is an ordinary join or leave) to add or remove someone else. Policy: an admin may for anyone, and a registered user (not a bot) for their own bot, `bot_<user_id>`, say to have it keep a thread's `description` current; anyone else is `denied`. `room_join` adds registered users only (a guest's rooms live in its connections, and a read-only guest stays in `general`): a guest or unknown `user_id` is `invalid_params`. The join is stored and logged like the user's own, charged to the adder's posting limits: the room's other members get it in `room_update` `memberships`, and the added user's connections get one `room_update` with `joined` and that `memberships`. Adding a member changes nothing. `room_leave` with a `user_id` is `/kick` (section 5, Admins) without its notice, including for connected guests: the removed user's connections get `room_update` `left`, with the logged membership in `memberships` for a registered user; removing someone not in the room changes nothing, and a `user_id` no identity or connection has is `invalid_params`.
- Allow at most 100 thread rooms, each with at most 2 KiB of serialized client fields. All room creation and saves consume posting and resource budgets. No implicit room creation. A thread room whose entire log (creation record included) has expired is removed at cleanup; its members leave it and are told with `room_update` `left`, releasing its slot; deny further creation while the ceiling is full.
- Reactions (cap `reactions`): a request sets the caller's complete emoji set on one retained message; `[]` clears it and duplicates collapse. Emoji are non-empty strings of at most 64 UTF-8 bytes without control characters, at most 8 distinct per user per message, and at most 32 reacting users per message (calibrated ceilings 16 and 64). A set that equals the current one is accepted without a new record. Non-empty sets on a tombstone are `invalid_params`; clearing is allowed. Each change is a logged record in the message's current room. Reactions are mutations: they share the posting quotas and request deduplication below.
- A new message with empty text and no embeds is neither logged, charged, nor delivered; its result is `{}` (an unknown room is still `invalid_params`). A save that would leave a message empty is `invalid_params` by local policy; delete it instead. Accept plain and Markdown formats. `body.mentions`, when present, is an array of non-empty `user_id` strings (duplicates collapse) stored as sent; the server never reads mentions out of `text`. Limit embeds to four within all byte budgets; store accepted URLs/content without backend fetching or rendering. Unknown embed kinds remain opaque. A client-built `og` keeps only its `title`, `description`, and `site_name` as bounded single-line text; media (unless the off-by-default `ogRemoteMedia` store setting keeps remote http(s) media) and other properties are dropped (§4.6.1 lets the server keep, replace, or drop it). Client sanitization/sandboxing remains mandatory under the base protocol.
- `me` merges into the profile ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)): a given field replaces its value, an omitted one is unchanged, and an empty one removes it. `roles` is not settable and is ignored. It changes the display name as a bounded, rate-limited identity operation for registered users; `name: ""` removes it (clients fall back to `user_id`) and is announced as `name: ""`, and guests keep their assigned name (`denied`). The demo keeps no profile `ext`, and avatars come only from `/avatar` uploads (section 4.3): `me` with `avatar: ""` removes a registered user's avatar, and other `avatar` values and `ext` are type-checked and ignored. No avatar downloads from other servers or automatic link previews.
- `user` notifications carry identity changes only ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)), as current objects with the user's `roles`. A rename sends `you` to the user's other connections and `new` to the connections of users who share a room with the user; so do `/admin` and `/role`, role changes. Signing in with a passkey or token on a guest's connection sends `new` with `old` (the retired guest) to those who shared a room with either. Joins and leaves are never `user` notifications. History pages carry no `users`: records keep the user objects they were logged with.
- `command` (cap `command`, [PROTOCOL.md §4.8](https://github.com/shazow/apron/blob/main/PROTOCOL.md#48-command)): `/help` answers `{}` and a `~private` notice listing the commands the sender may run, delivered to that connection only, never logged, with no `message_id` or `log_id`. `/invite-bot` (registered users other than bots; others get `denied`) is section 5, Bots, `/avatar` (the same users, with uploads) is section 4.3, and `/admin`, `/role`, `/kick`, `/rename`, `/invite-token`, `/invite`, `/purge`, `/toggle` and `/status` (admins only; others get `denied`) are section 5, Admins. Other commands are `invalid_params` without counting as policy violations, as are an admin command's usage and `user_id` errors. `/help` costs a frame and no SQL beyond a cached room check, plus, once per object wake, the `_meta` read of the roles (section 5, Admins), to list the admin commands to admins.
- Message snapshots carry `prev_log_id` when an earlier record for the same key is still stored, and a move's snapshot also `prev_room_id`. Reaction sets and memberships carry neither ([PROTOCOL.md §2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#2-identifiers)); room records carry no `prev_log_id` (it is optional). The links are added after the snapshot size check. Deleted messages are not redacted.
- `room_list` (cap `rooms`, [PROTOCOL.md §4.3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#431-listing)) returns room records with delivery fields in `joined` (the user's rooms, never truncated) and `not_joined` (visible rooms not joined: `general` when left, or with `parent_room_id` that room's threads), each most recently active first. `filter` (`joined`, `not_joined`, or `all`, the default; anything else is `invalid_params`) leaves out the other array, and an array it asks for is present even when empty. It takes `parent_room_id` and `room_id` (one room, in the array its membership selects; unknown is `invalid_params`). With `members: true`, each listed room carries `members`, bare `{user_id}` objects in `user_id` order, and `member_count` when those leave some out (see "Memberships"), and the result `users`, each member's current `{user_id, name}` (with `avatar` and `roles` where they apply) once, in `user_id` order, present even when empty; without it, neither. `latest_log_id` is validated and ignored (see "Memberships"). It reads the capped room table under the room-listing reservation, and with `members` each room's stored members, and writes nothing. A listing that would pass the 256 KiB response cap leaves out `members`, `member_count`, and `users`; room records alone stay under it, each room's client fields being at most 2 KiB. Listing unjoined top-level rooms while joined to `general` needs no storage and is not throttled.
- `room_update` `joined` carries the room's record with its `members` (and `member_count`) and the frame's `users`, as a `members: true` listing does.

### Memberships

The protocol logs every membership change, and lets a server keep some out of the log, such as ephemeral guests' ([PROTOCOL.md §4.3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#432-membership)). The demo logs what is durable already and keeps the rest out:

- A registered user's membership is stored (the `memberships` table) and each change is a logged `membership` record in the room's log: `{log_id, room_id, members: [{user: {user_id, name}, joined}]}`, one entry, with the user as a recorded object. Logged changes are `room_join`, `room_leave`, the creator's join when a registered user creates a thread, and each starting room of a new registration (the guest's rooms it replaces, or `general`). A record advances the room's `latest_log_id`, is delivered in `room_update` `memberships` ([PROTOCOL.md §4.3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#433-updates); there is no `membership` notification) to the room's members before and after the change, and is returned in `history`'s `memberships` array. The joining user's connections get it in the same `room_update` as their `joined`, and the leaving user's in the same one as their `left`; the room's other members get `memberships` alone, one frame each. The joins and leaves count as posts; an unchanged join or leave writes nothing.
- A guest's memberships live in its connection attachment, like the guest identity, and are not logged: no `membership` record is sent for them and they cost no writes. Logging them would cost a durable write per guest join (every guest joins `general` at `auth`) and per leave of each room when the connection closes, for identities that end with their connection. Clients learn guest members from `room_list` and `room_update`.
- Because guest joins and leaves are not in the log, `room_list` ignores `latest_log_id` and never sends `left`: its result is a full listing, which the protocol lets such a server send. A delta could miss a guest's join or leave.
- `members` lists every connected member, guests included, and the registered members stored with the room in `user_id` order, at most `room_list_members` (100) per room. A room with more registered members lists the first `room_list_members` by `user_id` besides those connected. This deviates from [PROTOCOL.md §4.3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#431-listing), which says a truncating server lists the most recently active members: the stored page is ordered by `user_id`, the membership table's primary key, because ordering by activity would need a last-active time on every membership, one more written row on each of a member's posts, and an index to read it by, against the write budget that is this demo's scarcest. Connected members, the ones most likely to be active, are always listed, which narrows the gap; an offline member past the page is learned from messages and memberships, as the protocol says for any truncated list. A registered user whose status hides being connected (`invisible`, or `""`, none) is not listed past the page for being connected, and such a guest, never stored, is not listed (section 4.4, User status). Each listed member costs two indexed reads, and with presence on one more for their chosen status when they have a `user_status` row (section 4.4, User status); a listing is reused, with no reads, for up to a minute until something it read is written. Such a room then carries `member_count`, the number of users who have joined it ([PROTOCOL.md §4.3.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#431-listing)): its stored registered members plus its connected guests, since a guest's membership lasts exactly as long as its connection. Each room row keeps the count of its stored memberships, changed in the same row update that advances the room's head for each logged join and leave (so it writes no extra row), by `/purge`, and by a reset's passkey carry; the listing reads it only for a room whose page of registered members is full. Listing all 101 rooms at that cap reads about 20,200 rows (see [cost report](docs/cost-report.md)).
- Retention discards the log prefix older than a day ([PROTOCOL.md §4.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#41-history)), membership records included. The demo does not append the full-member record the protocol asks for before discarding a prefix that holds memberships: member lists cannot be rebuilt from this server's history anyway, since guest memberships are out of the log, so clients start member lists from `room_list` and `room_update`, whose `members` are current. A full-member record would also re-log every registered member of every room each day, a maintenance cost that grows with the identity count. This is a deviation.
- A thread room removed at cleanup leaves the `rooms` table at once, and its members get `room_update` `left`. Its stored memberships are purged in later bounded cleanup batches from a list of removed rooms in `_meta` (at most 100; no further room is removed while it is full); until then membership reads join `rooms`, so they never see them.

### 4.2 Server-wide minute, activity, and per-type throttles

The whole server processes at most `globalFramesPerMinute` (300) frames in a rolling minute, counted in memory after the per-connection gates and parsing but before any SQL. Over it, a request gets `retry_after` with the seconds until the oldest counted frame leaves the window, and a notification or malformed frame is dropped; the socket stays open and nothing is charged. The default is sized for a spike from 50 connected users, 10 of them active: about 20 frames a minute per active user (posts, reactions, edits, history pages, room lookups), about one per quiet user, and a reconnect wave of one auth and one history page each. It is at least one IP's frame minute, so a single client cannot be starved by its own limits. The window is lost on hibernation, when the object has received nothing to count. It shapes spikes; the daily frame and SQL budgets still bound the day.

`activity` is on by default with the Workers Paid budgets and off with the Free ones; `ACTIVITY` overrides either. When off it is not advertised, and `activity` is ignored. `activity` is only a notification: one sent with an `id` is handled the same way and never answered, on or off (§1). When on: Typing (`typing`, seconds, capped at 30) in a known room (`general` without `room_id`) is relayed to the room's other members' connections as `{room_id, from, typing}` and never stored. `read_message_id` is dropped: the demo keeps no read cursors. Other fields, such as the former `away`, are ignored; neither typing nor a read cursor changes a connection's `status` `idle` (section 4.4). An unknown room drops the update; room existence comes from an in-memory cache refilled by listings, room changes, and one bounded lookup per unknown ID.

Some message types have their own per-user rate, counted across the user's connections in a rolling 60-second window whose events live in connection attachments (so they survive hibernation and need no SQL):

| Type | Default per user per minute | Over the limit |
| --- | ---: | --- |
| `activity` (relayed typing) | 10 | Dropped. The sender's connection gets one `~private` notice per window ([PROTOCOL.md Appendix A.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#a1-system-identities-and-scoped-notices)) saying typing is limited |
| `room_list` | 6 | `retry_after` with the seconds until the oldest counted listing leaves the window. The first `filter: "joined"` listing after each authentication is not counted: it is how a client learns its rooms |
| `push_register` (with push) | 10 (`registersPerUserMinute` in the push policy) | `retry_after`, as for `room_list`; refused registrations count too. Counted on the object per user rather than in connection attachments, so reconnecting does not reset it (lost only when the quiet object hibernates) |
| `status` `mute` and `me` `status` changes (with push) | 6 (`mutesPerUserMinute`), the two together | `retry_after`, and nothing in the request changes (section 4.4, Mute). Counted on the object per user, like `push_register` |
| `status` changes to `idle: true` (with push) | 12 per connection (IDLE_CHANGES_PER_CONNECTION_MINUTE) | `retry_after`, and nothing in the request changes (section 4.4, Attendance); `idle: false` is never refused. A repeat of the current value is not a change and is not counted. Counted in memory by connection, with no SQL |
| User `status` announcements (with presence) | 1 per `statusCoalesceSeconds` (60) for changes the connections cause; a `me` change at once | Not dropped: a change waits, and the latest one goes out when the minute is up (section 4.4, User status) |

The `~private` notice goes to the throttled connection only, is never logged, and carries no `message_id` or `log_id`, so it needs no SQL. Posting quotas continue to cover every logged mutation (`message`, `room_set`, `reactions`, `me`) and a registered user's room joins and leaves.

Every frame is charged to the IP and daily frame budgets before any other work (section 6). Each connection reserves frames in blocks of `frameLease` (10) and spends them from its attachment, so a frame carries a tenth of a reservation's SQL bookkeeping (section 7 allows durable block reservation). A block counts against the IP's frame minute and the daily frame budget when it is reserved, lives only in that connection's attachment so it is never granted twice, and is burned when the connection closes or the UTC day ends. A connection that sends a single frame costs what it did before blocks. Operations that do SQL work still reserve their own cost. Handlers read the attachment after the charge, so none writes back a copy with the block unspent. The frame is parsed before it is charged; parsing is bounded CPU work with no storage.

Internal names such as the `anonymous` quota tier and its `anonymousPosts*` configuration keys refer to guests; wire-visible names use `guest` (`guest_posts_per_minute` in `server.params.ext.demo`).


### 4.3 Uploads and avatars

With the Workers Paid budgets (`uploads` in `src/plans/paid.ts`) and a deployment that sets `MEDIA_ORIGIN`, `PUBLIC_ORIGIN`, the `UPLOAD_SIGNING_KEY` secret and the `MEDIA` R2 binding, the server advertises `embed:upload` and follows [PROTOCOL.md §4.6](https://github.com/shazow/apron/blob/main/PROTOCOL.md#46-embeds-and-avatars):

- Embed identity (§4.6.2): every embed gets an `embed_id`. A save keeps an embed by sending it back with its `embed_id`; one left out is removed; an unknown one is `invalid_params`. An upload keeps its `url` and `og` from the server's record and takes only a new `title` (single line, 256 code points).
- Writes (§4.6.3): a new `{"kind": "upload"}` embed from a registered user (guests and bots of guests cannot upload) is broadcast pending, and the sender's result lists `embeds: [{embed_id, kind, write_url}]` in request order. `write_url` is `PUBLIC_ORIGIN/w/<token>`: an HMAC-signed grant naming the R2 key, the largest body, and a 10-minute expiry, so a retry of the same request gets the same URL. `PUT` the image there with `Content-Length` (any origin; CORS preflight allowed). The entry Worker checks the signature before reading the body, the Durable Object claims the upload so one request writes it, and only PNG, JPEG, GIF and WebP bytes are kept, typed from their signature (never from the sender). The object is stored at `f/<128-bit random id>`, then the message gets a server snapshot with the embed completed: `url` on `MEDIA_ORIGIN` and `og.image` with `url`, `type`, and `width`/`height` when the header gives them. A failed write, or one that never comes within the window plus a minute's grace, publishes the message without the embed; a message left with neither text nor embeds becomes a tombstone. Removing the embed or deleting the message deletes the object.
- Avatars (§4.6.6): `/avatar` with exactly one upload embed returns its `write_url`; when the write finishes, the image (`a/<id>`) becomes the sender's avatar and they get `user` `you`, and users sharing a room `new`. `avatar` is in current objects (`you`, `new`, room `members` and `users`), never in `from`. `me` with `avatar: ""` removes it; other values are declined. A new avatar replaces and deletes the old.
- Limits: 5 MB per image and 256 KB per avatar; 500 uploads a UTC day server-wide and 20 per user (avatars included); live upload bytes, pending writes counted at their largest, at most 5 GB. Past a daily count, `retry_after` until the reset; past the byte cap, `retry_after` of an hour.
- Retention: images live 7 days and avatars 30, matching the bucket's lifecycle rules, and still count as stored for a day after, since R2 deletes them asynchronously. An avatar whose owner signs in during its last week is written again, restarting its 30 days. Messages are kept as long as their images (7 days on Workers Paid); cleanup removes a message up to a day after its image expires, so R2 can delete an image during its message's last day.
- Cost: uploads stay within R2's free tier (10 GB-month, 1 million Class A and 10 million Class B operations a month). At most about 16,000 writes a month, and the byte cap keeps storage at half the free tier. Views are served from Cloudflare's cache on the bucket's custom domain; the budget guard counts R2 operations against their daily and monthly shares and blocks the media host with the server's.

### 4.4 Push

Where the plan has a push policy (`push` in `src/plans/`, both plans) and the deployment sets `VAPID_PUBLIC_KEY`, `VAPID_SUBJECT` and the `VAPID_PRIVATE_KEY` secret ([configuration](docs/configuration.md#push)), the `server` frame carries `push: {"webpush": {"key": "<VAPID public key>"}, "wake": ["mentions", "replies"]}`, the wake scopes this server implements, and the server follows [PROTOCOL.md §4.7](https://github.com/shazow/apron/blob/main/PROTOCOL.md#47-push) for the `webpush` kind only. Without them there is no `push`, and `push_register` and `push_unregister` get the unsupported-method path.

- Registration: `push_register` with `{"kind": "webpush", "url": <endpoint>, "keys": {"p256dh": …, "auth": …}, "push_id": …}`, the browser's `PushSubscription.toJSON()` with `kind` and the optional `push_id` added (`expirationTime` is ignored). `keys` and `push_id` follow [PROTOCOL.md §4.7](https://github.com/shazow/apron/blob/main/PROTOCOL.md#47-push), which defines `webpush`: the VAPID public key as `server.push.webpush.key`, the subscription's `keys.p256dh` and `keys.auth`, and `aes128gcm` payloads. `push_id` is 1 to 64 letters, digits, `_` or `-` the client chooses (else `invalid_params`), stored with the registration and copied unchanged into every push to it. `wake` lists the scopes the registration wakes for: an array of at most 16 strings of at most 64 characters each (else `invalid_params`). Scopes this server does not implement (`private`, `joined`, `ext:` ones) are ignored, so an array of only those, or `[]`, keeps the registration but wakes it for nothing; without `wake` it wakes for `mentions` and `replies`. The scopes are stored as a bitmask in the registration's `wake` column. Any other `kind` (`relay` included) is `invalid_params`. Registered users only, bots included: a guest's identity lasts one connection, so `denied`. At most `registersPerUserMinute` (10) a user across their connections, counted per-type like `room_list` (section 4.2), refused ones included; past it, `retry_after`. `url` is at most 512 bytes (keeping each row small, so registrations from many accounts cannot fill storage) and must be `https`, without credentials or a port, naming a public host without a trailing dot: IP literals (in any spelling the URL parser normalizes), single-label hosts, and `localhost`, `.local`, `.internal`, `.home.arpa` and similar internal suffixes are `invalid_params`. Names are not resolved first; a public name that resolves to a private address is left to the platform, whose outbound fetch does not reach private networks. The host must also be one `PUSH_HOSTS` allows ([configuration](docs/configuration.md#push)), by default the browsers' push services (`fcm.googleapis.com`, `*.push.services.mozilla.com`, `web.push.apple.com`, `*.push.apple.com`, `*.notify.windows.com`); another is `invalid_params` "push service not allowed here". `p256dh` must be an uncompressed P-256 point on the curve and `auth` 16 bytes, both base64url. The endpoint is stored as the URL parser spells it (`new URL(url).href`), so one endpoint has one key whatever its spelling, and `push_unregister` matches it the same way. The result is `{}`.
- Registrations belong to a user: one is identified by `user_id` and `url`, so two users may register the same endpoint, each their own. A user registering a `url` they hold again replaces its keys, `push_id` (a registration without `push_id` removes it) and scopes; an unchanged one (same keys, `push_id` and scopes) registered again within a day writes nothing, so clients registering on every connection refresh it at most daily. A user keeps at most `subscriptionsPerUser` (5); another replaces the one least recently registered. One not registered again for `pushExpiryDays` (7) is skipped by wakes and deleted by cleanup (daily on Workers Paid, hourly on Free), in its bounded batches. `push_unregister` `{url}` removes only the sender's own registration, and answers `{}` for an unknown one (§4.7), a `url` over 512 bytes included, which could never have been registered and is answered without SQL. Registrations live in the `push_subscriptions` table; `/rename` moves them, `push_id` and scopes kept, and `/purge` deletes them. `/passkeys remove` deletes all the user's registrations, so a device that held the removed passkey stops getting their messages (their other devices register again on their next connection), and a new bot token (`/invite-bot`) deletes the bot's.
- Status: with push, the server advertises capability `status` ([PROTOCOL.md §4.11](https://github.com/shazow/apron/blob/main/PROTOCOL.md#411-status)), whether or not presence is on: the user `status` set with `me` (below), and the `status` request, with `idle` for the sending connection and the user's `mute`. `room_id` scopes only `mute`; `idle` applies to the sending connection whatever room it names. With presence on, the `server` frame also carries `status: ["dnd", "invisible"]` (§3.1), the optional values `me` accepts (`online` and `""` are always accepted and not listed), so clients offer both; with presence off it is left out, since nobody would be shown either. `me` still takes and keeps `dnd` and `invisible` with presence off, though `server.status` does not list them then (and `dnd` still silences pushes): a server choice, so that a choice made while presence is on holds across `/toggle presence` instead of being refused or reset, and a client that has none listed simply does not offer them. The frame is sent once per connection, so one opened before a `/toggle presence` keeps the list it got. Unknown fields are ignored. The server replies `{}` once it has applied the request; on an error nothing in it changes (§4.11): every check that can fail comes before any change, and the mute, the only part that can fail in storage, is applied before `idle`. An invalid field (an `idle` that is not a boolean, a `mute` that is not `true`, `false` or a whole number of seconds, with `mute`, a `room_id` that is not a string of 1 to 64 characters; without `mute`, `room_id` is neither checked nor used) is `invalid_params`, a policy violation like any other; a mute of a room that does not exist is `invalid_params` too; past `mutesPerUserMinute` or, for `idle: true`, the idle limit (Attendance) it is `retry_after` with the seconds to wait, and a room mute past the cap, or any guest's `mute`, is `denied` (Mute). Without an `id`, `status` is ignored (section 4, Framing, ordering, and errors). Before sign-in it is `denied` (§3.2), so nothing is kept from before authentication. Without push, `status` is `unsupported` (ignored without an `id`), and `me` ignores `status`. The server never sends `idle`.
- Attendance: `idle` is per connection, kept in the connection attachment, so it survives hibernation. A connection starts attended, with nothing kept from earlier connections (§4.11): its attachment is new, and `status` before sign-in is denied, so nothing sets `idle` before it signs in; a sign-in on a connection keeps the connection's own `idle`. `idle: true` marks the connection unattended; only `idle: false` ends it, and a close removes the connection. Messages, history, `activity` (typing and read cursors) and other requests do not end it. A connection that never sends `idle: true` stays attended for as long as it is open and not stale, however long it sends nothing: the server never infers idleness (§4.11), for wakes and for the status others see. A connection may go idle (`idle: true` when it is attended) at most 12 times a minute (IDLE_CHANGES_PER_CONNECTION_MINUTE, which §4.11 allows: rate limiting `status`, `idle` included); past that the request is `retry_after` and nothing in it changes. `idle: false` is never refused, so a client coming back is always shown attended at once; since each going idle needs a coming back to repeat, the limit bounds both. A repeat of the current value is answered `{}` and not counted. The count is kept in memory by connection, with no SQL, and is lost on hibernation, which only follows quiet. Each change re-derives the user's status from attachments, also with no SQL, and announcements stay coalesced (User status), so the limit bounds the CPU a flipping client can cost; frames are bounded besides by the per-connection frame limit. It is never delivered.
- Chosen status: `me` with `status` (a string, else `invalid_params`) sets the status the user chooses (§3.3, §4.11): `online` (the default), `""` (none, to opt out), `dnd` or `invisible`; any other string is taken as `""`, which §4.11 has servers set for a value they don't support. Guests may choose too. The result's `you` carries the choice, and so does every `you` a connection gets (the `auth` and `me` results, and `user` notifications to the user's own connections), presence on or off; each change is sent to the user's other connections as `user` `{"you": {"user_id", "status"}}`. A registered user's is stored in their `user_status` row (with the unscoped mute; the row goes once both are back to the defaults), so it holds across connections, devices and restarts; a guest's lives on its connection, like the guest. It is read once at sign-in with the mutes and kept on all the user's connections, so deriving what others see needs no SQL. Changes count against `mutesPerUserMinute` together with mutes, once stored; past it, `me` with a changed `status` is `retry_after`, before anything else in the request changes. An unchanged `status`, or one in a `me` that fails, counts nothing. `me` checks everything that can make it invalid (a `name` from a guest or bot, a `name` past the name limits, a non-string field) before the status applies, so an invalid `me` changes nothing. `dnd` silences the user's pushes like the unscoped mute (Wake). What others see of it is in User status below. If the status and mutes cannot be read at sign-in, the sign-in fails (`internal_error`, "sign in again"), before the connection becomes the user's, so it stays as it was and the client can try again at once (a passkey sign-in reads them before it issues its session, so a failed read leaves no session behind): signing in without them would show an invisible user to others as connected and tell the client none of its mutes are in effect, until their next sign-in. `/rename` moves the `user_status` row and `/purge` deletes it.
- Mute: `mute` is the user's, private (others never see it), and `true` (until changed), `false`, or seconds to stay quiet (cut to a year; `0` is `false`). Without `room_id` it silences the user's pushes everywhere; with `room_id`, in that room and its threads, mentions and replies included. The unscoped mute is stored for registered users in their `user_status` row (`mute_until_ms`, the largest safe integer for `true`), and each room's in the `room_mutes` table, keyed by user and room, at most 100 a user (MAX_ROOM_MUTES_PER_USER); both hold across connections, devices and restarts. A room mute needs the room to exist, except to clear it (so a removed thread's mute can still be cleared); past 100, a mute of another room first deletes the user's room mutes that ran out, and is declined if that frees none. A muted user gets no pushes and takes no wake slot. Guests get no pushes, so a mute could change nothing for them: a guest's `mute` is `denied` (§4.11 replies `{}` only once a change applies), and with it the whole request, so a guest's `idle` applies only when sent without `mute`; nothing is kept or sent. Each change goes to every connection of the user, the sending one included, before its result, as a `status` notification with the resulting `mute`: the seconds left (rounded up), `true`, or `false` once it ends or is cleared, with the `room_id` of a room mute (§4.11); an unchanged mute sends nothing. A change refused is no change, and nothing is sent but its error: past `mutesPerUserMinute` it is `retry_after`, a room that does not exist `invalid_params`, and a room mute past the cap `denied`. Only a change the store accepts counts against `mutesPerUserMinute`: a refused one, or one that fails in storage, spends nothing. After every sign-in of a registered user, the connection is sent one `status` for each mute in effect, the unscoped one and each room mute, with the seconds left or `true`, after the `auth` result and before the statuses of others (User status); any scope not sent is unmuted. A sign-in is an `auth` that signs the connection in as a user it isn't already signed in as (§4.11), on every path: passkey registration and login, a passkey session token, and the keyless tokens (bot, admin, invite and sign-up invite); a guest sign-in sends no mutes, since guests have none. An `auth` that only adds a passkey to a connection already signed in, a repeated guest `auth`, and a token `auth` on a connection already signed in (`denied`: switching identity takes a reconnect) are not sign-ins and are followed by neither the mutes nor others' statuses. The unscoped mute's end is read once at sign-in and kept on the user's connections; the room mutes are one range of the user's `room_mutes` rows (at most 100), read at sign-in to be sent, and only when the next of them runs out is kept on the connections. A mute that runs out is sent as `mute: false` to every connection of the user, by the same timer and sweep that announce statuses (User status): the unscoped one from the attachments, with no SQL; room mutes when the attachments say one ran out, by one range read of the user's room mutes that deletes those that ran out, so each is told once. A mute running out within a minute of an event is told on time; a later one at the first event after it (a frame, a connection, a close or an alarm), which may be later still if the object sleeps meanwhile; clients count the seconds down themselves. Room mutes of a user without a connection that ran out stay until they next set a room mute at the cap, or are read and dropped at their sign-in.
- User status (presence): with presence on, others see each user's `status` (§4.11) in current user objects: `users` in `room_list` and `room_update` `joined`, `new` when `/rename` gives a user a new `user_id`, and `user` notifications. Every current user object in `room_list` and `room_update` carries `status`, `offline` and `""` included (§4.11), presence on or off (off, it is `""`; below). A profile change's `new` leaves it out, so clients keep theirs, and recorded objects (`from`, a membership's `user`) never carry it. Others see a user who chose `online` as `online` when a connection is attended (by section 4.4 Attendance's rule), `idle` when connected with none attended, and `offline` with no connection; `dnd` as `dnd` while connected and `offline` without a connection; `invisible` as `offline`; and `""` as `""`, connected or not, so it never tells. Connected users' come from their connection attachments, with no SQL; a member listing reads each listed registered member's chosen status with them (one primary-key probe of `user_status`, which costs a read only for a member with a row), so a member without a connection who chose none shows `""`. A push registration never shows anyone as `idle`. `PRESENCE` is `true` or `false`, and admins turn it off and on with `/toggle presence`.

  Changes are announced as `user` `{"new": {"user_id", "status"}}` to every other user's connections that share a room with the user. The user's own connections are not told what others see: their `you` shows their choice. After every sign-in (Mute: not an `auth` that adds a passkey, nor a repeat `auth` as the same user), after the `auth` result and the mutes in effect, the connection is sent, the same way, the status of each other user with a connection who shares a room with it (§4.11), as others were last told it, so a change still waiting on the coalescing minute is not told early. Users shown `offline` (invisible, or made visible and not yet announced) or `""` (none) are left out, as users without a connection are and as connected member listings leave them out, so the frames never tell that a user who hides it is connected; listings carry their status. It reads attachments only, with no SQL. A connected user who joins a room has their status sent the same way to that room's members, after the membership, since the membership's `user` is a recorded object without it. What others were last told of a user is kept on each of the user's connections (`pres` in the attachment: the status others were told, when, and how long a change waits), and for a user whose last connection closed, on each connection that shares a room with them and still has to be told (`owed`, at most 32 a connection; more are sent at once), so a change waiting to be announced survives hibernation and eviction. Listings show what others were last told, so a change still to come applies to them too, and a connection shown a waiting user without a connection becomes owed that user's change. Changes the connections cause are coalesced per user: at most one per `statusCoalesceSeconds` (60), counted in memory and in `pres`; a change within the minute waits, and only the latest goes out (none if it is back to what was told). A change caused by a closed connection (offline, or idle when the attended tab closes while an idle one stays) waits `offlineGraceSeconds` (60) besides, so a reload or a mobile reconnect within it shows nothing. A runtime-closed socket whose close event has not yet arrived counts as closed with the grace too, and a vanished peer from when it is found stale. A change the user makes with `me` is announced at once (`me` changes are limited with mutes, above), so nobody keeps seeing an `invisible` user online. One in-memory `setTimeout`, armed for the earliest due change or mute ending within a minute and only while a signed-in connection is open, does what is due; it keeps the object awake at most `MAX_STATUS_DELAY_SECONDS` (60) after the last event, uses no SQL (but for a room mute that ran out), schedules no alarm, and is never periodic. Each event also sweeps (at most every 30 seconds, or when a change is overdue, and always first after a wake): a mute that ran out, a stale peer (never the one whose frame starts the sweep, which has just been heard from). Turning presence off with `/toggle` stops showing statuses to others and sending them after `auth`; the chosen status is still kept and in `you`, mutes are still kept, sent and ended, and `dnd` and mutes still silence pushes. Each connection is sent `""` (none, §4.11) for each user it was told of, as `user` `{"new": {"user_id", "status": ""}}`: users with a connection who share a room with it, and users it is owed a change for. This reads attachments only, with no SQL, and sends one frame per such pair. Listings then carry `status: ""` for every user: capability `status` is still advertised, and §4.11 has servers include `status` in every current user object of `room_list` and `room_update`, so leaving it out is not an option; `""` (none) is what showing nobody's status means, the value the toggle just sent, and it costs no read. So a user without a connection shown only in an earlier listing is cleared by the next listing, or when the client drops kept values at its next sign-in (§4.11). Turning it on starts from each user's status then, announcing no change for it, and sends each signed-in connection the status of each other connected user who shares a room with it, as after a sign-in.
  - Member listings are reused for up to `statusCoalesceSeconds`: the store keeps each room's member rows (chosen statuses included) in memory and serves a listing again with no SQL and no reservation until any write to `identities`, `memberships` or `user_status`, or until the time is up. Avatars are judged against the time of each listing, so a reused listing is as current as a fresh one. A reconnect wave that lists `general` 100 times reads it once.
- Wake: only a registered user's new message (not an edit, move, deletion, retry, reaction or command; a guest's messages wake no one) that replies to a message (scope `replies`) or whose `body.mentions` lists users (scope `mentions`). The replied-to message's author comes from one metered lookup of its current state, and is skipped when the message is unknown or expired. Candidates are the replied-to author first, so mentions cannot crowd them out, then the mentioned users in order, deduplicated with their reasons combined: users other than the sender (so a reply to one's own message wakes no one), not guests, who have no connection authenticated as them that is both fresh (not stale by the ping timeout) and not idle, at most 32, found without further SQL. Each candidate is then looked up in turn: one whose unscoped mute is in effect or whose status is `dnd` is passed over (§4.7: what a mute or `dnd` silences goes only to `badge` registrations, which this server does not have, so it is not sent), and takes no wake slot; then its live registrations, and only those whose scopes include a reason the candidate qualifies by count (a user both mentioned and replied to qualifies by either, and is pushed once): one with none takes no wake, so ten unregistered mentions do not crowd out the eleventh; one that muted the message's room, or for a thread the thread's parent, is passed over the same way (two primary-key probes of `room_mutes`; the room's parent is read once a message); one woken for the same room within `coalesceSeconds` (60) is passed over, so a busy conversation pushes an idle user at most once a minute per room; the rest are woken, up to `wakesPerMessage` (10) users, each on every live registration, most recently registered first. Each push counts against the recipient's `pushesPerRecipientDay` (100) and the server's `pushesPerDay` (5,000; Free: 1,000) when claimed, and against the sender's `pushesPerSenderDay` (200; Free: 50) once delivered (a 2xx from the push service; a claim checks what is left of it, counting the pushes it has already claimed); past any of them, the rest are skipped. So a few accounts cannot use up the day's pushes with failing endpoints, nor flood one recipient. A registration whose endpoint `PUSH_HOSTS` no longer allows is passed over before it counts. The window is kept per user and room in the `push_wakes` table, so it survives hibernation and moves with `/rename`; cleanup deletes rows past it. It does not restart when the user comes back: a user woken, back, and idle again within the window is not pushed again for that room until it passes. Every room is visible to everyone here, so a mention or reply in any room counts, joined or not. The pushes go out after the result, kept alive with `waitUntil`; a failure is logged and never affects the post.
- Delivery: the payload is the envelope `{"push_id": …, "message": {…}}` (§4.7), built per registration: `push_id` when the registration has one, no `unread` (not implemented), and `message`, the message object without `log_id`: `message_id`, `room_id`, `from`, `reply_to` when set, and `body` with `text` cut to 200 code points (ending in `…`; left out when empty) and `mentions`. The whole envelope is at most 2048 bytes of JSON (§4.7), so `message` drops `mentions` first, then all of `from` but `user_id` and `name`, then `body` (`body` is also left out when it would be empty), and last everything but `message_id`, `room_id` and `from.user_id`, which always fits (the server asserts it); `format`, `embeds`, `ext` and the `prev_*` links are left out. It is encrypted per [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291) (`aes128gcm`, a fresh P-256 key and salt per push) and sent with a [VAPID](https://www.rfc-editor.org/rfc/rfc8292) `Authorization: vapid t=<ES256 JWT for the endpoint's origin, 12 hours>, k=<public key>`, `TTL` of `ttlSeconds` (a day) and `Urgency: high` (a push for `mentions` or `replies`; §4.7 gives `normal` to `joined` and `low` to pushes without `message`, neither of which this server sends), without following redirects, all with WebCrypto. Before each push the endpoint is checked again against `PUSH_HOSTS` as configured now, so a registration made under a wider list is skipped. The configuration check signs and verifies with the VAPID pair, so a private key that does not match the public one fails it. §4.7 has servers remove a registration whose `url` will not accept pushes, such as one that answers 404 or 410. Here that is a 404 or 410 (gone), or a 403 (the push service refuses this server's VAPID key for it, so it was made with another key; the configuration check proves the pair matches, so no push to it will ever be accepted, and the client registers again with the current key on its next connection): each deletes the registration that was pushed to, by its primary key (user and endpoint) and only while it still has the keys pushed to, so a fresh registration of it stays. Other users' registrations of the same endpoint are left to their own pushes and to expiry: a delete by endpoint alone would grow with the accounts that share it, which anyone can multiply. Any other failure loses that push, which is not retried.
- Cost: a registration is about 8 written rows, one more for the partial index of waking registrations (none when unchanged within a day); a reply's author lookup is one indexed read (about 5 rows with the reservation); a wake claim reads each candidate's `user_status` row (mute and `dnd`), live waking registrations (by the partial index, so registrations that wake for nothing are not read), and, for one with registrations, its room mutes for the room and its parent (two primary-key probes, the parent read once a message) and wake time, about 1 row each without registrations, and for a message that wakes someone writes the wake times and both counters, about 19 rows for the first wake of a day; a message that wakes no one writes nothing. The pushes are outbound requests, which no allowance counts. `/status` shows the day's pushes against `pushesPerDay`. A `me` `status` change is about 3 written rows and an unscoped mute change about 4, a room mute about 4; a sign-in reads the `user_status` row and the user's room mutes (about 6 rows with none, 105 with 100), and nothing more for status. Deriving and announcing statuses, and telling an unscoped mute ran out, cost no SQL and no requests; a room mute that ran out costs one range read of the user's room mutes and a delete. See the [cost report](docs/cost-report.md#push) and its [user status](docs/cost-report.md#user-status) section.

## 5. Authentication and IP attribution

### Guest

`auth` with `scheme: "guest"` assigns a server-authoritative guest ID `guest_<n>` from a server-wide counter (`guest_1`, `guest_2`, …; [PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication) suggests this convention) and the generated display name `Guest <n>`, bounded by the name limits. Repeated guest auth on that same connection must not mint fresh identities to escape limits: it returns the connection's identity and takes no number. No durable account row is necessary for each guest socket.

Guest numbers are reserved in blocks of `guestNumberBlock` (10): the object keeps the next number and the end of its block in memory, and when the block is used up it advances a durable high-water mark (a `_meta` row) by one block in one write, then serves that block from memory. A start, eviction, or hibernation wake loses the in-memory block, so the first guest afterwards reserves a fresh block past the mark and the rest of the old one is skipped. Numbers are therefore unique across restarts, evictions, hibernation, and schema resets (the mark is carried across the wipe), but not contiguous: expect gaps of up to one block per wake, so the latest number overstates the count of guests by at most that much. Reserving and taking a number are synchronous, with no await between them, so concurrent auths never share a number or reserve twice. A reservation is charged like any other (see the cost report); an exhausted budget fails the guest `auth` that needs a new block.

Guest identity lasts for that socket, including hibernation. This initial version does not promise guest identity recovery after reconnect; explain that guest retry deduplication/ownership cannot span a reconnect that assigns a new identity. IP posting limits still span reconnects. Registered users have stable identity across devices/reconnects.

Guests only read unless the deployment sets `GUEST_POSTING=true`, and `server.params.ext.demo.guest_posting` says which. A read-only guest may authenticate, list rooms, read any room's history without joining it, and run `/help`; it stays in `general`, where authentication put it. `message`, `reactions`, `room_set`, `room_join`, `room_leave`, and `/invite-bot` are writes and are `denied` with "Guests can only read here; sign in with a passkey to post or join rooms" ([PROTOCOL.md §3.5](https://github.com/shazow/apron/blob/main/PROTOCOL.md#35-messages) and [§4.3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#432-membership) let a server deny these by policy), and its typing is dropped. `me` is not a write: any guest may set its `status` with it (section 4.4, Chosen status), and a guest's `name` is `denied` whether or not guests may post, since only registered users may rename (§3.3). Every connection gets a `~private` welcome right after the `server` frame, before any `auth` ([PROTOCOL.md §3.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#32-authentication) and [Appendix B](https://github.com/shazow/apron/blob/main/PROTOCOL.md#appendix-b--valid-scenarios-informative)): to that connection only, with no `room_id` since the client knows no rooms yet. Its markdown opens with "Welcome to Apron Chat. Server version: `<version>`", the deploy's tag (`wrangler deploy --tag`) or else the first 8 characters of its Worker version ID, from the `CF_VERSION_METADATA` binding. A deploy closes every socket, so clients see the new version when they reconnect. Where guests only read, a second paragraph says so, worded for what the connection can sign in with ("Guests can read. *Sign in with passkey* to participate." where passkeys are offered; elsewhere it points at a passkey on the demo's own site or a bot token). It is sent before the object reads any frame, so it precedes a pipelined `auth` result, and again on each connection; clients may replace the last one. The `server` frame's `welcome` (section 4) says the same for the sign-in screen, which is where protocol v7 clients show it; the notice stays for the room the client opens.

### Bots

A registered user (not a guest, not a bot) runs `/invite-bot` to get a bearer token for a bot account. The bot's `user_id` is fixed as `bot_` plus the owner's `user_id`, and its name is "Bot of <owner's name>" (the owner's `user_id` when the name was removed), cut to the name limits. The first invite creates the bot as an identity row with tier `bot` and no credential, which counts against the registration caps (per IP, per day, and the identity cap) and starts the bot in `general` with a logged `membership` record; a later invite renames the bot after the owner's current name, announcing the change with `user` `new` to those who share a room with the bot, and adds nothing else. Each invite mints a new token, `apron_bot_` plus 32 random bytes as base64url, and revokes the last one: bot connections open with the old token close with 1008. The token goes to the inviting connection only, in a `~private` notice in the room of the command (markdown: the token in a code block, then a second code block of instructions to give an LLM: read `PROTOCOL.md` on GitHub, connect to the WebSocket URL the inviting connection reached, authenticate with the token scheme and this token, and say hello and listen), before the `{}` result.

Tokens are kept in the object's key-value storage like passkey sessions: `bot-token:<sha256 of the token>` → `{botId, ownerId}`, and `bot:<botId>` → the current token's key, so the next invite can delete it. They do not expire; a new invite is how an owner rotates or revokes one, and a schema reset wipes them and the bot identities with everything else. A bot authenticates with `auth` `scheme: "token"`, which every connection is offered: `server.params.auth` is `["token","guest"]` where passkeys are not, since bots are not browsers and send no `Origin`. The `apron_bot_` prefix routes a token to the bot path without a storage read; passkey session tokens still resume only on the origin that minted them. A bot then acts as a registered user with its own posting quota and stored memberships, except that `me` cannot rename it ("A bot is named after its owner") and it cannot run `/invite-bot`.

An admin may also make a registered user a bot with `/role <user_id> bot` (section 5, Admins), say one made by `/invite-token` for a script that signs in with its token. Such a user acts as a bot everywhere except that it has no owner: it shows `roles` `["bot"]`, can't register a passkey, change its name with `me`, run the commands for owners (`/invite-bot`, `/passkeys`, `/avatar`), or be an admin, and `/rename` refuses it (`invalid_params`). Its `user_id` is not `bot_…`, so no owner may add it to rooms, and `/purge` treats it as a user. Taking the role away makes it an ordinary user again.

### Admins

Where `APRON_ADMIN_TOKEN` is set ([configuration](docs/configuration.md)), as a Worker secret, `auth` with `scheme: "token"` and that token signs in as the registered user `admin` ("Admin") from any origin, without a passkey. The user is created on first use like a bot, as an identity row with no credential that counts against the registration caps and starts in `general`, and otherwise acts as any registered user, `/invite-bot` included. The result carries no session `token`. Unset, there is no such token. The `admin` user is always an admin, and never holds a passkey (registering one while signed in as it is `denied`, and a schema reset carries none for it), so deleting the secret turns it off completely; an admin makes other registered users (not bots or guests) admins with `/admin <user_id>` or `/role <user_id> admin`. `/admin remove` takes the role away again.

Roles are a column of the user's identity row, `roles_json`, a JSON list of role names in the order given (at most 8; `[]` for none), so they are read with the identity wherever it is read anyway: at sign-in, where the connection keeps them for its current objects and for the admin and bot checks, which then need no storage read; in member listings, from the same joined row as each member's name; and in `/role`. They move with the row on `/rename`, go with it on `/purge`, and are carried across a schema reset with the user's passkey (but `bot`, which no passkey holder has). The `admin` user is created with `admin`, and an owner's bot (`bot_…`, identity tier `bot`) with `bot`; neither can lose it. Current user objects (`you`, `user` `you` and `new`, and room `users`) carry `roles` ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)); guests have none, and recorded objects such as `from` carry none. Any role name is a label for display, except two: `admin` lets the user run the admin commands, and `bot` makes the user a bot (section 5, Bots). A later version may grant capabilities by role; the admin and bot checks are where they would apply. Admins may also add and remove other users with `room_join` and `room_leave` and a `user_id` (section 4). Admins may run these commands, each answered by a `~private` notice to the sender before the `{}` result:

- `/admin <user_id>`: makes that registered user an admin, or says they already are. A new admin's connections get `user` `you`, and those who share a room with them `new`, with `roles: ["admin"]`. `/admin remove <user_id>` takes it away again (not from `admin`), announced the same way with `roles: []`, the empty value that clears a field ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)). A bot can't be an admin (`invalid_params`). Every current object of a registered user (`you`, `user` `you` and `new`, and room `users`) carries its `roles`, `[]` included, so any client's kept object clears a role the user lost, even one that missed the `user` notification; guests carry none. That adds `"roles":[]`, 11 bytes, per registered user in a listing's `users`, within the listing's 256 KiB cap (past it, `members` and `users` are left out as before) and at no SQL cost: roles are read with the identity row.
- `/role <user_id>` (a leading `@` is allowed): says which roles a registered user or bot has. `/role <user_id> <role>` gives them the role, or takes it away when they have it, and says which. A role is 1 to 24 lowercase letters, digits, `_` or `-`, starting with a letter (taken case-insensitively). A change is announced like `/admin`'s, `user` `you` to the user's connections and `new` to those who share a room with them, with the new `roles` (`[]` when the last went). `/role <user_id> admin` is `/admin`. `bot` is not given to an admin, nor to a user who holds a passkey, since a bot signs in with a token only (`/invite-token` makes such a user). `admin` can't be taken from the `admin` user, nor `bot` from an owner's bot, and guests have none: those, unknown users, malformed roles, and a ninth role are `invalid_params` or `denied`. It costs the identity read and, on a change, its update and the user's current object for the announcement (from a connection, else one identity read); giving `bot` adds one credential read. Showing roles costs one identity read.
- `/kick <user_id>`: removes the user from the room of the command, as if they had left it (`room_leave`): a registered user's leave is stored and logged, and its membership goes to the room's other members in `room_update` `memberships`; a connected guest's leaves its connections. The user's connections get `room_update` `left` (with the membership, for a registered user), and they may join again. It is charged to the admin's posting limits. Kicking oneself, or a user not in the room, is `invalid_params`. The notice goes to the kicker only, as a `~private` reply; the room's remaining members learn of the removal from the membership (for a registered user) rather than from a `~room` notice as in the [PROTOCOL.md §4.8](https://github.com/shazow/apron/blob/main/PROTOCOL.md#48-command) example, and a guest's removal, which is not logged, reaches only the guest.
- `/rename <old_user_id> <new_user_id>`: gives a registered user (not a bot, a guest, or `admin`) a new `user_id`, 1 to 64 letters, digits, `_` or `-`, starting with a letter or digit, not `guest_…` or `bot_…`, and not taken. The identity row, its passkeys (so they sign in as the new id), its stored memberships, its roles, its uploads, its limiter windows and its dedup rows move to the new id. The old `user_id` is retired in a `_meta` row (`renamed:<old>`) and never reissued, until a schema reset wipes the row. The user's connections become the new identity and get `user` `you`, and those who share a room with the user get `user` `new` with `old` ([PROTOCOL.md §3.3](https://github.com/shazow/apron/blob/main/PROTOCOL.md#33-identity)). What the user left under the old id is rewritten to the new one, keeping the recorded names: the `from` of their logged and current message snapshots (so they can still edit them), their reaction sets, logged and current, and their logged membership changes. This is the one case where a logged record changes after the fact. It is not announced: connected clients keep what they hold and see the new id when they load history again, so a client may briefly hold both ids for one user. Finding the records scans the retained log once, like `/purge` (at most about 5 reads per retained record), and the rewrite costs a write or two per record found. Other users' `body.mentions` keep the old id; the user's sessions are `denied` on resume, sending the client back to its passkey, and are deleted then or when they expire; and the user's bot keeps its `bot_<old>` id and token, while a later `/invite-bot` makes a new `bot_<new>`.
- `/invite <uses>`: mints the sign-up invite ([PROTOCOL.md Appendix B](https://github.com/shazow/apron/blob/main/PROTOCOL.md#appendix-b--valid-scenarios-informative)), `apron_join_` and 43 base64url characters, sent in a `~private` notice before the result: a token that signs up to `uses` (1 to 50) new users within 7 days. There is one live invite: a new `/invite` revokes the last, and `/invite 0` only revokes it. It is kept in key-value storage under its SHA-256 (`join-token:…`) with its remaining count and expiry, and a `join-invite` pointer. Each `auth` with `scheme: "token"` and the invite (from any origin, on an unauthenticated or guest connection) creates a registered user with no passkey, as `/invite-token` does: named as `auth`'s `name` asks (trimmed, within the name limits; else "Member", since "Guest" names guests), with a `user_id` picked from the name like a passkey registration's (`ada_1234`, else `u_…`), charged as a registration against the per-IP, daily, and identity caps, starting in `general`. The result carries `you` and the new user's own `apron_invite_` token, which the client saves and signs in with from then on; the user may add a passkey once signed in (section 5, WebAuthn). A used-up, expired, or revoked invite is `denied`, and a used-up or expired one is deleted when it is tried. Uses are serialized with the other token work, so they never exceed the count. A sign-up reserves its whole key-value cost (the invite read, and one put of the new user's token, its pointer, and the invite counted down) before the account is created, and spends no use when the connection has already closed, so an exhausted budget cannot leave an account without its token or an invite not counted down. The put follows the account's creation with no await between them. A reply lost after that costs one use: the account exists with a token nobody received, until an admin `/purge`s it. The session lock is taken before the mutation lock here; no code takes them the other way round.
- `/invite-token <user_id>` (a leading `@` is allowed): creates a registered user with that `user_id` and no passkey, named after the `user_id` and starting in `general` (a logged membership), charged as a registration against the per-IP, daily, and identity caps. The `user_id` follows `/rename`'s rules and must be free: not held by any identity or retired by `/rename` (`invalid_params` "The user_id … is taken"). The sender gets the user's bearer token, `apron_invite_` and 43 base64url characters, in a `~private` notice before the result. `auth` with `scheme: "token"` and it signs in as that user from any origin, like a bot token; it does not expire and is stored only as its SHA-256. The user is an ordinary registered user: they may rename themselves, run `/invite-bot`, and set an avatar. `/rename` moves the token to the new `user_id`, and `/purge` revokes it.
- `/purge <user_id>` (a leading `@` is allowed): disconnects the user and their bot (`bot_<user_id>`), then deletes, silently and with no new records, their message snapshots and current messages with every reaction set on them, their reaction sets elsewhere, their memberships and membership records, their uploads and avatar (R2 objects included), and their identity, passkeys, sessions (which then fail), bot and invite tokens, admin listing, limiter and dedup rows. A logged record listing them beside others (a move's reaction sets) is rewritten without them; rooms they created stay. Clients already showing their content keep it until they load history again. They may register a new passkey. Not the sender or `admin`; an unknown user is `invalid_params`. The sender gets a `~private` notice with the counts before the result.
- `/toggle activity`, `/toggle uploads` (with uploads configured) and `/toggle presence` (with push configured): turn the feature off or on for everyone and answer with a `~private` notice naming the new state. The override is kept in `_meta` across restarts; toggling back to the deployment's default (the plan or `ACTIVITY` for activity, on for uploads, the plan or `PRESENCE` for presence) removes it, and a schema reset clears it. Presence turned off stops showing statuses to others, and clears the ones connected clients were shown with `""`; the status each user chose is still kept and in their `you`, and `invisible` and `""` still leave the user out of connected member listings (section 4.4, User status). New connections are offered the cap (`activity`, `embed:upload`) only while the feature is on; connected clients keep the caps they were given. With activity off, typing is no longer relayed and `activity` gets the unsupported-method path. With uploads off, `/help` leaves out `/avatar`, and new upload embeds and `/avatar` are `denied` ("Uploads are turned off here"); writes already started still finish, and existing images stay. Any other argument is `invalid_params`.
- `/status`: today's Cloudflare account usage (refreshed from account analytics at most once a minute, where `ACCOUNT_ID` and `ACCOUNT_ANALYTICS_TOKEN` are set) against the selected plan's daily allowance (for Workers Paid, its monthly included usage over 31 days), and the object's own daily reservations (SQL reads and writes, frames, admissions, posts, registrations), registered users, open connections and database size against their budgets, as markdown tables.

### Canonical WebAuthn authentication

Implement protocol [§4.9](https://github.com/shazow/apron/blob/main/PROTOCOL.md#49-webauthn-authentication): `action` is `register` or `login`, `step` is `begin` or `finish`, and both steps require request IDs. Support discoverable passkeys; do not download a directory of all credentials to the client.

```json
{"method":"auth","id":"a1","params":{"scheme":"webauthn","action":"register","step":"begin"}}
```

A registration `begin` may carry `name`, the display name to register with (trimmed; over the name limits is `too_large`). It also picks the new `user_id`: the name as lowercase ASCII letters and digits, other runs as one `_`, at most 16 characters, plus `_` and 4 random digits (`Foo` → `foo_1234`), retried up to 8 times while taken. With no `name`, or one that leaves nothing usable or would read as a guest (`guest…`) or bot (`bot…`) id, the id is `u_` plus 16 random bytes as base64url and the name is the guest's. The id is only a candidate until `finish`, which still fails if another registration took it meanwhile.

The intermediate response is `{"id":"a1","result":{"challenge_id":"...","public_key":{...}}}`. `public_key` is JSON-encoded WebAuthn creation options, with binary fields represented as base64url; the client adapter converts them to browser API types. For `action: "login"`, return request options. An intermediate result does not authenticate the socket or start live delivery.

```json
{"method":"auth","id":"a2","params":{"scheme":"webauthn","action":"register","step":"finish","challenge_id":"...","credential":{}}}
```

`credential` contains the serialized browser credential response, not the empty illustrative object above. On successful verification return normal `result.you` plus a bearer `token` for session resume (see [policy](docs/policy.md#authentication-policy)), store the authenticated tier in the attachment, and establish live room delivery. Login uses the same exchange with `action: "login"`.

- Challenge TTL: 120 seconds, one outstanding challenge per connection. A challenge is bound to connection, action, RP ID, and allowed origin, and is consumed by a matching finish attempt. Begin replaces an earlier challenge. A challenge does not extend the initial authentication deadline; challenge expiry and unauthenticated timeout are independent.
- Guest users may initiate an upgrade on their authenticated guest socket; they retain guest rights until success. A guest is not an account, so its registration creates one, which replaces the guest identity on that connection (`user` `new` with `old` to those who shared a room with it). Failed upgrade grants no higher allowance.
- A registration on a connection already signed in as a registered user adds the passkey to that account ([PROTOCOL.md §4.9](https://github.com/shazow/apron/blob/main/PROTOCOL.md#49-webauthn-authentication)): `begin` offers creation options for the account's `user_id` and name, under its WebAuthn user handle (an account without a passkey yet, such as an invited user, gets a new one, stored at `begin` so concurrent ceremonies share it), excluding its existing passkeys; a verified `finish` stores the credential and answers `{you}`, the connection staying signed in as it was (no new session token), and the account's other connections get a `~private` notice that a passkey was added. A bot signs in with its token and is `denied`, and so is the `admin` user (section 5, Admins), so that deleting `APRON_ADMIN_TOKEN` turns it off completely. There is no re-authentication step: any signed-in connection may add a passkey, which is why the account's other connections are told and `/passkeys` exists.
- `/passkeys` (registered users other than bots) lists the sender's passkeys, oldest first and numbered, with when each was added and last used, in a `~private` notice; `/passkeys remove <n>` removes one and tells the account's other connections, but never the last one (`invalid_params`), which would leave a passkey user no way back in. Sessions a removed passkey started stay valid until they expire (sessions are not tied to a credential). Each is one bounded read of at most 8 rows, and a removal one delete. An account holds at most 8 passkeys (`MAX_PASSKEYS_PER_USER`); past that, `begin` is `denied`. Each added passkey is charged as a registration against the per-IP and daily caps, not the identity count. A `login` on a signed-in connection is `denied`: switching identity requires a reconnect.
- Configure an explicit RP ID and exact allowed origins. Validate type, challenge, origin, RP ID hash, signature, user presence, and user verification using a maintained verifier. Registration requires discoverable credentials, user verification, and `attestation: "none"`. Bound all credential sizes before expensive verification.
- Do not accept a claimed user ID or credential ID as authentication. Resolve identity from the verified stored credential. Handle zero/non-monotonic counters for synchronized passkeys according to the verifier's supported semantics; do not invent a counter-only proof of authenticity.
- A registered identity holds up to 8 passkeys, added while signed in; account linking across identities and recovery are out of scope. Unique credential IDs cannot register another identity or be added twice. Store only bounded necessary public-key and verifier metadata.
- Recheck registration caps and atomically write credential/identity/budgets after verification, before returning success. Concurrent successful verifications cannot exceed caps.
- Authentication executes on every new connection; it is not bypassed by the mutation deduplication cache. All begin/finish/retry attempts count toward auth/frame/resource limits.
- Registration does not clear the IP's anonymous usage or aggregate quota. Multiple passkeys remain subject to the common IP/global budgets.

Implementation reference: [WebAuthn verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).

### IP key

Extract Cloudflare's client address in the public entry Worker. Strip any incoming copy of the private forwarding field before setting trusted metadata for the DO. Do not trust `X-Forwarded-For`, client JSON, or a public query parameter. Account for documented Worker-subrequest and Pseudo IPv4 behavior; a missing/unusable trusted IP fails admission rather than creating a fresh unlimited bucket.

Canonicalize IPv4 and IPv4-mapped IPv6 to the same IPv4 key; group native IPv6 by /64. Store the first 128 bits of SHA-256 of the canonical key, encoded as unpadded base64url. This requires no server secret and is a compact internal identifier, not anonymization. Keep the hash format stable across daily rollover and deployments to preserve active rolling windows. Public users behind NAT share IP limits; explain this tradeoff in the demo help text.

Reference: [Cloudflare request headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

### Application allocations

| Budget | Ceiling | Allocation |
| --- | ---: | --- |
| SQL writes/day | 800,000 (Free: 80,000) | Up to 700,000 foreground; 100,000 reserved maintenance/control (Free: 60,000 and 20,000) |
| SQL reads/day | 30,000,000 (Free: 3,000,000) | Up to 25,000,000 foreground; 5,000,000 reserved maintenance/control (Free: 2,500,000 and 500,000) |

| Resume growth low-water | 80 MiB effective occupied storage | Avoid oscillating admission |
| Cleanup batch | At most 100 source records | Further limited by measured reads/writes and available reserve |

The daily post ceiling (10,000; Free: 5,000) is a maximum, not a promise. If the measured schema/traffic exhausts resources earlier, refuse work earlier. Do not claim capacity from a guess of one write per message. Include snapshot/log/index/dedup writes, limiter state, credential counters, alarms, failed work, expired-data deletion, migrations, and bookkeeping. Cleanup's workload includes yesterday's records while accepting today's. Avoid indexing every metadata column or enabling FTS.

Implementation must have one metered storage boundary for all SQL/KV/alarm work. For each operation class, establish a conservative cost bound, reserve it before work, and observe actual SQL cursor row counts to verify the model. Include the cost of the reservation itself. No public request may trigger a full-table scan, unbounded join, migration, or unmetered maintenance query. `LIMIT` alone does not prove bounded scan cost. A cap breach in cost calibration is a release blocker, not a reason to silently raise budgets.

Durable block reservation is allowed to avoid a SQL write on every incoming/rejected frame: commit an allowance before spending it; tie it to an owner and UTC day; never grant the same allowance twice. Persist consumption where necessary, or burn unused allowance on restart. Connection attachments can preserve connection-local lease state across normal hibernation. Budget reservations must remain charged even if subsequent work rolls back or crashes; a rolled-back row is not evidence of refunded platform usage. Once a metered operation finishes, the part of its reservation that its SQL cursors show it did not use (rolled-back rows count as used) is credited back in one budget-row update, which the operation pays for; a crash before then leaves the whole reservation charged, and KV work, which has no cursor, stays fully charged. Exhausted/uncertain accounting fails closed.

Posting window timestamps and counters must survive reconnection/hibernation and concurrent sockets. Keep bounded persistent limiter keys for admitted principals, expire them after their applicable windows, and bound any additional in-memory negative cache. Never create one durable record per attacker-supplied request ID, failed credential, or rejected IP. Proposed limiter-record cap: 10,000, with old expired entries reclaimable in metered batches; new principals are denied when the cap is reached.

The DO is the authoritative limiter. Cloudflare's edge Rate Limiting binding is optional preliminary filtering and cannot serve as an exact global budget: [documented locality/accuracy](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

### Storage pressure

Measure physical database bytes and bounded logical payload totals. Reject growth with enough margin for the largest admitted operation, indexes, and control updates; check again after commits. Deletions may free SQLite pages for reuse without shrinking `databaseSize`. A file staying large must not be mistaken for still-occupied data, and delete/reinsert churn must not make it grow without bound. Determine actual supported freelist/page instrumentation and page reuse in tests. Do not assume VACUUM is available or free, and do not put it on a request path.

At pressure thresholds, purge only already-expired data and stop growth if that is insufficient. Do not silently shorten the advertised retention window to accept another message. A 128 MiB target does not guarantee a day's ceiling of maximum-size messages plus all ancillary data; size admission takes precedence. Never delete the whole database to reclaim chat space because it contains credential and quota authority.

### What can and cannot be guaranteed

Select the budgets that match the account's plan, use no paid ancillary services, and reserve account headroom for this workload. Incoming rejected HTTP/WebSocket traffic still consumes platform resources; no application limiter can guarantee availability under unlimited hostile traffic. On Workers Free, Cloudflare's hard free-plan limits are the final zero-overage backstop. On Workers Paid there is no such backstop: rejected traffic past the included usage is billed (at the checked rates, $0.30 per million Worker requests and $0.15 per million DO requests). A budget guard on a minute cron trigger reads account usage for the day and the calendar month and, at 90% of a daily share or half of a monthly allowance, enables a zone WAF rule that blocks the server's hostname before the Worker runs, so blocked requests are not billed; see [the budget guard](docs/configuration.md#budget-guard) for its lag and limits. App quotas provide controlled degradation under admitted traffic, not a network-level request shield.

One active object at the documented memory allocation uses roughly 11,000 GB-seconds over a full day, below the duration allowance; still use hibernation and avoid extra production objects. Fan-out remains processing/memory work even when it has no outgoing request charge. Native resource errors must be caught where possible and fail closed without reconnect or alarm retry storms.

## 8. Persistence and transaction boundaries

Use versioned schema migrations, parameterized SQL, minimal indexes, and synchronous transactions for related writes. Do not run migration DDL on every hibernation wake. Keep constructors light and initialize once per schema version under the appropriate initialization gate. Reference: [SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

Suggested logical schema; physical layout may change to reduce measured costs:

| Table/state | Required contents |
| --- | --- |
| log_state | Server-wide last log ID, monotonic history floor F, last commit time |
| rooms | Room ID, fixed parent, creation/current record log IDs, per-room head, bounded client fields (`title`, `description`, `ext`), count of stored registered members; one top-level room plus at most 100 threads |
| memberships | Each registered identity's joined rooms, one row per room and user: by room (the primary key) for `members`, and by user for the user's rooms; guests' live in connection attachments |
| records | Room/log primary key, internal commit time, record kind, complete record JSON; a move is stored in both rooms |
| message_state | Message ID primary key, current room, latest log ID, latest snapshot and author |
| reaction_state | Message/user primary key, latest log ID, reacting identity, emoji set |
| identities/credentials | Stable user ID, unique credential ID (several per user ID, at most 8), public key, required verifier state, bounded name, roles |
| push_subscriptions | User and push endpoint URL primary key, browser keys (`p256dh`, `auth`), the client's optional `push_id`, wake scopes, created and registered times; by user and registration time for a user's registrations, by registration time for expiry, and by user and registration time for those that wake for messages (a partial index, so wakes read only those) |
| user_status | User primary key, the `status` the user chose with `me` (`online` by default) and until when they are muted (`status` `mute` without `room_id`); a row only while either differs from the default |
| room_mutes | User and room primary key, until when the user muted the room and its threads (`status` `mute` with `room_id`); at most 100 a user |
| push_wakes | User and room primary key, when the user was last woken by push for the room (coalescing); by that time for cleanup |
| accepted_requests | User/request primary key, canonical method+params digest, the result's identifiers (replayed against current state), expiry |
| resource_budgets | UTC day, charged/reserved reads/writes/frames/admissions/posts/registrations |
| principal_limits | Bounded IP/user counters and rolling posting timestamps |
| maintenance | Next due tasks, pending cleanup cutoff/cursor, schema version |
| _meta | Schema version, effective clock, bounded counters and latches, and the guest-number high-water mark |

Indexes cover per-room log ranges (the primary key), the server-wide log prefix and commit time for expiration, latest-record expiry of message and reaction state, registered memberships by room (the primary key) and by user, dedup expiry, and limiter expiry. A record belongs to every room its message is in just before or after it; storing a move once per room keeps each room's history a single indexed range. Benchmark the actual query plan.

Each mutation, after resource reservation and validation, performs one atomic decision: check dedup, recheck all applicable quotas/ownership, allocate log IDs, update current state, append every record to each room log it belongs to, advance room heads, record result, update applicable posting counters. Send the recorded result and ordered broadcast only after success. Do not call remote services inside the mutation transaction.

Store internal commit time for retention, distinct from the wire log ID. Make commit times nondecreasing so expiration is a prefix of the log even if the system clock rolls back. Keep a nondecreasing effective time for budget/retention decisions; clock anomalies may delay expiry, never resurrect expired data or replenish a used budget.

### Schema versions

The schema version lives in `_meta` and the `maintenance` row. A new object creates the current schema (8: the `push_subscriptions` (with a partial index of the registrations that wake for messages), `push_wakes`, `user_status` and `room_mutes` tables; 7: identities keep their roles in `roles_json`; 6, for protocol v7: rooms keep a `description` among their client fields and count their stored members; 5 added the `uploads` table and each identity's avatar; 4 added membership records and the `memberships` table for protocol v6) and seeds the `general` room's creation record. An additive change that older code ignores and whose absence reads as its initial value needs no new version and no wipe: the guest-number mark is such a `_meta` row, absent (zero) in schema 4 objects created before it.

Schema 5 is upgraded in place, so the protocol v7 deploy keeps the demo's history, sessions, tokens, and every passkey. On the first wake, synchronously in the constructor and in one transaction: each room's `intro_message` becomes its `description`, the text of the intro message's current retained snapshot (none when it is deleted, expired, or empty), cut by whole code points and ending in `…` where the room's client fields would pass their 2 KiB cap; the `intro_message_id` column is dropped; every logged room record loses `intro_message` the same way (the room's current record takes the room's new description, an older one the text of the snapshot it embedded), which reads every stored record once; each room's member count is filled from `memberships`; and `credentials` is rebuilt without the UNIQUE `user_id` that limited an identity to one passkey (SQLite drops a constraint only by copying the table), reading and writing every credential once. A plain-text intro is escaped as Markdown (inline markup characters, and block markers at the start of a line), so it reads the same as a description, which is Markdown by convention; a Markdown intro is kept as written. The rows it measurably read and wrote are charged to the day's maintenance reservation without a capacity check, like the passkey carry below.

Schema 6 is then upgraded to 7 the same way, in its own transaction: `identities` gets `roles_json` (default `[]`), set to `["bot"]` for bots (tier `bot`) and `["admin"]` for the `admin` user and the users schema 6 listed in its `_meta` `admins` row, which is deleted. It reads and updates the identities once (at most the identity cap) and is charged the same way. Schema 7 is upgraded to 8 the same way, in its own transaction, by creating the empty `push_subscriptions`, `push_wakes` and `user_status` tables and their indexes, the partial index of waking registrations among them. A schema 5 object takes all three upgrades on one wake.

An upgrade fails closed: if it throws, its transaction rolls back completely, the object stays at its schema (a schema 5 object that finished the first upgrade stays at 6), and the constructor throws on every wake, so the demo is down until a fixed deploy upgrades it. It never falls back to the wiping reset, which would lose the history and tokens the upgrade exists to keep. Upgrades are also one-way: redeploying older code afterwards finds a newer schema and resets the object, keeping only the 100 most recently used passkeys; roll forward rather than back. No sender needs migrating to the `~` system identities: the demo never logged `@server` or `@room` messages, and `@private` notices were never stored.

Other stored data is not migrated: when the constructor finds any other schema version, older or newer, it wipes the whole object with `deleteAll()` (every SQLite table and key-value entry, so chat, rooms, passkey sessions, bot tokens, limiter windows, and deduplication rows) under `blockConcurrencyWhile`, then creates a fresh schema. The demo is public and retains about a day of content, so a reset on schema changes is simpler and safer than upgrade code. Registered passkeys are the exception, so users need not delete and re-create them on every deploy: before the wipe, up to `MAX_CARRIED_PASSKEYS` (100) credentials of `registered` identities are read, most recently used (by the credential's `updated_ms`, bumped on every sign-in) first, and afterwards written back with their identity rows (same `user_id`, name, and WebAuthn user handle), `identity_count`, and each one's `general` membership row (without a log record; other rooms are gone). They keep their roles (from an older schema without `roles_json`, its `_meta` `admins` list as `admin` roles). Passkeys past the cap, bot identities, and the `admin` user (recreated on its next sign-in) are dropped. The carry reads these tables by column name, so a schema change to `identities` or `credentials` must keep that query working or accept that the reset drops them. A token that outlives its session or identity is `denied`, which sends the client back to sign-in, where a carried passkey still works. To avoid replenishing platform usage already metered today, the current UTC day's resource-reservation row is read before the wipe and added back afterwards, together with the one-time 512/512 bootstrap reservation and the rows the passkey carry actually read and wrote (it reads every credential to find the most recent), charged as maintenance. Neither addition checks capacity, so a reset cannot fail on, or be blocked by, an exhausted budget; an exhausted day stays exhausted until UTC midnight. The guest-number high-water mark is carried the same way, so a reset never reissues a guest ID. The accounting-unsafe latch is not carried: an operator deploy that resets storage is its recovery path. The log head is not preserved across a reset; new log IDs are commit-time milliseconds and so normally still exceed old ones, but every old record is gone, so clients reconnecting after a deploy must rebuild from the listed history bounds.

### Deduplication

Deduplicate accepted mutating requests by `(user_id, request_id)` for 24 hours after acceptance. Canonicalize method and params recursively with stable object-key ordering, preserving arrays/types; ignore envelope `jsonrpc`. Store a cryptographic digest rather than a full duplicate message payload where practical. Same key/same operation is not executed or broadcast again, and returns a result reflecting the current state ([PROTOCOL.md §1.2](https://github.com/shazow/apron/blob/main/PROTOCOL.md#12-retries-and-deduplication)): the stored result names what the operation made (`message_id`, `room_id`), which stays true, and an upload's write grant is left out once its write was claimed, finished, or expired (one indexed read per upload embed); `me` answers with the current `you`. Same key/different operation returns invalid_params. Concurrent copies cause one effect and one broadcast. Dedup responses still spend their bounded lookup/frame costs.

Check an unexpired duplicate before applying new-post quotas or deciding an old message has expired; a previously accepted result remains valid through the dedup window. Expired records are logically absent even if physical cleanup is pending. Failed/limited operations are not recorded as accepted. Notifications have no dedup guarantee. After the documented TTL, replaying an old request ID may execute again; the client must not retry stale queued operations indefinitely.

## 9. Rolling history and base-protocol availability

Retention replaces all earlier daily-reset/room-rotation ideas. Keep `general` unchanged. Every cleanup interval (`cleanupSeconds`), expire the prefix of the server-wide log committed more than `retentionSeconds` earlier: 7 days once a day on Workers Paid, 24 hours every hour on Workers Free. Healthy operation normally exposes the retention window plus up to one interval of records (7 to 8 days on Paid); scheduling delay or quota exhaustion can delay physical cleanup. This is a demo history policy, not a secure-erasure SLA or a guarantee about backups, provider recovery, or copies on clients.

### Retention semantics

- Expire records by their internal nondecreasing commit time, not message creation ID. Commit times are nondecreasing in log order, so expiry is always a prefix of the one server-wide log.
- Retain a current message while its latest record remains retained. Remove current state when its latest record expires. Tombstones and reaction sets follow the same rule; a move re-logs the moved message's reaction sets, refreshing them.
- A recent edit can keep a message visible past the retention window from creation. Its older creation/edit records may be removed; its latest complete snapshot is sufficient to reconstruct it.
- A registered user's membership is current state, kept in `memberships` after its record leaves the log (see "Memberships" in section 4).
- Room records are current state, like messages: a room keeps being listed with its latest record (and that record's original `log_id`) after the record itself leaves the log. A thread room whose entire log has expired is removed, and its members get `room_update` `left`.
- Physical row deletion is separate from logical visibility. History, edits, and lookups always enforce the published floor, including during partial cleanup.
- Passkeys and global/principal budgets are independent of chat retention. Dedup uses its own 24-hour expiry.

### Floor definition and wire shape

Internally maintain one server-wide positive log boundary F, initially 1. All
records with `log_id < F` have been logically discarded; records at/above F, if
committed, are available. F never decreases and is not a client checkpoint.
Advance F to one greater than the greatest record logically expired. If
nothing further expires, retain F. Future IDs must be at least F.

On the wire, each room reports its own values. `latest_log_id` is the room's
historical committed head H (the greatest `log_id` in its log), including when
history expires. `history_log_id` is the inclusive decimal-string coverage
boundary max(F, the room's creation `log_id`) while that is <= H, and `null`
when no history remains. A new room's history therefore starts at its creation
record. Clients derive the effective floor from a null value as H + 1; no
inverted range is sent on the wire. The boundary never decreases: F is
monotonic, and a room reports `null` only while F > H, so any later record in
the room is at least F.

Include both fields in every room record the server sends (`room_list`,
`room_update`) and every successful history result, without an extension
advertisement:

```json
{"method":"room_update","params":{"updated":[{"room_id":"general","log_id":"1789900000000","title":"General","latest_log_id":"1790000001000","history_log_id":"1789913600001"}]}}
```

```json
{"id":"h1","result":{"more":false,"latest_log_id":"1790000001000","history_log_id":"1789913600001"}}
```

This empty page can represent an out-of-range or expired query; only a room
whose retained log is empty uses `history_log_id: null`.

After advancing F, tell removed thread rooms' members first with `room_update` `left` (no storage access), then send every room whose `history_log_id` changed as `room_update` `updated` to the members of the room and of its parent, with the listing charged to the maintenance budget; a failed listing never suppresses committed removals. A cleanup job whose last batch reported more work (including thread rooms still awaiting removal) continues on its next run without the idle probe ending it. Attach both wire boundaries atomically with each history page's query snapshot; do not return entries evaluated under an older floor with a newer response floor. Capture response state synchronously without external awaits. Keep F monotonic on clients even if paginated responses arrive out of order.

### History queries

Follow protocol [§4.1](https://github.com/shazow/apron/blob/main/PROTOCOL.md#41-history): inclusive after/before, forward oldest selection when after is present, backward newest otherwise, always return each array ascending. Without `room_id` the default room `general` is paged; unknown rooms are `invalid_params`. A window with `after` equal to `before` returns exactly that record when it is retained in the requested room's log; a moved message's earlier snapshot is fetched from the room its `prev_room_id` names. Query only the intersection with the room's `[history_log_id, latest_log_id]`. `limit` counts records of every kind, and `first_log_id`/`last_log_id` span all kinds; results are partitioned into `rooms` (with the room's delivery fields), `messages`, `reactions`, and `memberships`, each omitted when empty. An empty or entirely expired range returns `more: false` and neither bound, with F; do not invent pagination IDs. History carries no `users`. No compaction is required for this version.

Select from the room's own log before the source-slice limit. With a byte cap, shrink the effective positive limit before selecting the final contiguous slice in the requested direction. Return its true first_log_id/last_log_id and more, accounting for records omitted due to either count or byte cap. Each allowed snapshot must fit into at least one response with envelope overhead. Forward continuation is last_log_id+1, backward continuation first_log_id-1; never use string ordering or message IDs for pagination.

A move's snapshot appears in both rooms' histories and carries the destination `room_id`; the message's earlier history stays in the source room. Threads are separate rooms with independent histories and floors.

### Client recovery

The implementing harness must add this behavior to the demo client:

1. Track the greatest advertised F per room. Remove cached snapshots whose greatest applied log ID is below F; remove expired pending rendering references. Preserve newer snapshots even when their message creation IDs are old.
2. A checkpoint C is usable for forward recovery only when `C + 1 >= F`. If `C + 1 < F`, some uncovered records were discarded: clear that room's recovered state/checkpoint and rebuild from F. This handles the exact boundary without needless resets at `C = F - 1`.
3. Capture head H when establishing live delivery. Recover forward through fixed H, buffer live entries above H, apply newer snapshots only, then drain the buffer. If F>H, the retained initial view is empty and subsequent live entries can proceed.
4. Before applying each page, inspect its F. If retention has overtaken the next unprocessed recovery position, discard the partial history replay and rebuild against the new floor while preserving the fixed head H and retained live entries buffered above it. Do not mark a silently truncated gap as recovered. Cancel or ignore obsolete in-flight requests by a local recovery generation.
5. An increased floor within already processed coverage need not restart recovery, but must evict newly expired snapshots. Bound live/recovery buffers (1 MiB or 1,000 entries); on overflow, clear partial recovery and reconnect/recover with backoff.
6. Each room's checkpoint is independent; threads are separate rooms. Eviction and asynchronous older pages must never resurrect snapshots below the current floor or overwrite a newer snapshot.
7. Room record updates (`room_update`, listings) do not advance checkpoints or replace an active fixed recovery head by themselves. The floor only invalidates unavailable history.

Include a visible demo notice that only roughly the last day is retained.

### Cleanup algorithm and failure recovery

Use a single scheduler backed by the DO alarm API. Due cleanup fixes a cutoff (`effective_now - retention`) and identifies an expired log prefix with indexed, bounded work. Persist logical floor advancement and a cleanup job before discarding its rows. Publish floor changes in commit order. If discovering the prefix requires several batches, advance the floor incrementally; each visible floor must match actual logical coverage.

Delete expired records, expired current message and reaction state, fully expired thread rooms and then their stored memberships, expired accepted-request entries, and expired limiter state in separately bounded, metered batches. Retained latest snapshots and necessary current state must not be accidentally removed with an older version of the same message. Never reset room head, floor, credentials, or live quota counters. A next task is scheduled until the job completes; ordinary cleanup starts every cleanup interval, continuation wakes only as needed and within the budget.

Retries are idempotent and work from persisted progress. A crash before or after any batch must preserve externally advertised coverage. If maintenance budget is exhausted, defer physical work until resources reset, suspend growth as needed, and do not spin alarms. Alarm/API failures must not permanently orphan cleanup: re-establish missing due work on subsequent valid activity as well as documented alarm retries. No live socket is needed to perform cleanup.

Use the same scheduler for unauthenticated socket deadlines, batching deadlines where possible; every alarm setup/invocation is accounted. Alarms are at-least-once and retries are finite: [Alarm API](https://developers.cloudflare.com/durable-objects/api/alarms/).

## 10. Degradation and public-demo behavior

| Exhausted resource | Required behavior |
| --- | --- |
| Principal posting limit | Reject new mutations with retry_after; allow affordable reads |
| Global daily posting/foreground write budget | Read-only until replenished; matching dedup retries may return stored results |
| Read/history budget | Reject history; do not fake an empty successful history page |
| Registration count/durable identity cap | Stop registration; existing logins and guest use continue if affordable |
| Storage high-water | Stop growth, clean expired data using reserve, resume only when safe |
| Socket/admission cap | Reject upgrade; existing sockets continue if affordable |
| Global frame budget | Stop processing new application work, close sockets, reject admissions until reset |
| Cloudflare hard limit or uncertain accounting | Fail closed; no automatic paid fallback |

Compute retry delay from the limiting window where known; when multiple limits apply, use the longest applicable delay. Capacity/storage retries may use a documented backoff estimate, not a false guarantee of future availability. Persist an optional operator-configured admission-off flag; it must not require migrating or deleting the object.

For a permanent policy cap with no automatic replenishment, such as the identity or thread-room ceiling, use `denied` with an explanatory reason such as `registration_closed` or `thread_limit`; do not induce endless retries with an invented reset time. The operator can raise a policy ceiling only after reassessing the resource budget.

Keep UI messages concrete: "Guest posting limit reached", "Demo is read-only until daily reset", "History temporarily unavailable", or "Demo capacity reached". No billing/SQL details in normal user flows. Do not silently drop a successful write, alter user content, or hide an error as success.

Support a standalone `ALLOWED_ORIGINS = "*"` to admit every guest origin, including opaque origins. Exact allowlist deployments reject unexpected browser origins before upgrade. Require explicit exact RP origins for WebAuthn even under wildcard guest admission; advertise WebAuthn only to connections from those origins. Non-browser clients with no Origin may use the public protocol subject to the same quotas; origin checking is not bot authentication. Reuse the existing Markdown sanitization and iframe restrictions. No backend URL fetching from embeds. Secrets never enter logs, public status responses, or source control.

Limit observability to bounded structured events and counters: operation category, accepted/rejected reason, daily resource reservations/actuals, active sockets, database bytes, oldest retained commit, floor/head, cleanup backlog, and alarm failures. Sample repetitive rejection logs and never persist request bodies, passkey challenges, or raw IPs to analytics.

## Appendix: status history

How this server's user status and mutes (section 4.4) followed changes to [PROTOCOL.md §4.11](https://github.com/shazow/apron/blob/main/PROTOCOL.md#411-status). Section 4.4 describes only what holds now.

- shazow/apron 9825e38 said to send every connected user's status after a sign-in and to show `dnd` as `dnd`. This server already left out users shown `offline` or `""` and showed `dnd` only while connected; since 48af29b both are what §4.11 asks, so it no longer deviates there.
- Presence once had two variants: `full`, which read push registrations (a waking registration made its user `idle`), and `connected`. Registrations no longer show anyone as `idle`, so they are one, and `PRESENCE` is `true` or `false`.
- Before 6bda48b, a client's `status` was a notification, and a refused mute change sent the sender the mute in effect; it is now a request, and a refused change sends only its error.
- Before 35c5631, a sign-in was any `auth` that signed the connection in; it is now one that signs it in as a user it isn't already signed in as. Listings carried `status` only with presence on, and clients dropped kept statuses after a reconnect of more than 60 seconds; listings now carry it always (`""` with presence off), and clients drop kept statuses at each sign-in. A connection that never sent `idle` counted as idle after ten minutes without a frame, as §4.11 then allowed; it now stays attended until it sends `idle: true`.
